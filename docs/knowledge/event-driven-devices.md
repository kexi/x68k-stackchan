# デバイスへ時間を渡す仕組みをイベント駆動にする

## なぜ JIT ではないのか

「実機比 100% (10MHz) には JIT しかない」というのが前回の結論だった。
根拠は「CPU 実行を空回しにすると 10000 kHz 出る = 残り 1.82x は全部
命令の実行」という実測。

**撤回後の実機で測り直したら上限は 5161 kHz しか無く、JIT を書いても
最大 1.03 倍だった。** 前回の数字は MFP の 8 サイクル quantum があった
状態のもので、その quantum は観測可能なずれを作るため撤回済み。撤回に
よって tickDevices が毎命令呼ばれるようになり、上限そのものが半減して
いた。

**古い実測値は、それが測られた条件が変わったら無効になる。**

## 内訳 (2026-08-17、CoreS3 実機)

命令の実行を空回しにして段階的に外した。

| 段階 | 実効 | ns/cycle |
|---|---|---|
| 通常実行 | 4992 kHz | 200.32 |
| 命令の実行を空回し | 5160 kHz | 193.80 |
| + tickDevices を外す | 13333 kHz | 75.00 |
| + 割り込み判定を外す | 7272 kHz | 137.51 |
| + 両方外す (ループ運営のみ) | 53323 kHz | 18.75 |

| 項目 | ns/cycle | 割合 |
|---|---|---|
| **tickDevices** | **118.76** | **59%** |
| **serviceInterrupts** | **56.25** | **28%** |
| ループ運営 | 18.75 | 9% |
| 命令の実行 | 約 6 | 3% |

**律速は 68000 の命令実行ではなく、命令ごとにデバイスへ時間を渡すこと。**

### 計測器自身がバイアスになる

最初は段階を実行時の `int` で見ていた。それだと計測器が毎命令の
ロードと分岐になり、測る対象にコストが乗る。テンプレート引数へ移したら
**床が 32000 → 53323 kHz へ動いた**。

本番の `'&'` スイッチで同じ誤りを一度犯している。**計測モードでも
「有効側の生成コードを変えない」規律が要る。**

## ゲストが実際に何を動かしているか (実機から読んだ)

設計は「次に状態が変わるまで何サイクルあるか」で決まるので、推測せず
実機から読む (シリアルの `'@'`)。

```
MFP TACR=08 TBCR=01 TCDCR=70
MFP TADR=00 TBDR=0D TCDR=C8 TDDR=00
MFP IERA=18 IERB=26 IMRA=18 IMRB=26
```

| タイマ | 制御 | 分周 | データ | 非同期イベントの間隔 |
|---|---|---|---|---|
| A | $08 | — | — | 外部入力モード。内部クロックでは進まない |
| B | $01 | 4 | 13 | **IERA bit0 が 0 なので割り込みを上げない** |
| C | $07 | 200 | 200 | 80,000 CPU サイクルごと |
| D | $00 | — | — | 停止 |

CRTC の垂直帰線が平均 90,171 サイクルごと、RTC の秒が 10,000,000
サイクルごと。合わせると **次のイベントまで平均 42,000 サイクル**、
1 命令 4 サイクルなら **約 10,000 命令に 1 回** で足りる計算になる。

### タイマ B が要点

分周 4 は最小で、8 CPU サイクルごとに 1 減る。これを「状態が変わる」と
数えると 2 命令に 1 回起きることになり、イベント駆動の意味が無い。

しかし **IERA bit0 が 0 なので `raise()` は早期リターンし、タイムアウト
しても何も起きない** (mfp.cpp の raise を見よ)。つまり非同期の影響は無い。

一方でカウンタは **ゲストが TBDR を読める**。だから無視はできず、
**読み出し時に実体化する (lazy materialization)** 必要がある。ここが
設計の核心で、「非同期に効くか」と「読めば見えるか」を分けて扱う。

### Human68k 起動後も同じだった (確認済み)

上の値は最初 IPL-ROM のエラー画面で読んだものだったので、「Human68k
到達後に IERA が変わればこの見積もりは崩れる」というリスクがあった。

Human68k 3.02 を retropc.net から取得し、`just make-hdd` で起動イメージを
作ってホストで確かめた (`--hdd ... --keys $'dir\n' --stats`)。

```
[mfp] TACR=08 TBCR=01 TCDCR=70 TADR=00 TBDR=0D TCDR=C8 TDDR=00
[mfp] IERB=26 IMRB=26 IPRB=00
[mfp] IERA=18 IPRA=00 IMRA=18 RSR=01 UDR=9D SR=2004
```

**完全に一致した。** `A>` プロンプトで `dir` が通る状態でもタイマ B は
割り込みを上げない。前提は成立する。

ホストで確かめられるのは、core/ が ESP32 非依存で同じコードが動くため。
**「実機でしか判定できない」のは速度であって、ゲストの設定はホストで
読める。** この区別は
[cores3-emulator-runtime.md](cores3-emulator-runtime.md) の
「ただし『実機でしか分からない』のは速度だけ」に一般則として書いた。

## 設計 (codex の案を採用)

### 毎命令の判定をゼロ比較に保つ

過去 2 回、動的 quantum を試して 2 回とも後退した (-18%、-6.5%)。原因は
**「毎命令の `pendingDeviceCycles_ >= deviceQuantum_` が定数比較から
変数比較になる分だけ高くつく。計算回数の問題ではなかった」**。

そこで **期限を負数で持ち、0 との比較だけにする**。

```cpp
std::int32_t wakeDebt_ = 0;   // arm 直後は -delta、期限を跨ぐと 0 以上
u32 wakeSpan_ = 0;            // 遅い側でしか読まない

void armWake(u32 delta) { wakeSpan_ = delta; wakeDebt_ = -static_cast<std::int32_t>(delta); }

// 毎命令
wakeDebt_ += used;
if (wakeDebt_ < 0) return;    // ここが最頻。ゼロとの符号比較だけ
settleTimedDevices();
```

実体化すべき経過時間は `elapsed = wakeSpan_ + wakeDebt_` で求まる
(期限前なら負の debt が実際の経過量になり、跨いだら正の値が
オーバーシュート量になる)。

第 2 オペランドのロードもレジスタ同士の比較も無い。

### quantum との違い

quantum は「N サイクルまとめて渡す」ので、ゲストがポーリングすると
**状態変化が遅れて見える**。3 回入れて 3 回撤回した理由がこれ。

イベント駆動は「次に状態が変わる時点」を計算して、**そこへちょうど
着地する**。着地点は 1 サイクルもずれない。加えて、

- レジスタを読む前に実体化する (lazy materialization)
- レジスタを書く前に、遅延中の時間を **旧設定へ** 適用してから書く

これを守れば、ゲストから見える値は命令ごとに tick した場合と完全に
一致する。

### 割り込み判定 (56.25 ns/cycle) も同じ機構へ

「割り込み線が変わるのはデバイスが進んだときだけ」では**不十分**。
線が同じでも配送可能性が変わる経路がある:

- RTE や MOVE to SR で CPU の割り込みマスクが下がる
- MFP の IMR/IER/ISR/VR が書き換わる
- マスク中に保留していたものが unmask される

**特に「マスク中に IPR が立つ → 後で SR が下がる」を落とすと、割り込みが
永久に配送されない。** デバイスのイベントだけを見る設計では捕まらない。

wake を要求する経路を契約として列挙する: MFP タイムアウト / CRTC→MFP の
エッジ / pressKey / 受理された moveMouse / 割り込み関連レジスタの書き込み /
FDC の線変化 / **CPU の SR マスク変更** (M68k::setSr でマスクが実際に
変わったときだけ callback)。

## 段階的な導入順

一度に全部やらない。各段で実機計測できる形にする。

1. 計測器をテンプレート化して数字を取り直す (**完了**。床が 32000 →
   53323 kHz へ動いた)
2. scheduler を shadow 動作させ、予測した期限が実際の最初の状態変化と
   一致するかを検証する
3. RTC と CRTC だけイベント化する (効果は小さいが配線を確かめる)
4. MFP を「次の 1 デクリメント」でイベント化する
5. serviceInterrupts を wake 型へ移す (単独で 28%)
6. 必要なら MFP を「次のタイムアウト」へ広げ、レジスタ読み出し時の
   lazy materialization を足す

A/B 切り替えはスライス境界で行い、**ホットループは別実体にする**
(variant の中に実行時のモード分岐を置かない)。

## 見積もり

| | 実効 (見積もり) |
|---|---|
| 現状 | 5006 kHz |
| tickDevices のみイベント化 | 約 11,900 kHz |
| + 割り込み判定も | 約 35,900 kHz |

毎命令に残る「負数加算 + ゼロ比較」を 3.1 ns/cycle として計上済み。

**これは見積もりであって実測ではない。** 上限 (両方外して 53323 kHz) を
超えることはない。実機で段階ごとに測って確かめる。
