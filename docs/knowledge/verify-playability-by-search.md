# 「遊べる」は探索で確かめる

## 問題

ゲームを移植して「遊べるか」を確かめたい。手で操作の台本
(何フレーム目に何を押すか) を書いて流すのが素直だが、**失敗したときに
何も分からない**。

- ゲームが本当に詰んでいるのか
- 台本の踏み切り位置が数ピクセルずれているだけなのか

この 2 つが区別できない。実際、移植中に台本を何度も書き直したが、
「渡れない」が続くだけで原因に近づかなかった。

## やり方

**ゲームのロジックを探索させる。** core/ がプラットフォーム非依存の C
なら、ホストで秒間数百万フレーム進められる。

到達した位置ごとに一番良い状態を 1 つ持ち、そこから全部の入力を
試して先へ広げる。ゴールに着く道が 1 本でもあれば「遊べる」。

```
  1-1: クリア可能 (444 フレーム)
  1-2: クリア可能 (444 フレーム)
  1-3: クリア可能 (448 フレーム)
  1-4: クリア可能 (444 フレーム)
  ボス: 倒せる
```

0.7 秒で回る。`just solve` として常設した。

### 探索の作り方で効いたこと

1. **高さも状態に含める。** x だけで 1 つに絞ると、同じ x でも
   「立っている状態」と「跳んでいる途中」が潰し合う。跳び越えるには
   跳んでいる状態を残す必要があり、潰すと「越えられない」という
   誤った結論になる。実際、x だけの版は越えられるブロックの手前で止まった。

2. **入力を続ける長さも枝分かれさせる。** 可変ジャンプは押した長さで
   高さが決まる。短い刻みしか試さないと穴を越える高さが出せない。

3. **1 手先だけ見ない。** 穴は縁に着いてから跳んでも間に合わず、
   手前で踏み切る必要がある。「今この瞬間に得か」では正しい手が選べない。

## 見つかったもの

**足場敵 (パタパタ) の上下が裏返っていた。** Y を `100 + wave` と
書いていたが、原作は `ENEMY_GROUND - wave`。一番低いときでも
足場として届かない高さになっていた。

1-2 と 1-3 は「広い穴を、敵を硬化させた足場で渡る」設計なので、
**この 2 ステージは物理的にクリア不可能だった**。手で台本を書いている
限り、これは「台本が下手」と見分けが付かなかった。

## 思い込みも 2 つ潰れた

探索を書く過程で、症状の読み違えが 2 つ表に出た。どちらも
「ボスが強すぎる」という誤った結論へ向かっていた。

- **「ボスに殺される」** → 実際はボスの手前を飛んでいる**コウモリ**に
  先に殺されていた。ボスの当たり判定を疑って調べ直す羽目になった
- **「ボスから逃げられない」** → 逃げた先が**穴**だった。HP に関係なく
  必ず同じフレーム数で死ぬのが手がかりで、それはボスの挙動では説明が付かない

**同じ数字が繰り返し出るときは、原因が「相手の強さ」ではなく
「地形のような固定のもの」であることが多い。**

## いつ使うか

- 移植や書き直しで「元と同じ挙動か」を確かめたいとき
- レベルデザインを変えたあと、詰みが生まれていないかを見たいとき
- 「手で試したら失敗した」が、それが実装のせいか操作のせいか分からないとき

単体テストは部品の正しさを測る。探索は**組み合わせた結果として
成立しているか**を測る。両方が要る
([[sprite-plane-not-composited]] と同じ構図)。
