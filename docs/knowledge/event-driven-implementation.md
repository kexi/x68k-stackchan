# イベント駆動デバイス — 実装確定版

## 内訳が入れ替わった。律速は命令実行へ移った (2026-08-17)

**イベント駆動でデバイス処理を削り切った結果、律速が 68000 の命令実行に
移った。** 実機で区間を分けて測った (スライス 60000、Human68k 稼働中):

| 項目 | ns/cycle | 割合 |
|---|---|---|
| **命令の実行そのもの** | **91.8** | **74%** |
| デバイス処理ほか (run 内) | 22.2 | 18% |
| run の外 (描画・入力・音声・yield) | 11.6 | 9% |
| 合計 | 125.6 | (= 7962 kHz) |

測り方: `run` の前後を `esp_timer_get_time()` で挟んで「run の中と外」を
分け、さらに**イベント駆動のまま `cpu_.step()` だけを空回しに**して
(シリアルの `'='`) 命令実行のぶんを引いた。空回しでは 36,924 kHz 出る。

### 「命令実行は 0.90 ns/cycle」は無効になっていた

セッション序盤にこう測っていたが、あれは **quantum を撤回した直後、
tickDevices が毎命令だった頃**の値。デバイス処理が 118.76 ns/cycle も
あったので命令実行が埋もれ、差分としてほぼ 0 に見えていた。

**古い実測値は、それが測られた条件が変わったら無効になる。** この
プロジェクトで 2 度目の同じ失敗 (1 度目は JIT の上限 10000 kHz)。

### JIT の評価が覆る

序盤に「JIT の上限は 1.03 倍」と測って却下したが、**あれも同じ条件下の
測定だった**。今の内訳で計算し直すと:

- 命令実行を無限に速くできたときの上限 = 22.2 + 11.6 = 33.8 ns/cycle
- = **29,586 kHz (実機比 296%)**
- 現状 7962 kHz に対して **3.7 倍**

目標 10000 kHz (100 ns/cycle) には、**命令実行を 28% 削れば届く**。
JIT でなくとも、インタプリタの命令実行を 3 割速くする手があれば足りる。

**却下した判断を、条件が変わったら見直すこと。**

## フラグ遅延評価を実装したが -3.6% (2026-08-18)

上限が +8.5% あると分かったので実装した。**結果は -3.6%。revert した。**

### 何をしたか

`setLogicFlags` を「値とサイズを控えるだけ」にして、実際に読まれたとき
(条件分岐など) に計算する形にした。V と C は常に 0 なので即座に落とし、
**N と Z だけを保留**する部分保留にした。

### 保留を命令境界でまたげなかった

最初は「命令をまたいで保留する」形にしたが、**テストが落ちた**。
SR を読む経路が 33 箇所ある (条件分岐、MOVE from SR、例外フレーム、
X フラグを見る ADDX 系、テストの覗き見…)。全部に解決を挿す必要があり、
1 つ漏らすと**古いフラグで分岐する**。症状が原因から遠い。

そこで `execute` から戻る直前に必ず解決する形にして、**保留を 1 命令に
閉じた**。正しさは出口 1 箇所で守れる (テストは全部通り、400M サイクルの
状態も完全一致)。

### だが、それでは削れない

1 命令に閉じると、省けるのは「同じ命令の中で複数回フラグを書く」場合
だけになる。そんな命令はほとんど無い。一方で**保留の記録 (値とサイズの
ストア 2 回) は毎回払う**。

実測 8280 → 7984 kHz (**-3.6%**)。

### 学んだこと

**上限が大きくても、その上限に近づく実装が安全に書けるとは限らない。**

+8.5% は「フラグを一切計算しない」ときの値だった。実際に近づくには
命令境界をまたいで保留する必要があり、それは SR の読み手 33 箇所すべてに
契約を持ち込む。**このプロジェクトで「無効化を 1 箇所漏らす」事故は既に
2 度踏んでいる** (fetch のポインタキャッシュ、そして今回の最初の試み)。

安全側に倒すと効果が消える。それが今回の構図。

## フラグ計算の上限が +0.3% から +8.5% へ変わっていた (2026-08-18)

**5 例目の「古い実測値が条件で無効になる」。**

前セッションで `setLogicFlags` を丸ごと空にして測り、**+0.3%** だったので
「フラグの遅延評価は割に合わない」と結論していた。今の条件で測り直したら
**+8.5%** (7896 → 8569 kHz、同一起動で往復して確認)。

当時は tickDevices が 118.76 ns/cycle あり、命令実行は全体の 0.5% しか
無かった。フラグ計算はその中の一部なので、差が誤差に埋もれていた。
イベント駆動でデバイス処理を削った今、命令実行は 73% を占める。

| | 前セッション | **今** |
|---|---|---|
| フラグ計算を省いた効果 | +0.3% | **+8.5%** |

### それでも目標には届かない

8280 kHz から +8.5% で **8984 kHz**。目標 10000 kHz には 1.21x が要る。

しかも **+8.5% は「フラグを一切計算しない」上限**で、遅延評価はそこまで
行かない。フラグを読むのは条件分岐 (分岐が全体の 24.4%) と一部の命令なので、
4 命令に 1 回程度は結局計算することになる。

加えて遅延評価は「保留状態」を持つので、SR の読み書き 95 箇所を組み替える
必要がある。**得られるのが 8.5% の一部で、変更範囲がコア全体**という取引。

### 測り方

`setLogicFlags` の先頭に `if (flagProbe_) return;` を置き、シリアルの
`'f'` で切り替えて同一起動内で往復した。**当然ゲストは壊れる**が、
「これ以上は削れない」という上限を知るには十分。

**上限を先に測れば、実装の前に見込みが分かる。** このセッションで
ブロックキャッシュを 2 度書いてから諦めたが、フラグは測るだけで
「届かない」と分かった。

## 命令長を解いてもブロックは効かなかった (2026-08-18)

最初のブロックキャッシュが失敗した原因は「命令長を静的に決められない」
ことだった。**そこを解いて組み直した。**

### 命令長デコーダ (m68k_length.h)

実効アドレスのモードから拡張ワード数を求める。MOVE / MOVEQ / 分岐を
対象にし、分からない命令には 0 を返して呼び出し側が打ち切る。

**全数検証済み。** 65,536 通りの命令語すべてについて、実際に 1 命令
実行して PC が進む量と突き合わせ、**3,268 件すべて一致**した
(制御が飛ぶものと対象外は除く)。テストは変異で落ちることも確認済み。

### それでも -9.2% だった

正しい命令長でブロックを組み直した結果:

| | 実効クロック |
|---|---|
| ブロック OFF | 7990 kHz |
| **ブロック ON** | **7256 kHz (-9.2%)** |

状態は完全に一致し (400M サイクルで 99998982 命令 / $ED0000=82773638)、
Human68k も起動する。**正しいが遅い。**

### なぜ遅いのか

ブロックに入るたびに払うものが、消せるものより多い:

| 消せるもの | 払うもの |
|---|---|
| `fetch` のキュー繰り上げと窓判定 | スロット検索 (シフト + マスク + ロード) |
| `execute` の switch (self time 0.15%) | タグ比較 |
| | 世代検査 2 回 (ページ番号 → 配列参照) |
| | 入口条件の判定 (halt/stop/pendingIrq/headroom) |
| | 命令ごとに pc/ir/irc を 3 回ストア |

とくに最後が効く。インタプリタの `fetch` は「キューをずらして 1 ワード
読む」だけだが、ブロックは**命令ごとに 3 つの値を書き戻す**。プリフェッチ
状態を毎回揃えないと例外フレームと PC 相対アドレッシングが壊れるので、
省けない。

### 実機で止まった件 (置き場の大きさ)

最初 PSRAM に 495KB (枠 4096 × 命令 32768) を確保したら、**実機で
エミュレーションが止まった**。ホストでは同速だったので気づけなかった。

内部 SRAM に載る大きさ (枠 2048 × 命令 8192) へ絞ったら動いた。
**PSRAM への散らばったアクセスは、まとまった読み書きとは別物。**
dbus のミス率 0.31% は「散らばっていない」状態での値だった。

### 残したもの

**命令長デコーダ (m68k_length.h) は残す。** 全数検証済みで、変異テストも
ある。ブロックやネイティブ化を再検討するとき、ここは作り直さなくてよい。

## ネイティブ発行の床を実測する (2026-08-18)

ブロックキャッシュが可変長命令で成立しないと分かった後、**Xtensa の
ネイティブコードを直接吐く**手が残っていた。着手する前に床を測った。

実行可能メモリへ「何もしない関数」(`entry` / `movi.n` / `retw.n`) を
置き、1000 万回呼んで実時間を測った (シリアルの `'n'`):

| | |
|---|---|
| **何もしない関数への呼び出し 1 回** | **58.7 ns = 14.1 CPU サイクル** |
| インタプリタの 1 ゲスト命令 | 約 85 CPU サイクル |

### これが意味すること

ブロックが組めない以上、ネイティブ化は「1 命令ごとにネイティブへ飛ぶ」
形しか取れない。すると **仕事を一切しなくても 85 サイクルの 17% を
呼び出しだけで払う**。

目標 10000 kHz には 1 命令 61 サイクル以下が要るので、呼び出しだけで
**23% を消費**する。残り 47 サイクルで実効アドレス計算・メモリアクセス・
フラグ計算をこなす必要があるが、これらはネイティブでも同じ処理量で、
インタプリタが既にやっていることと変わらない。

**ブロックが組めれば呼び出しは償却できる**が、それができないことは
既に実測済み (上記)。**前提が崩れているので、ネイティブ発行も成立しない。**

### 判断

**10000 kHz (実機比 100%) には、この構造では到達できない。**

打てる手をすべて実測で潰した:

| 手段 | 結果 |
|---|---|
| 即値のインライン化 | -3.3% (2 度試して 2 度とも) |
| MFP の rearm 削減 | ±0 |
| fetch のポインタキャッシュ | +0.2% |
| PSRAM の高速化 | 効かない (ミス率 0.31%) |
| コード配置の変更 | 効かない (I-cache ミス 0.003%) |
| ディスパッチ表 | 的が無い (self time 0.15%) |
| デコード済みブロック | **100 倍以上の劣化** (可変長命令で組めない) |
| ネイティブ発行 | **呼び出しだけで 17%** (ブロック不可なので償却できない) |

到達点は **8280 kHz (実機比 83%)**。セッション開始の 4842 kHz (48%) から
**+71%**。

10000 kHz に届く道が残っているとすれば、**命令長のデコーダを別に書いて
ブロックを組めるようにする**こと。それは「デコーダをもう 1 つ書く」ことに
等しく、本 PoC の範囲を超える。

## 効かなかった: デコード済みブロックキャッシュ (2026-08-18)

**実装して測ったら 100 倍以上遅くなった。revert した。**

### 何をしようとしたか

命令列を一度デコードして「命令語 + 実行後の PC + プリフェッチ状態」の
配列に落とし、`fetch` と `execute` の switch を毎命令払うのをやめる。
実行可能メモリ (最大連続 21KB) が要らないので、ネイティブ発行より先に
これを試す、という設計だった。

### なぜ効かなかったか

**68000 の命令長を静的に決められない。**

命令は 2〜10 バイトで、長さは実効アドレスのモードと拡張ワードの有無で
決まる。それを知るには命令語を実質デコードしないといけない。

ブロックを組むには「次の命令はどこか」が要る。2 バイト固定で並べると
2 命令目以降の `pcAfter` が実際とずれ、**規則 3 (PC が想定と違えば抜ける)
が毎回成立して 1 命令で抜ける**。つまりブロックが機能せず、毎命令
`buildBlock` を呼ぶことになる。

1 ブロック = 1 命令に留めても、消えるのは `execute` の switch だけ
(self time 0.15%)。代わりにスロット検索・タグ比較・世代検査 2 回が乗る。
**純粋なオーバーヘッド。**

実測: ホストで 1.67 秒 → 200 秒以上。

### 学んだこと

**「デコード結果を使い回す」は、命令長が可変だと成立しにくい。**
x86 や 68000 のような可変長命令では、ブロックを組む前に長さのデコードが
要る。そのデコードは `execute` の中でやっていることとほぼ同じなので、
「一度デコードして使い回す」の一度目が高くつく。

固定長命令 (ARM / RISC-V / MIPS) なら次の命令位置が自明なので、同じ設計が
素直に効く。**アーキテクチャの性質が設計の成否を決める。**

段 2 (実効アドレスのモードを解釈して命令長を求め、特化 uop を作る) まで
行けば成立しうるが、それは「デコーダをもう 1 つ書く」ことに等しく、
本 PoC の範囲を超える。

### 残したもの

**世代機構 (code_gen_map.h) は残す。** ゲスト RAM の書き換えを追う仕組みで、
3 経路すべてで変異テストが落ちることを確認してある。将来ブロックや
ネイティブ化を再検討するときの土台になる。コストは -1.84% だが、
**ストレージを与えなければ範囲外判定 1 回ぶん**しか払わない。

## JIT の的を実測する (2026-08-18、ホストで実測)

JIT の設計を決めるために 2 つ測った。**どちらも設計を大きく左右した。**

### 1. 命令フェッチの行き先は起動中と稼働中で逆転する

`refillPrefetch` を通る PC が IPL-ROM の窓内かを数えた
(Human68k 稼働中 + `dir`、9 億サイクル):

| | 起動中 (既存の記録) | **Human68k 稼働中** |
|---|---|---|
| IPL-ROM | 79% | **19.3%** |
| メイン RAM | 17.7% | **80.7%** |

**完全に逆転していた。** 起動が終われば Human68k 本体は RAM 上で動くので
当然だが、既存ドキュメントの「IPL-ROM 79%」だけを見て設計すると的を外す。

**「古い実測値は条件が変わったら無効になる」の 4 例目。**

これにより「ROM 窓に限ってブロックを作れば自己書き換えの無効化契約を
構造的に回避できる」という案は、動的実行の 2 割しか覆えないと分かった。

### 2. 実行は極端に集中している

ブロック先頭 PC のヒストグラム (PC を 2 で割って下位 16bit で畳んだ簡易集計。
衝突は集中度を過大評価する側に働くが、到達が 2,033 個しかないので影響は小さい):

| | 動的実行のカバー率 |
|---|---|
| **上位 50 ブロック** | **96.6%** |
| 上位 100 ブロック | 99.7% |
| 上位 200 ブロック | 99.9% |
| 到達したブロック先頭 | **2,033 個** |

**上位 50 でほぼ全部が取れる。** 21KB のコードキャッシュに対し上位 100 なら
1 ブロック 210 バイト使える計算で、threaded 形式 (8-16B/命令) なら
13-26 命令ぶん。ブロック上限 32 命令とほぼ一致する。

**容量は「足りる」側。** 的が絞れるので、小さいキャッシュでも当たりが良い。

## 実行可能メモリは 21KB しかない (2026-08-18、実機で実測)

JIT のコードキャッシュに使える量を測った (シリアルの `'j'`):

| | 空き合計 | **最大連続** |
|---|---|---|
| 現状 (IRAM 配置あり) | 31,196 | **21,504 バイト** |
| IRAM 配置を外した場合 | 46,812 | **36,864 バイト** |

**全命令の JIT には全く足りない。** 参考までに、現在 IRAM にある
インタプリタのコードは合計 25,797 バイト (`groupMisc` だけで 3,939)。
**JIT のコードキャッシュはインタプリタ本体より小さい**という制約下で
設計する必要がある。

### IRAM 配置を外すと実行可能メモリは増えるが、遅くなる

`X68K_HOT_PATH` を空にして測った:

| | 最大連続 | 実効クロック |
|---|---|---|
| IRAM 配置あり | 21,504 | **8280 kHz** |
| IRAM 配置なし | 36,864 (**+71%**) | 8131 kHz (**-1.8%**) |

**I-cache のミス率は 0.003% なのに -1.8% 落ちた。** ミス率だけでは
説明できない。IRAM は直接実行 (キャッシュを介さない) なので、ミスが
無くてもキャッシュのタグ引きとライン充填の待ちが無いぶん速い、と
考えるのが自然。

**ミス率が低いことは「配置を変えても影響しない」を意味しない。**
セッション中に「メモリ階層は律速ではない」と結論したが、それは
「PSRAM を速くしても効かない」までで、**IRAM と Flash の差は残る**。

JIT のコードキャッシュを広げるために IRAM を明け渡すのは、
**1.8% を先に失う取引**になる。

## JIT は実現可能だった (2026-08-18、実機で実測)

**`MALLOC_CAP_EXEC` で実行可能メモリが取れ、生成したコードが実際に走った。**

```
[jit] EXEC|32BIT -> 0x403da764
[jit] EXEC|32BIT で確保
[jit] 実行可能メモリ 0x403da764 / 生成コードの戻り値 = 10 (期待 10)
```

`main/main.cpp` の `probeJitFeasibility()` には「`CONFIG_ESP_SYSTEM_MEMPROT_FEATURE=y`
の間は `MALLOC_CAP_EXEC` が必ず失敗する (実測)」というコメントが付いていたが、
**現在の sdkconfig ではその設定が無効** (`sdkconfig:1312` が
`# CONFIG_ESP_SYSTEM_MEMPROT_FEATURE is not set`)。前提が変わっていた。

**「古い実測値は条件が変わったら無効になる」の 3 例目。**
(1) JIT の上限 1.03 倍 → 実は 3.7 倍
(2) 命令実行 0.90 ns/cycle → 実は 91.8 ns/cycle
(3) MALLOC_CAP_EXEC は必ず失敗 → 実は成功する

いずれも「測ったときの条件」を書き残していたおかげで気づけた。**数字だけ
でなく、それが成り立つ条件を一緒に書くこと。**

### JIT に投資する根拠が揃った

| | |
|---|---|
| 命令実行が占める割合 | **73%** (実測) |
| 命令実行を無限に速くしたときの上限 | **29,586 kHz** (実機比 296%) |
| 目標 10000 kHz に必要な削減 | 命令実行の **28%** |
| 実行可能メモリ | **確保できる** (実測) |
| メモリ階層 | 律速ではない (ミス率 0.003% / 0.31%) |
| 計算削減型の最適化 | **3 連続で外れた** (-3.3% / ±0 / +0.2%) |

インタプリタのままでは 28% が出ない見込みが強く、JIT には十分な余地がある。

## キャッシュミスは律速ではない (2026-08-18、実機で実測)

ESP32-S3 の EXTMEM カウンタ (`soc/extmem_reg.h`) を読んで、Human68k 稼働中の
ミス率を直接測った (シリアルの `'c'`)。

| | アクセス | ミス | ミス率 |
|---|---|---|---|
| **命令 (ibus)** | 518,285,291 | 15,725 | **0.003%** |
| **データ (dbus) の PSRAM** | 69,235,942 | 211,373 | **0.31%** |
| データ (dbus) の Flash | — | **0** | 0% |

**どちらもほぼゼロ。メモリ階層は律速ではない。**

これで次の 2 つが同時に否定された:

1. **PSRAM を速くしても効かない** (120MHz 化・OCT 化を検討する必要が無い)。
   そもそも CoreS3 の PSRAM は Quad 接続なので OCT にはできないが、
   速度を上げる余地も無いことがミス率で分かる
2. **コード配置を変えても効かない** (I-cache のミスが 0.003%)。IRAM への
   移動や、逆に Flash へ戻すことの効果は測るまでもない

### sdkconfig.defaults の「Why not 120MHz」は前提が変わっている

「±20℃ の温度変化でクラッシュする experimental 扱いだから避ける」と
書いてあり、判断としては今も妥当。ただし**その理由づけの前に「そもそも
効くのか」を測っていなかった**。当時はデバイス処理が律速で PSRAM を
速くしても効かない状況であり、今回ミス率 0.31% と実測されたことで、
**リスクを取る取らない以前に効果が無い**ことが確定した。

**「やらない」の理由は、リスクより先に「効かない」で足りることがある。**

## 効かなかった: fetch のポインタキャッシュ (2026-08-18)

**+0.2% (8264 -> 8280 kHz) で誤差の範囲。revert した。**

`fetch` は毎回「RAM の窓に収まるか」→ 外れたら「ROM の窓に収まるか」
(`fastRomHas` は base と length を引く) を判定してから読んでいた。分岐しない
限り PC は 2 ずつ増えるだけなので、同じ答えを毎命令計算し直していることに
なる。`refillPrefetch` で窓を 1 回だけ解決してポインタで持ち、`fetch` を
**ポインタ 1 比較**に縮めた。見込みは +8〜15% だった。

**実測は +0.2%。** 理由の見立て:

- 窓判定はどちらも数命令で、しかも分岐は毎回同じ方向 (RAM か ROM の
  どちらかに落ち着く) なので、分岐予測がほぼ当たっていた
- 削れたのは予測の当たる分岐と数命令だけで、88 CPU サイクル/命令に対して
  比率が小さい

加えて **無効化の契約を持ち込む** 危険がある。窓が変わる経路
(`setFastRam` / `setFastRamReadable` / `setFastRom` / `loadStateForTest` /
アドレスエラー) の全てでポインタを捨てる必要があり、1 つ漏らすと
「差し替わった実体の古いポインタを読み続ける」という追いにくい壊れ方を
する。実際 `loadStateForTest` の無効化を外す変異を **既存テストが検出
できなかった**。効果が誤差なら、この契約を抱える理由が無い。

**「毎命令の計算を減らす」型の最適化は、この構造ではもう効かない。**
削れる候補 (即値のインライン化 -3.3%、rearm の削減 ±0、fetch の
ポインタキャッシュ +0.2%) が 3 つ続けて外れた。88 CPU サイクル/命令は
「1 つの重い処理」ではなく、**命令グループ内部の分岐・ALU・フラグ更新と
複数回の operand アクセスの合算**という codex の見立てが裏付けられた
形になる。

## Human68k 稼働中の命令分布 (2026-08-18)

これまでの分布は **IPL-ROM の起動中** に採ったものだった。Human68k が
`A>` で動いている状態で採り直すと違う (9 億サイクル、`dir` 実行込み):

| グループ | 起動中 | **Human68k 稼働中** |
|---|---|---|
| 0100 misc | 25.4% | **32.7%** |
| 0110 分岐 | 21.5% | **24.4%** |
| 0010 MOVE.l | 3.0% | 9.9% |
| 0001 MOVE.b | 11.9% | 6.4% |
| 0000 即値/ビット | 13.5% | 4.2% |
| 1111 F-line | — | 0.6% |

**misc と分岐だけで 57%。** 最適化の的を選ぶときは、起動中の分布ではなく
こちらを見る。

### IRAM の配置状況 (実測)

`xtensa-esp32s3-elf-nm` で確認したところ、命令グループは既に IRAM
(`0x4037xxxx`) に置かれている。IRAM のコード合計は **25,797 バイト**。

| 関数 | サイズ |
|---|---|
| `groupMisc` | 3,939 バイト |
| `groupImmediate` | 2,140 バイト |

ESP32-S3 の IRAM は直接実行される (キャッシュを介さない) ので、ここに
入っているコードは Flash の I-cache 競合から自由。

### inline 化が 2 度とも -3.3% だった理由 (codex の見立て)

即値経路をヘッダへ出すと、**各命令グループへ条件判定と `fetch()` 本体が
重複展開される**。I-cache は 32KB / 8-way / 32B line なので:

- ホットな命令グループの working set が増える
- 32B line を余計に跨ぐ
- Flash 側の capacity/conflict miss が増える
- レジスタ圧と分岐も増える

一方 `readEaSlow` は 1 個だけで、しかも IRAM にある。**削れるのは安い
「IRAM への共通呼び出し」で、増えるのは Flash 上の複製コード。**
2 度とも -3.3% なのは測定ノイズではなく、この footprint 効果と見るのが
自然。

**1 命令 88 CPU サイクルは、ESP32-S3 の汎用 C++ インタプリタとしては
妥当な範囲** (codex の判断)。異常に重いわけではないので、28% を削るには
構造を変える必要がある。

## 効かなかった: 遅い側の回数を減らす (2026-08-17)

**遅い側へ落ちる回数を 25% 減らしても実効クロックは動かなかった。**

イベント駆動にしたあと、スケジューラの統計で「rearm が遅い側の 22.5%」と
出た。5 秒で 502 回、きれいに一定だったので周期的なアクセスと当たりを
付け、ホストで MFP のレジスタ別書き込み回数を数えた (9 億サイクル):

| レジスタ | 回数 |
|---|---|
| **UDR (送信データ)** | **11,202** |
| その他すべて | 各 1-2 回 (初期化のみ) |

80,343 サイクルに 1 回で、実機の 5 秒あたり 499 回。実測の rearm 502 回と
一致した。X68000 の IOCS がキーボードへ定期的にコマンドを送っている。

**UDR は本エミュレータでは値を捨てている** (送信先を持たない) ので、
状態が 1 ビットも変わらないのに期限を捨てて張り直していた。除外すれば
確実に減るはずだった。

実測: **rearm 502 -> 0、遅い側 2233 -> 1686 回 (-25%)。実効は
8141 -> 8020 kHz で変化なし** (むしろわずかに低い = 誤差)。

**遅い側の回数は律速ではない。** 547 回減らして効かないということは、
1 回のコストがごく小さいということ。期限を伸ばす (スライス長 20000 ->
60000) が効いたのは回数が減ったからではなく、**別の理由**だったことになる。

変更は revert した。「状態が変わらないなら rearm しない」は理屈として
正しいが、**理屈で正しいことと速くなることは別**。

次に詰めるなら、遅い側の回数ではなく **1 命令あたりに残っているコスト**
を直接測ること。実効 8020 kHz = 124.7 ns/cycle のうち、床 (18.75) と
命令実行 (0.90) を引いた **105 ns がどこにあるか**がまだ分かっていない。

## 1. 採用する設計と理由

### 採用: `debt_` 単一カウンタ + **保留中フォールバック** + **STOP 専用の飛び越し**

3 案の骨格 (負数 `debt_`、絶対サイクルの期限表、`Settled` トークン) は採るが、**攻撃で fatal と判定された 3 点で構造を変える**。

#### 変更 1: 割り込みは「wake エッジ」でなく「保留中フォールバック」で守る

deadline-cache 案は「配送可能性が変わる契機で `debt_ = 0`」という**エッジモデル**だった。これは interrupt-loss レンズの指摘どおり原理的に不足する。理由は 2 つあり、どちらも実コードで確認した。

1. **配送失敗は状態を変えない。** `serviceMfpInterrupt` (`machine.cpp:406-411`) はマスク中に `acknowledgeInterrupt` を呼ばずに `return false` する。IPR は立ったまま、wake だけが消費される。現行はこれを「次命令で必ず再試行される」ことに全面依存している。
2. **IoSc はレベル保持。** `acknowledgeInterrupt` が const (`iosc.h:170`) なので受理しても `status_` が下がらない。新しいエッジは二度と来ない。

**採る形**: `reachSlow()` の末尾で「保留があるのに 1 つも配送できなかった」なら **`debt_` を再 arm せず 0 のまま返す**。次命令の `debt_ += used` が必ず正になり、現行と同じ毎命令リトライへ縮退する。

```
保留なし        → 期限まで飛ぶ            (通常。ここで 28% が効く)
保留あり・配送済 → 期限まで飛ぶ
保留あり・不能  → debt_ = 0 のまま        (ハンドラ内。現行と同じ速度へ縮退)
```

これで**正しさが `setSr` フックの網羅性に依存しなくなる**。`setSr` callback は後から足す純粋な速度最適化になり、将来 SR を触る命令が増えても静かに壊れない。攻撃が maintainability として挙げた指摘をそのまま採用する。

> ハンドラ内が現行速度に落ちる代償は認める。X68000 は垂直帰線ごとに数千命令がハンドラ内なので、28% の削減は実効で目減りする。段 5 で実測し、足りなければ段 7 で `setSr` callback を**上乗せ**する (正しさの前提ではないので、いつでも外せる)。

#### 変更 2: `debt_` は期限専用にし、スライス終端を畳まない

perf レンズの指摘どおり `min()` は情報を落とす。「`debt_` と `span_` から理由を復元できる」は算術的に不可能で、タイのとき区別できない。スライス超過を検出できないとフレーム同期が壊れる。

**採る形**: スライス終端は `debt_` に入れず、`armDeadline` が `min(次イベント, スライス残り)` を取ったうえで **`sliceEnd_` を絶対サイクルで別に保持**する。`reachSlow()` は `now_ >= sliceEnd_` を見て終了を判断する。毎命令のホットパスは `debt_` の 1 分岐のままで、比較が増えるのは slow 側だけ。

#### 変更 3: STOP は専用の飛び越し経路を持つ

perf レンズの指摘どおり、`STOP` 中に `call8 M68k::step()` を 20,000 回回すのは**利得が最大のはずの区間での純粋な劣化**になる。かといってホットパスに `st_.stopped` のロードと分岐を足すのは規律違反。

**採る形**: `M68k::step()` は `stopped` のとき 4 を返す既存の契約を変えない。代わりに **`reachSlow()` の中で** `cpu_.state().stopped` を見る。STOP 中なら、そこから次の期限まで **1 回の `settle` で丸ごと飛ばして** `debt_` を張り直す。ホットパスは 1 命令も増えない。

STOP に入った直後は `debt_` がまだ負なので最大 1 期限ぶん (80,000 サイクル = 20,000 回の `step`) は空回りするが、その後は期限ごとに 1 回で飛ぶ。空回りを完全に消すには `M68k::setSr` の STOP 経路 (`m68k_ops_group4.cpp:167`) で `debt_ = 0` を書けばよい — これは正しさに要らない純粋な最適化なので段 7 に置く。

#### 変更 4: CRTC はイベント化しない (段 3 から外す)

timing レンズの指摘が正しい。`rasterNumber()` (`video.cpp:41-55`) は 568 段階すべてが観測可能な状態変化点で、平均 317 サイクルごとに値が変わる。`crtcEdge` (垂直帰線 2 点) では表現できず、`test_device_timing.cpp:324` が現に比較対象にしている。

**CRTC は毎命令 tick のまま残す。** `Crtc::tickFast` は既にインラインの早期リターン (`video.h:86-97`) で、`frameCycles_ += cycles` と 1 比較しかしない。ここをイベント化しても利得は小さく、`$E80028` 実装時に破綻する。**やらない。**

これは `tickDevices` の 59% のうち CRTC 分を諦めることを意味する。内訳の再測 (段 0) で CRTC 単独の寄与を先に確かめ、大きければ判断し直す。

#### 変更 5: `Settled` はデバイス単位でなく機械全体の証明にする

timing レンズの指摘どおり、`Mfp::read(Settled, kGpip)` の `Settled` が「MFP は実体化した」しか意味しないと GPIP4 (実体は CRTC) を守れない。ただし変更 4 で CRTC を毎命令 tick に残したので **GPIP4 は常に最新**であり、この穴は消える。それでも将来の再発を防ぐため、トークンは `Settled` 1 種類だけを `Scheduler` が発行する**機械全体の実体化証明**として定義する (デバイスごとに型を分けない)。

## 2. 毎命令のホットパス (確定版)

```cpp
// machine.h の private セクション。
// runWith の EventDriven=true 側だけが使う。
template <bool FastMfp, bool FastRtc, bool FastCrtc>
u32 Machine::runEventDriven(u32 cycles)
{
    sched_.beginSlice(cycles);   // sliceEnd_ = now_ + cycles; armDeadline()
    for (;;)
    {
        const u32 used = cpu_.step();
        if (used == 0)
        {
            // halted。溜まった時間を捨てずに実体化してから抜ける。
            // (attack: halt 経路だけ now_ が更新されない非対称を潰す)
            sched_.settleAndStop<FastMfp, FastRtc, FastCrtc>();
            break;
        }
        debt_ += static_cast<std::int32_t>(used);
        if (debt_ >= 0)                        // ← 毎命令の判定はこれだけ
        {
            if (reachSlow<FastMfp, FastRtc, FastCrtc>())
            {
                break;                          // スライス終端
            }
        }
    }
    return sched_.sliceSpent();
}
```

生成される Xtensa 命令列 (`-O2 -mlongcalls`、offset は vtable ぶん 0 にはならないので 20 と仮定):

```
.L3:
    mov.n a10, a7
    call8 _ZN4M68k4stepEv
    beqz.n a10, .L8              # used == 0 (halted のみ)
    l32i.n a8, a7, 20            # debt_ をロード      ← ロード 1 (narrow)
    add.n  a10, a10, a8          # debt_ += used       ← 加算 1
    s32i   a10, a7, 20           # 書き戻し            ← ストア 1 (wide)
    bltz   a10, .L3              # 期限前なら即ループ  ← 分岐 1
    mov.n  a10, a7
    call8  _ZN7Machine9reachSlowILb1ELb1ELb1EEEbv
    beqz.n a10, .L3
```

**ロード 1 / 加算 1 / ストア 1 / 分岐 1。** 現行の `spent < cycles` の `add.n` + `bltu` と `serviceInterrupts` の `call8` が消える。

### 攻撃で指摘された性能上の罠への対処

| 罠 | 対処 |
|---|---|
| STOP で `used==0` にならず空回り | `reachSlow` 内で `cpu_.state().stopped` を見て期限まで一括 settle。ホットパスは不変 |
| スライス終端を `min` に畳むと復元不能 | `sliceEnd_` を絶対サイクルで別持ち。`debt_` は期限専用 |
| halt 時に未実体化時間が消える | `used == 0` 経路で `settleAndStop` を必ず通す |
| `debt_` を offset 0 に置けない | Machine は多相基底 3 つ (`machine.h:48`) で offset 0 は vtable。**`perf_` の直後**に置き、offset ≤ 60 を狙う。`l32i.n` は narrow になるが `s32i.n` は適用外 — 設計根拠を訂正のうえ採用 (4 命令構成自体は変わらない) |
| IERA bit0 が立つと期限 8 サイクルで劣化 | `armDeadline` が「最小期限 < `kMinDeadline` (256 サイクル)」を検出したら **`debt_` を張らず毎命令 tick へ縮退**する (下記) |

### 最悪ケースの保護 (現行より遅くならない保証)

```cpp
// scheduler.h
static constexpr u32 kMinDeadline = 256;

void Scheduler::armDeadline()
{
    const std::uint64_t next = nextEventCycle();     // 全期限の min
    if (next == kNever) { armFallback(); return; }
    const std::uint64_t delta = next - now_;
    if (delta < kMinDeadline)
    {
        // 期限が近すぎる。イベント駆動のオーバーヘッドが利得を上回るので、
        // 毎命令 settle へ縮退する (現行と同じ形)。
        // Why not 0 を張らないか: 0 だと reachSlow が毎命令 call8 になり、
        // 現行のインライン早期リターン (mfp.h:131-135) より遅くなる。
        degraded_ = true;
        debt_ = 0;
        return;
    }
    degraded_ = false;
    span_ = static_cast<u32>(delta);
    debt_ = -static_cast<std::int32_t>(span_);
}
```

`degraded_` のときは `reachSlow` が `tickDevices` を呼んで `debt_ = 0` を書き直す。呼び出しは残るが、`Mfp::tickFast` のインライン早期リターンは効いたままなので現行 + `call8` 1 回で収まる。**IERA bit0 が立っても破綻せず、劣化幅が有界になる。**

## 3. 読み出し時に実体化しなければならないレジスタ (完全なリスト)

実体化 = `Scheduler::settle()` を呼び、`now_` から実経過ぶんをデバイスへ流す。**トークンはデバイスの `read`/`write` 側に置く** — `ioRead8` / `ioRead16` (`machine.cpp:841` で `ioRead8` x2 に落ちる) / DMA (`machine.cpp:933-941` が `bus_.read8` を直接呼ぶ) の 3 経路を一度に覆うため。

| # | レジスタ | アドレス | 実体 | 変化粒度 | 到達経路 |
|---|---|---|---|---|---|
| 1 | TADR | `$E8801F` | `timerValue_[0]` (`mfp.cpp:66-73`) | 分周 x 2 CPU cyc | `machine.cpp:577-591` |
| 2 | **TBDR** | `$E88021` | `timerValue_[1]` | **8 CPU cyc** (分周 4) | 同上 |
| 3 | TCDR | `$E88023` | `timerValue_[2]` | 400 CPU cyc (分周 200) | 同上 |
| 4 | TDDR | `$E88025` | `timerValue_[3]` | 分周 x 2 CPU cyc | 同上 |
| 5 | IPRA | `$E8800B` | `reg_[kIpra]`。`raise` (`mfp.cpp:281`) が立てる | タイマ A/B タイムアウト | 同上 |
| 6 | IPRB | `$E8800D` | `reg_[kIprb]` | タイマ C/D + GPIP4 | 同上 |
| 7 | RTC 秒〜年 | `$E8A001`〜 | `second_` 他 (`rtc.cpp:188-231`) | 10,000,000 cyc | `machine.cpp:604-607` |

**2 番の TBDR が設計の核心。** IERA bit0 = 0 なので割り込みは上げず期限計算に入らないが、ゲストは読める。実体化を落とすと quantum 撤回とまったく同じ観測可能なずれが読み出し側から再発する。

### 実体化が **不要** と確定したもの

|---|---|
| **GPIP ($E88001)** | **変更 4 で CRTC を毎命令 tick に残したので常に最新。**イベント化するなら必須になる |

`Mfp::peek` (`mfp.h:238-241`) は `reg_` を返すのでトークン不要のまま残す。ただし **タイマデータレジスタでは `read()` と値が違う** (`mfp.h:234-237` が明言)。ホストの `'@'` ダンプ (`host/main.cpp:1102-1111`, `main/main.cpp:1036-1041`) は `read()` 側へ寄せる — でないと古い値を出す。

## 6. fatal 判定への対処

| 攻撃の指摘 | レンズ | 対処 |
|---|---|---|
| GPIP4 は raise しなくても変化し、ゲストが読める | timing | **設計変更。CRTC をイベント化しない** (変更 4)。GPIP4 は常に最新になり穴が消える |
| STOP は 4 を返すので `used==0` で抜けない | timing / perf | **設計変更。`reachSlow` 内で `stopped` を見て一括飛ばし** (変更 3)。ホットパスは不変 |

| `rasterNumber` が同値テストの比較対象 (317 サイクル粒度) | timing | **CRTC をイベント化しないので発生しない**。`$E80028` を実装しても安全 |
| `Settled` がデバイス単位だと GPIP4 を守れない | timing | **トークンを機械全体の実体化証明に統一** (変更 5) |

### やらないと明示するもの

1. **CRTC のイベント化。** `rasterNumber` が 317 サイクル粒度で観測可能。利得より破綻リスクが大きい。毎命令 tick のまま残す。
2. **`setSr` callback を正しさの前提にすること。** 段 7 の速度最適化としてのみ足す。
3. **STOP 中の完全な空回り解消。** 段 7 で `m68k_ops_group4.cpp:167` にフックを足すまでは、STOP 突入後の最大 1 期限ぶんは空回りする。
4. **`step()` のイベント駆動化。** `step()` (`machine.cpp:170-193`) はトレース用で常に毎命令 settle (`degraded_` 相当) として扱う。`run()` との同値性を `test_device_timing.cpp:243` が守る。
5. **`runNullExec` のイベント駆動化。** 通さない。ただし**内訳を測り直す** (段 0) — 通さないままだと計測値が本番と乖離する。

## 7. 実機で段階ごとに測れる導入順序

各段は Human68k を起動した状態 (`A>` プロンプト) で測る。ディスク無しだと同じ変更が +3.17% と +6.40% で倍違った実測がある。`PerfSwitch` と同じく**同一起動内で切り替えて**測り、焼き直しの揺れ (3711 vs 3630 kHz) と効果を混ぜない。

### 段 0: 内訳の再測 (実機、変更なし)

**なぜ最初か**: CRTC をイベント化しない判断 (変更 4) が正しいかは、CRTC 単独の寄与を知らないと決まらない。`tickDevices` の 118.76 ns/cycle を MFP / RTC / CRTC に分解する。

**測り方**: `nullExecStage_` にステージを 3 つ足し、`tickDevices` から 1 つずつ外したテンプレート実体を作る。**実行時 `int` で見てはいけない** — 計測器自身が毎命令のロードと分岐になり、床が 32000 → 53323 kHz へ動いた前例がある。

**期待**: CRTC が 20 ns/cycle 未満なら変更 4 を確定。それ以上なら「垂直帰線 2 点だけの期限 + `rasterNumber` を bus 非到達のまま凍結」を再検討する。

### 段 1: shadow 検証 (ホストのみ、速度は変わらない)

期限を計算するが**飛ばさない**。毎命令 tick は現行のまま。予測期限と、実際に最初に状態が変わったサイクルが一致するかを `assert` する。

**測り方**: ホストで Human68k を起動 (`--hdd ... --keys $'dir\
' --stats`)。実機計測は不要。

**なぜここ**: 不一致が出るなら以降は全部無意味。実機に持っていく前にホストで潰す。

### 段 2: `updateFdcInterruptLine` を毎命令から外す

`machine.cpp:747` の `dmac_.write` 直後に 1 行足し (§5 の #21)、`machine.h:313` の毎命令呼び出しを消す。**イベント駆動の本体と独立**に入れられる。

> ⚠️ **この段だけでは `serviceInterrupts` の毎命令リトライを外さない。** IoSc はレベル保持なので (`iosc.h:170`)、リトライを同時に外すとフロッピー起動が retry ループから抜けなくなる (MEMORY の `$FF9058` と同じ場所を踏む)。外すのは `updateFdcInterruptLine` の呼び出しだけ。

**期待効果**: 28% のうち IoSc/FDC 分。単独で実機計測でき、以降の投資判断に使える。

**検証**: フロッピー起動が通ること。

### 段 3: `debt_` の配線を RTC だけで入れる

RTC は期限が 10,000,000 サイクルと最長で、**無効化の契約が最も軽い** — `Rtc::write` も `setDateTime` も期限を変えないと確定済み (`rtc.cpp:51-64`)。`Scheduler` / `Settled` / `sliceEnd_` / `reachSlow` の合流点をここで実機確認する。

**期待効果**: 小さい (RTC の tick は `rtc.h:77-87` で既にインライン早期リターン)。**目的は機構の検証。**

**壊れたときの症状**: 時計が止まる。分かりやすい。

### 段 4: MFP を「次のタイムアウト」でイベント化 + lazy materialization

TBDR/TCDR の読み出しで実体化する (§3 の 1-4)。**IERA bit0 = 0 という動的な事実に依存する**ので、IER 書き込みで期限を張り直す配線 (§4 の #5) とセットでしか入れられない。

**期待効果**: `tickDevices` の 59% のうち MFP 分。CRTC は残るので全部は消えない。

**検証**: `kMinDeadline` 縮退が効くことを、IERA bit0 を立てるテストで確かめる (§8 の T7)。

### 段 5: `serviceInterrupts` を wake 型 + 保留中フォールバックへ

最大の単一項目 (28%)。wake 契機 22 項目を配線する。**この段だけは効果が出ても正しさが確認できるまでマージしない。**

**実機で通す 3 つ**: キー入力 / マウス (連続ドラッグ) / フロッピー起動。

**期待効果**: 28% のうちハンドラ外の分。ハンドラ内はフォールバックで現行速度に縮退するので、**実効は 28% より小さい**。ここで実測して段 7 の要否を決める。

### 段 6: 内訳の再々測

イベント駆動を入れた後は内訳が変わる。「古い実測値は、それが測られた条件が変わったら無効になる」を一度踏んでいる (quantum ありの上限 10000 kHz が撤回後 5161 kHz だった)。**測り直さないと次の判断を誤る。**

### 段 7 (任意): `setSr` callback と STOP フックを上乗せ

段 5 の実測でハンドラ内の縮退が支配的だった場合のみ。`m68k.cpp:73-98` に「IPL が実際に下がったときだけ」の callback を足し、`m68k_ops_group4.cpp:167` (STOP) に `debt_ = 0` を足す。**正しさの前提ではないので、効果が出なければ捨てる。**

## 9. 実装を始める前に確かめること

1. **CRTC 単独の寄与 (段 0)。** 変更 4 (CRTC をイベント化しない) はこの数字で決まる。20 ns/cycle 未満なら確定、それ以上なら設計を見直す。**これを測らずに実装を始めない。**

2. **`Settled() = default` と `Settled() {}` の違いを Xtensa GCC 14.2.0 で実際に確かめる。** 攻撃レポートが実測で確認したと主張しているが、この 1 点が設計の型安全性の全体を支える。`xtensa-esp-elf-g++ 14.2.0 -std=c++17` で両方コンパイルし、`= default` 側が通ることを自分の目で見る。通らないなら T6 の形を変える必要がある。

3. **`debt_` を `perf_` 直後に置いたときの実オフセットと生成コード。** `machine.h:48` の多相基底 3 つで vtable がどこに入るか、`l32i.n` が効くか (offset ≤ 60) を `objdump` で確認する。効かないなら配置の設計判断を捨てる (4 命令構成は変わらないので致命的ではない)。

4. **`Mfp::hasPendingInterrupt` が `reachSlow` の中で呼ばれても十分速いか。** 現在は毎命令インライン (`mfp.h:256-264`) で、`IPR & IMR` が 0 なら即 return する。`reachSlow` へ移すと `call8` の中に入る。保留中フォールバックが働く区間 (ハンドラ内) ではこれが毎命令になるので、**現行のインライン版より遅くならないこと**を確かめる。遅いなら `hasPendingInterrupt` の早期リターンだけホットパスに残す設計変更が要る — ただしそれは分岐 1 本の追加になるので、規律との兼ね合いを段 5 で判断する。

5. **`reachSlow` の中で `Crtc::tickFast` へ渡すサイクル数が `kCyclesPerFrame` を超えないこと。** `video.h:54-58` のコメントどおり、超えると垂直帰線の開始/終了が**丸ごと消える**。RTC の期限 (10,000,000) だけを見て飛ばすと即座に踏む。CRTC を毎命令 tick に残す設計 (変更 4) ではそもそも `tickFast` に大きな値が渡らないが、**STOP の一括飛ばし (変更 3) だけは例外**。ここで必ず `kCyclesPerFrame` 未満に刻む。

6. **ホストの `'@'` ダンプが `peek()` を使っている箇所。** `host/main.cpp:1102-1111` と `main/main.cpp:1036-1041` を確認し、タイマデータレジスタは `read()` 側へ寄せる。でないと実体化が入った後に古い値を出し、**実機のゲスト設定を読み違える** — 段 4 の前提 (IERA bit0 = 0) を確認する道具そのものが壊れる。

7. **`kMinDeadline` の値 (256 サイクル) の妥当性。** `reachSlow` の `call8` + 期限再計算のコストを実測し、それを下回る期限では縮退させる。推測で決めず、段 3 の機構が動いてから測って決める。

## 結論: 10000 kHz (実機比 100%) はこの設計では届かない

**到達点は 8128 kHz (実機比 81%)。** 目標に必要な 1.23 倍を埋める手段が実測で尽きた。

### run の外の内訳 (2026-08-18、CoreS3 実機、イベント駆動 ON)

5 秒あたりの実時間を分離して測った:

| 区分 | 実時間 | 割合 |
|---|---:|---:|
| `run` の中 (命令実行 + デバイス) | 4542ms | 90.8% |
| 描画 (`renderTo`) | 214ms | 4.3% |
| その他 (`vTaskDelay` / 入力 / 音声) | 244ms | 4.9% |

**「描画を Core0 へ移す」の上限は +4.5% だった。** 直前まで 9% を根拠に +7% と見積もっていたが、
それは描画・入力・音声・yield を一括りにした数字で、描画だけを分離すると 4.3%。
残る 4.9% の主体は `vTaskDelay` で、ウォッチドッグ対策なので移せない。

`renderTo` はエミュレーションコアが持つテキスト VRAM を読むため、Core0 へ移すと
所有権の境界をまたぐ。**+4.5% のためにデータ競合の対処を入れる価値はない**と判断した。

### 手段が尽きたことの根拠

必要なのは 1.229 倍。すべて実測済み:

| 手段 | 実測 |
|---|---|
| 描画を Core0 へ移す | **+4.5%** (唯一残っていた正の未実装手段) |
| フラグ計算の除去 | 上限 +8.5% だが**実装すると -3.6%** |
| デコード済みブロックキャッシュ | **-9.2%** |
| ネイティブ発行 | 呼び出しだけで 14.1 サイクルの床 (17%) |
| メモリ階層 (PSRAM / 配置) | 効果なし (キャッシュミス率で確認済み) |
| CPU クロック | 240MHz で **ESP32-S3 の上限** |

唯一の正の手段を足しても 8505 kHz。残るのは真の動的リコンパイルだけで、
上の「床」を覆す必要があり、別プロジェクト規模になる。

### 計測でつまずいた点 (再発防止)

**`g_eventDrivenEnabled` の既定は `false`。** シリアルの `$` で切り替わる。
これを送らずに測ると 5446 kHz (毎命令版) が出る。**8128 と 5446 を取り違えると、
無関係な変更を「大幅な後退」と誤診する。** 実際にこのセッションで一度誤診した。

トグルのキーは `$` であって `` ` `` ではない (`main.cpp` の `isEventDrivenToggle`)。
切り替え時に `イベント駆動: ON` がログへ出るので、**計測スクリプトはこの行を必ず確認する**。

## 床を測り直したら 14.1 → 6.7 サイクルだった (2026-08-18)

**上の「ネイティブ発行の床 = 14.1 サイクル」は 2 つの理由で過大だった。**
JIT に本腰を入れる判断の前に測り直したところ、**実費は 6.7 サイクル**だった。

### 何が混ざっていたか

| | CPU サイクル |
|---|---:|
| 文書に記録していた値 (windowed + ループ込み) | 14.1 |
| 空ループ 1 周 (`for` の増分と分岐) | 4.7 |
| **呼び出しの実費 windowed** (`callx8` + `entry` + `retw.n`) | **9.3** |
| **呼び出しの実費 call0** (`callx0` + `ret.n`) | **6.7** |

**理由 1: ループのコストを引いていなかった。** 1000 万回回す `for` 自体が
4.7 サイクル使う。JIT の実コードはこのループを持たないので、床に含めてはいけない。

**理由 2: windowed ABI で測っていた。** 計測コードは `entry a1, 32` /
`retw.n` を発行し、呼び出し側も `callx8` だった。レジスタウィンドウの回転は
**JIT が `call0` を選べば payしなくてよい**コストで、差は 2.6 サイクル。

### 結論が変わる

目標 10000 kHz には 1 命令 61 サイクル以下が要る。

- 旧: 呼び出しだけで 23% を消費 → **ブロックが組めない以上、不可**
- 新: 呼び出しは **11%**。残り 54 サイクルで 1 命令ぶんの仕事をすればよい

さらに**ブロックが組めればこの 6.7 は複数命令で償却される**。命令長デコーダ
(`m68k_length.h`) は全数検証済みで完成しているので、ブロックは組める
(組んだ結果 -9.2% だったのは、pc/ir/irc を命令ごとに 3 回ストアしていたため。
ネイティブ発行ならブロック内でレジスタに保持できる可能性がある)。

**「10000 kHz は不可」という上の判断は、この測り直しで前提が崩れた。**

### 教訓 (6 回目)

「古い実測値は、それが測られた条件が変われば無効になる」の 6 例目。
今回は条件が変わったのではなく、**最初から交絡が入っていた**。

**床を測るときは、床でないものを引く。** ループ・ABI・呼び出し規約は
測りたい対象ではない。差分を取れば分離できたのに、絶対値だけ見て
「不可」と結論していた。

## 命令長デコーダに偽陰性があった (2026-08-18)

JIT の可否は被覆率 h (翻訳できた命令 / 実行した命令) で決まる。
実ワークロードで測ったら **h = 28.2%** で、必要な 48〜80% に遠く届かなかった。

**原因はデコーダのバグだった。** 番兵の衝突で、レジスタ間 MOVE が
軒並み「翻訳できない」と判定されていた。

### 何が起きていたか

```cpp
inline constexpr u32 kUnknownLength = 0;   // 命令長の番兵

inline u32 eaExtensionWords(...)           // 拡張ワード数を返す
{
    case 0: return 0;                      // Dn は拡張ワード無し ← 正当な 0
    default: return kUnknownLength;        // 不明 ← 同じ 0
}
```

拡張ワード数は **0 が正当な値** (Dn や (An) は拡張ワードを持たない) なのに、
「不明」の番兵も 0 だった。呼び出し側は `srcWords == kUnknownLength` で
不明を判定していたので、**拡張ワードを持たない実効アドレスがすべて
「不明」に化けた**。

MOVE 系 12,288 通りのうち翻訳できたのは **1,260 通り (10.3%)** だけだった。

### 修正

拡張ワード数の番兵を命令長の番兵と分ける (`kUnknownExtensionWords = 0xFFFFFFFF`)。

| | 修正前 | 修正後 |
|---|---:|---:|
| MOVE 系の翻訳可 (全数) | 10.3% | **86.4%** |
| 実ワークロードの h | 28.2% | **49.1%** |
| 連続翻訳できる平均長 | 1.27 命令 | **1.58 命令** |

### なぜテストが通っていたか

**全数検証のテストが偽陰性を検出しない形だった。**

```cpp
const u32 length = instructionLength(op);
if (length == kUnknownLength) { continue; }   // ← ここ
```

「翻訳できると判定した命令が正しいか」しか見ておらず、`kUnknownLength` を
返した命令は飛ばしていた。だから **3,268/3,268 一致で通り続けた**。

取りこぼしはブロックを短くするだけで**正しさは壊さない**。速度としてしか
現れないので、正しさのテストでは原理的に捕まらなかった。

**「保守的側に倒すのは安全」という設計判断が、テストの盲点を作っていた。**
安全側の誤りは、それを数える手段を別に用意しないと見えない。

対策として「対象グループを取りこぼさない」テストを追加した (変異で落ちることを確認済み)。

### 判断への影響

h = 49.1% なら、必要な Chit は **36 サイクル以下**。
呼び出しは連続 1.58 命令で償却して 4.2 サイクル/命令なので、
残り 32 サイクルで 1 命令ぶんの仕事をすればよい。

さらに $4 misc (実行の 32.3%) を足せば h = 81% まで伸びる余地がある。
**「JIT は不可」の根拠だった数字が、2 つとも測り直しで変わった** (床 14.1→6.7、h 28→49)。

| その他 (TRAP, MOVE to/from SR, CHK…) | 729,664 | 1.9% |
| JMP / NOP / PEA / LINK / UNLK | 1,363 | ~0% |

**推測で選ばず、実行頻度で選ぶ。** 静的な出現頻度ではなく動的な実行頻度が
要る (ループ内の 1 命令は 1 回しか現れないが何万回も実行される)。

### 判別ビットを実装と揃える

単項演算 (NEGX/CLR/NEG/NOT/TST) を `(op >> 9) & 7` で判定して TST を
取りこぼした。実装 (`m68k_ops_group4.cpp` の `unary_ops`) は
`(op >> 8) & 0xF` で switch していて、TST は `0xA`。

**判別に使うビット位置は実装からコピーする。** 自分で導出すると、
今回のように「6.5% を占める命令が丸ごと落ちる」形の取りこぼしになる。
この誤りは正しさを壊さないので、テストではなく h の計測でしか見えなかった。

TST は読むだけなので PC 相対と即値も取れる (書く方の NEGX/CLR/NEG/NOT は取れない)。
ここを一律に禁じると、また取りこぼす。

### 結果

| | h | 連続長 | 必要な Chit |
|---|---:|---:|---:|
| 当初 | 28.2% | 1.27 | **到達不能** |
| 番兵を分ける | 49.1% | 1.58 | 36.1 サイクル |
| $4 を足す | 74.2% | 3.66 | 52.7 サイクル |
| TST を直す | **80.7%** | **5.63** | **55.3 サイクル** |

$4 の翻訳率は 97.9%。**連続長が 1.27 → 5.63 命令に伸びたのが大きい。**
呼び出しの 6.7 サイクルが 1.2 サイクル/命令まで償却され、
仕事に使える予算が 54.1 サイクルになった。

**インタプリタ (85 サイクル/命令) に対し、ネイティブが 1.57 倍速ければ
10000 kHz に届く。** 当初の「呼び出しだけで 17% 消えるので不可」とは
まったく違う状況になった。

命令長の検証は全数で 13,073 命令 (従来 3,268) が実行と一致することを確認済み。

## JIT の前に潰した 2 つの潜在バグ (2026-08-18)

どちらも「今は誰も使っていないので症状が出ない」が、ブロックの有効性判定に
使い始めた瞬間に**古いコードを静かに実行する**形の失敗になる。

### 1. 世代が 65,536 回で一周していた

`CodeGenMap::touch` は `std::uint16_t` を無条件にインクリメントしていた。
**65,536 回書くと元の値に戻る。** 戻った瞬間、書き換えられたページが
「変わっていない」と判定される。1KB ページに 65,536 回の書き込みは、
スタックやワーク領域なら数秒で届く。

飽和させて `kAlwaysStale` (0xFFFF) で止める。以後そのページは世代では
判定できないので、呼び出し側はバイト照合へ落ちる。**遅くなるが正しい。**

`generation()` が範囲外に 0 を返していたのも直した。0 は「まだ一度も
書かれていないページ」と区別できず、範囲外に置いたブロックが有効に見える。

ホットパスに比較 1 本が増えるが、実機で 8128 → 8139 kHz と差は出ていない。

### 2. 写像の変化をページ世代で表現できていなかった

`setFastRam` / `setFastRamReadable` / `setFastRom` は「どの番地に何が
見えるか」を変えるが、**ゲスト RAM の中身は 1 バイトも変わらない**。
ページ世代は書き込みしか数えないので、この変化を取りこぼす。

取りこぼすと、$000000 の ROM 写像が外れる前後で古い前提のまま実行する。

`mappingEpoch` を足し、5 経路すべてで進めるようにした
(setFastRam / setFastRamReadable / setFastRom / reset / loadStateForTest)。
ブロックの鍵にこの値を含めれば、写像が変わった瞬間に全ブロックが自分から
無効になる (pull 型のまま扱える)。

`setFastRamReadable` は**値が変わるときだけ**進める。同じ値で呼ばれる
たびに全ブロックを捨てるのは無駄なので。

### どちらも変異テストで固定した

- 飽和をやめて素の `++` に戻す → 2 assertion が落ちる
- `setFastRamReadable` の epoch を消す → 2 assertion が落ちる

## Cavg モデルの重みを検証した (2026-08-18)

`Cavg = h*Chit + (1-h)*(85+Cmiss)` の「85」は全命令の平均。
**翻訳できない命令だけが平均より重いなら、このモデルは楽観的すぎる。**

実測 (Human68k 稼働中、ゲストの公称サイクル数):

| | 1 命令あたり |
|---|---:|
| 翻訳できる命令 | 10.07 |
| 翻訳できない命令 | 10.55 |
| 全体 | 10.17 |

**差は 5% で、偏りは無視できる。** 翻訳から漏れた命令が特別に重い
(あるいは軽い) ということはないので、全命令平均の 85 サイクルを
そのまま使ってよい。

Why これを先に測るか: エミッタを書く前に、モデルの前提が崩れていないかを
確かめられる。崩れていたら Chit をいくら小さくしても届かないので、
実装に入る前に分かる方がよい。

## h_decode と h_native は別物だった (2026-08-18)

**80.7% は「命令長が分かる」割合であって、「ネイティブの直線コードとして
続けられる」割合ではない。** Codex のレビューがこの点を指摘し、測ったら
実際に大きく違った。

ブロックは次の理由で切れる。長さが分かっても切れる:

| 切れた理由 | 回数 | 割合 |
|---|---:|---:|
| 分岐 (taken) | 6,726,571 | 43.3% |
| 呼出・復帰 (JSR/RTS/JMP) | 4,702,892 | 30.3% |
| 書込 (ゲスト RAM) | 4,115,340 | 26.5% |

### 数字

| | h | 平均区間長 | 必要な Chit | インタプリタ比 |
|---|---:|---:|---:|---:|
| h_decode (長さが分かる) | 80.7% | 5.63 | 55.3 | 1.57 倍 |
| **h_native (書込で切る)** | **41.2%** | **1.47** | **26.7** | **3.84 倍** |
| h_native (書込で切らない) | 51.6% | 1.81 | 38.5 | 2.44 倍 |

**区間長が 5.63 → 1.47 命令に落ちる。** 呼び出しの 6.7 サイクルが
1.2 → 4.6 サイクル/命令になり、予算を大きく食う。

### 書込で切るかは設計の選択

切る側: 書いた先が自分の後続命令なら翻訳済みコードが古くなる。
その場で終端すれば必ず正しい。

切らない側: **ブロックの途中へ飛び込む経路は無い**ので、「次にこの
ブロックへ入るとき」に世代を検査すれば足りる。自分自身を書き換えた
場合も 1KB ページの世代が上がるので入口で捕まる。

切らない設計なら h が 41.2% → 51.6%、必要な速度が 3.84 → 2.44 倍になる。
**ただし支配的なのは分岐と呼出・復帰 (合計 73.6%) で、こちらは消せない。**

### 教訓

**「翻訳できる」と「ネイティブで走り続けられる」を取り違えない。**
前者だけを測ると、呼び出しコストの償却を 4 倍近く過大に見積もる。

これは h_decode を測った時点では気づけなかった。実行時の状態
(分岐が成立したか、書込先はどこか) が要るので、静的な解析では出ない。

## direct chaining を入れると判定が変わる (2026-08-18)

0-C2 の結果は「4 倍速でも黄信号」だったが、**ブロック間直結
(direct chaining) を仮定していなかった**。

分岐が成立したとき、検索とゲートウェイを払って次のブロックへ入るのではなく、
生成コードから直接飛べる。分岐はブロックが切れる理由の 43.3% を占めるので、
ここが効く。

| 想定 | h | 区間長 | E_budget | 必要な速さ |
|---|---:|---:|---:|---:|
| 書込で切る | 41.2% | 1.47 | 15.5 | 5.47 倍 |
| 書込で切らない | 51.6% | 1.81 | 29.4 | 2.89 倍 |
| **+ direct chaining** | **60.9%** | **2.08** | **37.7** | **2.25 倍** |

C_pred (最良の想定):

| ネイティブ本体 | C_pred | 判定 |

| 2 倍速 | 63.9 | No-Go |
| 3 倍速 | 55.3 | 黄信号 |

| 6 倍速 | 46.7 | Go |

**ネイティブ本体がインタプリタ比 4 倍なら Go の線 (52) に入る。**

ただし direct chaining には条件が付く:

- BSR は戻り番地をスタックへ積むので直結できない (除外して数えた)

## 段 0-C3: ネイティブ命令本体の実費 → 判定は Go (2026-08-18)

残る未知は「ネイティブの命令本体がインタプリタ比で何倍か」。
エミッタは書かず、**JIT が吐くであろう形を C++ で手書きし、-O2 の
生成コードを実機で測った** (Xtensa のエンコーディングを自分で組むのは
2 度失敗しているので、コンパイラに吐かせる)。

実機 CCOUNT、200 万回、空ループ (7.34) を差し引き済み:

| | サイクル |
|---|---:|
| MOVE.w D0,D1 + N/Z フラグ | 測定限界以下 (保守的に 2.0 と置く) |
| MOVE.w (A0),D1 + 境界検査 + ビッグエンディアン組立 + N/Z | **5.07** |
| MOVE.w D1,(A0) + 境界検査 + 世代更新 | **10.45** |
| Bcc の条件評価 + debt 更新 + 期限判定 | **1.98** |
| **分布で重み付け** (レジスタ30/読み30/書き20/分岐20%) | **4.61** |

**インタプリタ 85 サイクルに対し 18.5 倍速。** 必要だったのは 4 倍。

### 判定

| 想定 | h | 区間長 | Chit | C_pred | 判定 |
|---|---:|---:|---:|---:|---|
| 書込で切らない | 51.6% | 1.81 | 13.7 | **48.2** | **Go** |
| + direct chaining | 60.9% | 2.08 | 12.5 | **40.8** | **Go** |

基準は C_pred ≤ 52 で Go。**どちらの設計でも Go の線に入る。**

### 18.5 倍が妥当な理由

インタプリタの 85 サイクルの中身は、fetch・switch 2 段・実効アドレス計算の
関数呼び出し・メモリアクセス・フラグ計算・debt 更新・pc/ir/irc のストア。
**ネイティブが消せるのは前 3 つと最後**で、残るメモリアクセスとフラグ計算が
4.61 サイクルに相当する。

0-C2 で測ったブロック固定費 16.40 の方が本体 4.61 より大きいことも、
この見立てと整合する。**JIT の利得は命令本体を速くすることではなく、
命令ごとの間接費を消すことにある。**

### 最適化で消える計測を 3 回踏んだ

このプローブだけで 3 回「負の値」が出た:

1. 出口の状態書き戻し → 静的変数への固定ストアがループ外へ持ち上げられた
2. Bcc → SR が固定で条件が定数畳み込みされ、分岐そのものが消えた
3. レジスタ間 MOVE → 転送元が不変で結果が不変になった

いずれも**空ループぶんちょうどのマイナス**として現れる。
差分を取る計測では、消えた側が必ず負になるので気づける。
プローブに「負の値があれば無効」と出す判定を組み込んだ。

**ループごとに入力を変える。** アドレス・フラグ・転送元のどれかが
固定だと、測りたいものが丸ごと消える。

### 未計上の費用

翻訳の初回コスト、再翻訳と eviction、21KB に散る生成コードの I-cache
ミス、偽共有によるバイト照合、$4 の misc (MOVEM/JSR/RTS) の本体、
実エミッタのレジスタ割り当てが手書きより下手になること。

**余裕は C_pred 40.8 に対し Go の線 52 まで 11.2 サイクル。**

## 前提 A: ALU 群が 1 つも翻訳できていなかった (2026-08-18)

段 1 の設計をワークフローで検討した際、**着手前に潰すべき前提**が 3 件
見つかった。その 1 つ目。

`instructionLength` の `switch` にある `case` は MOVE / MOVEQ / Bcc / $4 だけで、
**$8 (OR/DIVU) / $9 (SUB) / $B (CMP/EOR) / $C (AND/MULU) / $D (ADD) は
`default:` に落ちて `kUnknownLength` を返していた。**

危険なのは、この状態で段 1 に着手すると:

- 対応範囲に「単純な ALU」を挙げても**一度も真にならない死んだコード**になる
- テストは「ALU を弾く」ことを緑で確認して通る
- 被覆率を測ると、測定器 (`instructionLength`) の欠落を
  **測定対象 (ワークロードの性質) だと読み違える**

### 足した形

5 群はどれも `gggg rrr ooo mmm rrr` で、`opmode = (op >> 6) & 7` で意味が変わる。
実装 (`m68k_ops_alu.cpp`) の判別と揃えた:

- opmode 3 / 7 → ADDA/SUBA/CMPA (word/long) または DIVU/DIVS/MULU/MULS (word 固定)
- メモリ方向 かつ mode 0/1 → ADDX/SUBX/SBCD/ABCD/EXG/CMPM。**保守的に諦める**
  (判別が群ごとに違い、実行頻度も低い。諦めてもブロックが短くなるだけ)

### 結果

| | h_decode | h_native (chaining 有) | 区間長 | C_pred |
|---|---:|---:|---:|---:|
| ALU 前 | 80.7% | 60.9% | 2.08 | 40.8 |
| **ALU 後** | **91.6%** | **71.3%** | **3.07** | **31.5** |

全数検証は 13,073 → **28,964 命令**が実行時の PC 進行と一致することを確認。

**C_pred 31.5 は Go の線 (52) に対して大きく余裕がある。**
目標 61 サイクルに対して 29.5 サイクルの余裕。

## 前提 B: 分岐の命令長が全数検証から除外されていた

`test_scheduler.cpp` の全数検証は分岐を `continue` で飛ばしていた
(成立すると PC が飛ぶので長さの検証にならないため)。

**ブロックは分岐で終端するのが中心**なので、ここが穴のままだと
`Bcc.w` の長さ 4 が 2 に化けてもテストが全部通る。

不成立にすれば PC の進み方がそのまま命令長になる。CCR を 0 にしてから
`BEQ` (cond=7) を置けば Z=0 で必ず不成立。BRA/BSR は飛ぶので、
命令長を直接問う形で固定した。

変異 (`Bcc.w` の 4 を 2 にする) で 3 assertion が落ちることを確認済み。

## 前提 C: CodeGenMap が未配線で「常に古い」が「常に有効」に化ける

`setStorage` の呼び出し元はテストの 1 箇所しか無く、`main/` にも `host/` にも
無かった。未配線だと `pageCount_ = 0` なので `generation()` は全アドレスに
`kAlwaysStale` (0xFFFF) を返す。

ここが罠で、素朴に照合すると:

```
控えた世代 == 今の世代   →   0xFFFF == 0xFFFF   →   一致
```

**「常に古い」ではなく「常に有効」になる。** 自己書き換えを一切検出しない
ブロックキャッシュが成立してしまう。飽和は「スタックやワーク領域なら
数秒で到達する」ので、配線しても実機で必ず踏む。

対処は 2 つとも要る:

1. `main/` と `host/` で 4KB (2048 ページ × 2 バイト) を確保して配線する
2. **照合を「`kAlwaysStale` でない かつ 一致」にする**

2 が本体。1 だけでは飽和したときに同じ穴が開く。テストで固定した
(素朴な照合が通り、正しい照合が通らないことを両方 CHECK する)。

### 配線のコストは 0.45%

実機で 8139 → 8102 kHz (13 サンプル、8053〜8119)。**誤差ではない。**
`pageCount_ = 0` の間は `touch()` の分岐が一度も成立しなかったが、
配線後は毎回インクリメントが走るため。

書き込み 1 回あたり load + 比較 + add + store。1 命令あたり平均 0.5 回の
書き込みに対して 0.45% は妥当な値。**JIT が成立すればこのコストは
回収できる**が、成立しなければ払い損になる。

## 段 1: ポータブルな block plan と翻訳器 (2026-08-18)

**Xtensa のエミッタはまだ書かない。**「ブロックを正しく組める」ことだけを
core/ 側で確定させ、ホストで全数検証できる形にする。

### 置いたもの

| ファイル | 中身 |
|---|---|
| `core/cpu/native_exec.h` | 注入 API。`NativeExit` (kRan / kDeferToStep)、事前・事後条件 |
| `core/cpu/block_plan.h` | `BlockPlan` / `PlannedOp` / `kMaxOps = 4` |
| `core/cpu/block_planner.h/.cpp` | 翻訳器。不変条件 I1〜I9 |
| `test/test_block_plan.cpp` | 全数テスト (14 TEST_CASE / 118,855 assertion) |

### 戻り値を 3 状態にした理由

`u32` で「0 = 実行できなかった」とすると、**「未対応命令の手前」「halted」
「割り込みの受理が要る」の 3 つを区別できない**。区別しないと halt を
「未対応」と読み違えて `step()` を無限に呼ぶか、割り込みを飲み込む。

`kDeferToStep` 1 つで表すが、**`step()` が 3 つとも正しく処理する**ので
実行器側は理由を区別しなくてよい。区別が要るのは統計だけ。

### 不変条件で効いたもの

**I4 の `+2` が要点。** ブロックの出口では `irc == mem16(fallThroughPc + 2)`
が成り立っている必要がある。`fallThroughPc` までしか見ないと、
**出口で `irc` に入るワードが窓の外に出る**。`+2` を消す変異で
2 assertion が落ちることを確認済み。

### 翻訳器に Bus も M68k も渡さない

入力を関数ポインタ (`PlanSource::read16`) で閉じた。M68k を持つと
テストが `Machine` を立てないと書けなくなる。命令長デコーダが
65,536 通りの全数検証をできているのは入力が `u16` だけで閉じているから。
**同じ性質を保つ。**

副作用の禁止も明示した。バスを叩くと**翻訳しただけで MFP の割り込み
要因レジスタが動く**。

### EOR を許可リストから外した

設計は「ADD/SUB/AND/OR/EOR/CMP のレジスタ間」としていたが、**EOR は
68000 の符号化上 `$B` のメモリ方向にしか存在しない**。そこは
`m68k_length.h` の `isSpecialForm` が CMPM と区別できないため
`kUnknownLength` を返す。

`plan` は I1 (長さ) を I2 (許可リスト) より先に見るので、**EOR を
許可リストに入れても一度も真にならない死んだコード**になる。
これは前提 A が名指しした失敗形そのもの (テストは「弾く」ことを
緑で確認して通る)。

実装者と、独立にテストを書いた側が**別々に同じ結論**へ到達した。
命令長デコーダが `$B` の特殊形を判別できるようになったら、
実装とテストの許可リストを**一緒に**開ける必要がある。

### テストを実装者に書かせない

自分の実装に対しては「通るように書く」バイアスが入る。**仕様
(I1〜I9) から独立に「安全な命令」の集合を組み直し**、65,536 通りで
実装と突き合わせて偽陽性 0 / 偽陰性 0 を確認した。

さらに許可リストが受けた 5,120 件を**実際に `M68k::step()` で実行**して
halt しないことを 68000 の実装そのものに問うテストを足した。

### 変異で確かめた

9 種類の変異を注入し、すべて落ちることを確認 (実装者・テスト作者・
攻撃役の 3 者が別々に実施):

I1 の `instructionLength` 除去 / I4 の `+2` 除去 / I7 の奇数分岐先 /
I8 の BSR 除外 / MOVE の mode 検査 / Bcc.w の不成立 12→8 /
成立側を「不成立 +2」で導く / 分岐先の基準 `pc+2`→`pc+4` /
ALU の opmode 3/7 検査。

### 設計の計算違いを 1 つ直した

`sizeof(BlockPlan)` は設計の「約 96 バイト」ではなく**実測 112 バイト**。
256 ブロックで 28,672 バイト、世代配列 4,096 と合わせて 32,768 バイト。
内部 SRAM の空き 48,351 バイトには収まるので結論は変わらないが、
数字を残す以上は実測値にしないと後段の見積もりがずれる。

### 攻撃役が見つけた 2 件を直した

段 1 の実装を別のエージェントに攻撃させたら、変異テストでは捕まらない
種類の欠陥が 2 件出た。**どちらも「変異が全部 killed」の外側にあった。**

**1. 誤った正当化が正しい結論を支えていた。**

I4 のコメントが「同一ページに収まればブロック内のプリフェッチも出口の
状態も**原理的に窓を外れない**」と書いていた。これは誤り。
**ページに収まることと窓に収まることは別の性質**で、現在の窓
(メイン RAM 2MB / IPL-ROM 128KB) の境界がたまたま 1KB 整列している
ために一致して見えているだけ。

窓の判定は I3 が別に担っている。今は無害だが、**危険なのはバグ自体より
間違った理由が正しい結論を支えていること**。段 2 で誰かがこのコメントを
読んで「I4 があるから窓は考えなくてよい」と信じると、`setFastRam` の
長さを変えた瞬間に「インタプリタでは一度も起きなかったバスエラー」が出る。

コメントを直し、「I4 があるから窓を考えなくてよい、とは読まないこと」を
明記した。

**2. `entryPc == 0` の番兵が守られていなかった。**

`BlockPlan::entryPc` の 0 は「空きスロット」を意味するのに、番地 0 から
翻訳しない検査が無かった。番地 0 のブロックを作ると**空きスロットと
区別できない計画**ができる。

X68000 では $000000-$0003FF が例外ベクタテーブルなので通常そこにコードは
無い (リセットは番地 4 から PC を読む) が、**「通常無い」に頼らない**。
番兵の意味は 68000 の都合とは無関係に守られるべき。検査とテストを足し、
変異で落ちることを確認した。

### 変異テストの限界

攻撃役の指摘が正しい: **8 変異が全部 killed でも、それはテストが名前を
付けた不変条件への攻撃でしかない。**想定の外 (窓端をページ内に置く /
`entryPc == 0`) は素通りした。

「変異が全部 killed だから安全」と読むと**実際の被覆範囲を過大評価する**。

### 残る既知の穴: kMaxOps の妥当性は段 1 では検証できない

許可リストが MOVE/MOVEQ/ALU/Bcc のレジスタ間形だけなので、実ワークロードの
ブロック長は 1〜2 命令に張り付く。すると `kMaxOps` を 4 から 16 に上げる
変異は**何も落とさない**。

「落ちない = 安全」と「落ちない = テストが効いていない」が区別できず、
**割り込み受理の遅れの上限**という安全性に直結する定数が根拠を持たないまま
段 2 へ引き継がれる。段 2 で許可リストを広げたら、真っ先にここを問う。

## 段 2: Xtensa エミッタ (2026-08-19)

**エンコーディングを推測しない。** このプロジェクトは手で組み立てて 2 度
失敗している。段 2 では `xtensa-esp32s3-elf-as` を正解として使い、
エンコーダの出力と機械照合した (1,412 通りで不一致 0)。

### 突き合わせが素朴な想定を覆した 3 か所

推測で書いていれば全部間違えていた:

1. **`movi.n` は RRRN ではなく RI7。** 対象レジスタは `t` でなく `s`
   フィールドに入り、7bit 即値は `imm[6:4]` が `t`、`imm[3:0]` が `r` へ
   分かれる。負値も 2 の補数ではなく「`imm[6:4] == 7` なら -32..-1」という
   非対称な規則 (範囲が -32..95 なのはこのため)
2. **`extui` は `op1` が `maskimm-1`、`op2` が `0x4|sae[4]`。**
   `shiftimm` の bit4 が `op2` へ繰り上がる分割を忘れると、16 以上が
   16 小さい値に化ける
3. **`j` の下位 6bit は `0x06`。** CALL 形式の `0x05` と 1 違いで、
   取り違えるとサブルーチン呼び出しになって a0 を潰す

**`objdump -d` の逆アセンブル欄は 3 バイト命令をバイト逆順で表示する。**
`objdump -s` (メモリ順) を正とすること。

### オフセットのスケールが命令ごとに違う

| 命令 | オフセットの符号化 | 範囲 |
|---|---|---|
| `l32i.n` / `s32i.n` | 4 で割る | 0-60 |
| `l32i` / `s32i` | 4 で割る | 0-1020 |
| `l16ui` / `s16i` | **2 で割る** | 0-510 |

`M68kState` の実測オフセットは d[0..7] が 0-28、a[0..7] が 32-60、
**pc が 72 / sr が 76 / ir が 78 / irc が 80**。d/a はコンパクト形が届くが、
**pc 以降は届かない**。sr/ir/irc は 16bit なので `l16ui` / `s16i` が要る。

### 攻撃で見つかった 3 件

**1. ゲートウェイが窓の外のレジスタを壊していた (実害あり)**

飛び先を `a12` に置いていたが、コンパイラが吐く `entry a1, 32` は
**call4 の窓 (a0-a3 のみ)**。a12 はこの関数の窓の外で、物理レジスタ
ファイル上は**祖先フレームの生きた値**が入っている。WINDOWBASE を回さずに
書くと、呼び出し元のさらに呼び出し元のローカル変数を静かに壊す。

窓のオーバーフロー例外で物理レジスタがメモリへ落ちて初めて症状が出るので、
**呼び出し深さに依存して散発的に現れる**。

引数の順を `(state, code)` にすると a2 = 第 1 引数 / a3 = 第 2 引数で
そのまま収まり、**mov が 1 つも要らない**。実ファームのオブジェクトを
逆アセンブルして `entry a1,32` / `callx0 a3` / `retw.n` の 3 命令に
なることを確認済み。

**2. `isync` を呼ぶ人がいなかった**

`syncInstructionCache()` の呼び出し元が 0 件。ヘッダは「書いた直後に必ず
呼ぶ」と書いていたが、**それを守る仕組みが無かった**。失敗の形が
「1 回目だけ壊れる」なので、規律では守れない。

`commit()` を足して isync をその中に畳み、`isCommitted()` で確定済みかを
問えるようにした。`reset()` は確定の印も戻す (同じ番地へ別のコードを
書いたのに isync を省くと、古い命令が残ったまま実行される)。

**3. 成立側の出口がテストの死角だった**

同値テストは分岐成立側で pc/ir/irc を比較から外している (飛び先の
プリフェッチは `branchTo` が詰め直す契約なので)。そのため**成立側で
生成コードが何を書いても全 446,888 assertion が緑のまま通る**。

危ないのは「速度のために成立側でも pc を書けば `branchTo` が省ける」と
誰かが思いつくこと。pc だけなら正しいが、ir/irc を足した瞬間に壊れる。
壊れ方は「I/O の余分な読み出し」か「インタプリタでは起きなかった
バスエラー」で、**エミュレータの正しさのテストではなく実機の挙動として出る**。

usp/ssp に対して既にやっているのと同じバイト列走査で、pc/ir/irc への
ストアが**不成立側の 1 件だけ**であることを問うテストを足した。
成立側で `ir` を書く変異で落ちることを確認済み。

### まだ繋がっていない

`NativeExec` を満たす実行器が無く、`setNativeExec` も `tryNative` も未実装。
**速度はまだ 1 回も測っていない。**残りは §5.4 (`mustDeferToStep` の入口
検査) と §5.5 (鍵の照合) とブロックキャッシュ。

## 実機検証: IRAM へバイト書き込みはできない (2026-08-19)

段 2 を実機へ配線して初めて分かったこと。**ホストのテストでは原理的に
見えない**種類の失敗。

### 症状

JIT を ON にすると実効クロックが 8155 → 5415 kHz へ落ち、統計がすべて 0。
5415 は「イベント駆動 OFF」の値 (5446) にほぼ一致する。

**真因は再起動だった。** シリアルログを掘ると:

```
Guru Meditation Error: Core 1 panic'ed (LoadStoreError)
PC : 0x42016d77   EXCVADDR: 0x403daa3c
```

`addr2line` で `xtensa_encoder.h:77` の `emit16` — つまり**生成コードを
書いている最中**。落ちて再起動し、起動時の既定 (毎命令 tick) に戻るので、
「遅くなった」ように見えていた。

### 原因

**ESP32-S3 の IRAM は 32bit 単位でしか読み書きできない。**
エンコーダは `out[0] = ...; out[1] = ...` とバイト単位で書くので、
`MALLOC_CAP_EXEC` で取った領域へ直接発行すると必ず落ちる。

`MALLOC_CAP_32BIT` を付けても「32bit でアクセスすれば使える」だけで、
**バイト書き込みが許されるようにはならない**。`exec_memory.cpp` の
コメントは制約を正しく書いていたが、**エンコーダ側がそれを守る形に
なっていなかった**。

### 直し方

通常の RAM に控えを持ち、そこへ発行してから **32bit 単位で写す**。

```cpp
alignas(4) std::uint8_t staging_[512];
...
emitBlock(plan, fallIr, fallIrc, staging_, need, emitted);
const std::size_t words = (need + 3) / 4;
auto* dst = reinterpret_cast<volatile std::uint32_t*>(buf);
const auto* words32 = reinterpret_cast<const std::uint32_t*>(staging_);
for (std::size_t i = 0; i < words; ++i) { dst[i] = words32[i]; }
```

### 次の失敗へ進んだ

修正後、例外が `LoadStoreError` から **`IllegalInstruction`** に変わり、
位置も `emit16` から **`runBlock` の中** へ移った。

**つまり「コードを書けない」段階は抜け、「書いたコードが実行される」
段階に来た。** 生成コードが不正な命令を含んでいる。

### 教訓

**ホストのテストは「バイト列が正しいこと」までしか問えない。**
446,888 assertion が緑でも、そのバイト列を**実機の IRAM へどう置くか**は
1 つも検査していなかった。

計測が「遅くなった」と出たとき、**真っ先に疑うべきは計測系ではなく
再起動**だった。5415 kHz という値が既知の別モードの値と一致していたのが
最大の手がかりで、そこに気づくまでに数回の測り直しを費やした。

## 実機で JIT が動いた (2026-08-19)

**生成した Xtensa コードが実機で正しく走り、Human68k が動き続ける。**
ブロック 1,999,173 本 / 2,068,110 命令を実行。

### 落ち続けた真因: callx0 が a0 を潰す

`callx0` は戻り番地を **a0** に書く。ところが a0 は windowed ABI の
戻り番地でもあり、`runBlock` の出口の `retw.n` はそれを使って戻る。

**callx0 が上書きした a0 のまま retw.n を実行すると、自分自身の
retw.n の番地へ戻ろうとして IllegalInstruction で落ちる。**

証拠: パニック時に **PC == A0 == retw.n の番地**。

`clobber` に `"a0"` と書いても GCC は退避コードを出さない。a0 は
「entry / retw が面倒を見る」前提の特別なレジスタなので、通常の
caller-saved と同じには扱われない。**自分で退避するしかない。**

退避先も罠だった:

| 退避先 | 結果 |
|---|---|
| 制約なし (GCC が選ぶ) | **a12 を選ぶ**。`entry a1, 32` の窓の外で祖先を壊す |
| `a3` に固定 | 入力オペランドと衝突してコンパイルできない |
| **スタック** | **正解**。窓と無関係に安全。コストは s32i/l32i の 2 命令 |

### 切り分けの手順が効いた

「生成コードが悪いのか、経路が悪いのか」を分ける最小プローブを置いた:

| 実験 | 結果 |
|---|---|
| A: windowed コードを普通の関数ポインタで呼ぶ | **成功** (段 0 と同じ形) |
| B1: 素の `callx0` をインラインアセンブラで | **成功** |
| B1b: 同じものを 2 回目 | **成功** |
| B2: `runBlock` 経由 | **落ちる** |

**同じ番地の同じコードが、呼び方だけで結果が変わる。**
これで「メモリでもエンコーディングでも isync でもない」と確定し、
ゲートウェイ 3 命令に絞り込めた。

途中で疑って外れたもの: IRAM へのバイト書き込み (これは本物のバグで
別途修正済み)、l32r とリテラルプール、確保のタイミング、
`M68kState` のスタック消費、`runBlock` の flash 配置、a4-a11 の退避。

**a4-a11 は clobber に書けば足りる。** 特別扱いが要るのは a0 だけだった。

### いまは遅い (8156 → 3994 kHz)

統計が理由をそのまま示している:

| | 値 | 意味 |
|---|---:|---|
| ブロックあたり命令数 | **1.03** | 呼び出しコストが償却できていない |
| 翻訳失敗 | **8,819,504** (実行の 4.4 倍) | **失敗を控えていない**ので毎回翻訳し直す |
| タグ外れ | 421,771 (実行の 21%) | 256 スロットでは足りない |

段 0 の見積もり (h_native 71.3% / 区間 3.07 命令) と実測が食い違うのは、
**段 1 の許可リストが MOVE/MOVEQ/ALU/Bcc のレジスタ間形だけ**だから。
h_decode 91.6% は「命令長が分かる」割合で、ブロックに**入れられる**割合は
ずっと小さい。

次に効くのは、この 3 つを順に潰すこと。

## JIT が遅い 3 つの原因を潰した (2026-08-19)

実機で JIT が動くようになった直後は **3994 kHz** (JIT OFF の基準は 8150)。
統計が原因をそのまま示していたので、順に潰した。

| 段階 | 実効クロック |
|---|---:|
| 実機で動いた直後 | 3994 |
| 翻訳失敗を覚える (相乗り版) | 4905 |
| スロットを 40 バイト化して倍増 | 5258 |
| 負のキャッシュを別表に | **5330** |

### 1. 翻訳失敗を覚えていなかった

`translate()` が失敗時に何も残さないので、同じ番地に来るたび
`BlockPlanner::plan()` を呼び直していた。**失敗がブロック実行の 4.4 倍**。

最初は成功ブロックのスロットへ相乗りさせたが、畳み先が同じ失敗番地同士が
互いを追い出して不十分だった。別表 (2048 件 × 8 バイト) にした。

**相乗りにはもっと悪い失敗もある。** 負の記憶が成功ブロックを追い出すと、
追い出された番地は再翻訳のたびに実行可能メモリを新しく食う (解放しない)。
負と正が 1 組で往復するだけで 16KB を使い切り、JIT 全体が止まる。

### 2. スロットが BlockPlan をまるごと持っていた

実行時に使うのは鍵と生成コードの位置とサイクル数だけで、`ops[]`
(20 バイト × 4 = 80 バイト) は翻訳の途中でしか要らない。落として
120 → 40 バイトにし、同じ内部 SRAM で 512 スロット (旧 256) を置いた。

**2 の冪でなければならない。** 768 にしようとして気づいた。`slotIndex` が
マスクで畳むので、767 をマスクに使うと 0..767 を返すものの一様でなく、
衝突が偏る。

### 3. 予測が外れ、それが原因の特定に効いた

設計は「翻訳失敗 20,000 未満 / クロック 5500-6500 kHz」と**反証可能な形**で
予測していた。実測は 4,411,602 / 5330 kHz で大きく外れたので、
設計が挙げた候補を順に潰した:

| 仮説 | 検証 | 結果 |
|---|---|---|
| 相乗りが原因 | 別表にした | 改善したが不足 |
| 偽共有で世代が動く | **世代を鍵から外して実機で測った** | **変化なし。誤り** |
| 表が小さくて追い出し | 1024 → 2048 | **-3% だけ。誤り** |

**残る失敗は「初めて見る番地」だった。** 未対応の番地が数千種ある。

`run()` の内訳: ブロック実行 18% / 負ヒット 50% / 翻訳失敗 32%。
**82% がネイティブで実行できない。** これがブロックあたり 1.03 命令の正体。

### 教訓: 予測は外れる形で書くと役に立つ

「速くなる」ではなく「翻訳失敗が X から Y へ」と書いてあったから、
外れたことが分かり、**次に何を疑うべきかが決まった**。
「世代を鍵から外して測る」のように、**正しさを一時的に捨てて原因だけを
見る実験**が切り分けに効く (もちろん捨てた版はコミットしない)。

### 次: 許可リストを広げる

段 1 の許可リストは MOVE/MOVEQ/ALU/Bcc の**レジスタ間形しかない**。
Tier A (静的・ガード不要: MOVE An,Dn / MOVEA / MOVE #imm,Dn / TST Dn /
CLR Dn / LEA) だけで**実行の 16.2%** を占める。しかも全候補が既に
`instructionLength` を通るので、前提 A の失敗形にはならない。

## Tier A: 許可リストを広げた (5330 → 5520 kHz)

ブロックあたり 1.03 命令の原因は、許可リストがレジスタ間形しかないこと。
**メモリに触れず例外も起きない形**だけを足した (Tier A)。

足したもの: MOVE An,Dn / MOVE #imm,Dn / MOVEA の 3 形 / TST Dn / CLR Dn /
LEA の 4 形。**§5.3 の前提を 1mm も動かさない**のが Tier A の定義で、
実行時ガードが要らない。

| | 実測 |
|---|---:|
| 実効クロック | 5330 → **5520 kHz** |
| ブロックあたり命令数 | 1.03 → **1.20** |
| ブロック実行 | 2,642,274 → **3,339,560 本** |

### サイクル数は実装から取る

| 命令 | 値 | 注意 |
|---|---:|---|
| TST Dn | 4 | |
| **CLR Dn** | **6** | **サイズによらず。実機の 68000 は .b/.w が 4** |
| LEA | 4 | EA の形によらず |

**実機の値へ「直す」と JIT ON/OFF でサイクルが割れる。** JIT の契約は
「インタプリタとビット単位で同一」なので、実装の値を写す。全数のサイクル
検証テストがこれを機械で固定している。

### フラグの扱いが命令ごとに違う

| | N/Z | V/C | X |
|---|---|---|---|
| MOVE / TST | 立てる | クリア | 保存 |
| CLR | Z=1, N=0 | クリア | 保存 |
| **MOVEA / LEA** | **触らない** | **触らない** | **触らない** |

MOVEA は「MOVE と同じだろう」と `emitLogicFlags` を足すと壊れる。
`emitStoreCcr` を呼ばないことがそのまま「フラグ不変」の実装になっている。

### テストが本物のバグを 1 つ捕まえた

同値テスト (発行したコードをミニ Xtensa 解釈器で実行し、`M68k::step()` と
`M68kState` を丸ごと比べる) が `MOVE #imm,Dn` で落ちた。値が 0x8000 ずれ、
N フラグが Z になっていた。

**拡張ワードから即値を畳む処理を書いていなかった。** `planOne` は命令語
だけから決まる欄を埋めるので、拡張ワードの値は `plan()` 側で畳む必要が
あった。あわせて拡張ワードを **2 語**集めるようにした (MOVE.l #imm と
LEA (xxx).L は 6 バイトで 2 語ある。1 語しか持たないと上位が落ちる)。

### エミッタ未対応の種別は明示的に拒否する

planner を先に広げたので、エミッタが知らない種別が計画に積まれる期間が
できた。`emitAll` の switch に `default:` が無く、9 個の種別を足したことで
`-Wswitch` が 2 件出た。

**危ないのは警告ではなく「何も発行しないまま成功したことにする」形**で、
そうなるとその命令が実行されずに飛ばされ、ゲストの状態が静かにずれる。
全種別を列挙して `failed` を立てるようにした。

### 予測との照合

| | 予測 | 実測 | 判定 |
|---|---|---:|---|
| ブロックあたり命令数 | 1.35-1.75 | 1.20 | 下振れ |
| 翻訳失敗 | 2.0M-3.2M | 4.57M | **外れ** |
| ブロック実行比率 | 30-45% | 23% | **外れ** |
| クロック | 5600-6300 | 5520 | ぎりぎり |

**「Tier A 単独では JIT OFF (8150) を超えない」という言明は当たった。**
ブロックは依然として最初のメモリアクセスで切れる。段 0 の実測では
書込 26.5% + 呼出復帰 30.3% が切る理由なので、そこを解かない限り伸びない。

次は Tier B (読みガード) が要る。**実行時ガードの設計が本体**で、
§5.3 の契約を「例外条件をガードが先取りし、不成立なら状態を 1 ビットも
変えずに脱出する」形へ改訂することになる。

## ROM のコードが 1 ブロックも翻訳されていなかった (2026-08-19)

Tier B の設計調査で見つかった。**実行の 23% を丸ごと捨てていた。**

### 何が起きていたか

世代配列はメインメモリぶん (2MB / 1KB = 2048 ページ) しか無い。
`generation()` は範囲外に `kAlwaysStale` を返す。$FE0000 の IPL-ROM は
範囲外なので、翻訳器の I9 が「常に古い」と見て**翻訳自体を拒否**していた。

しかも ROM 番地は「飽和したページは覚えない」規則で負のキャッシュにも
入らないので、**毎回翻訳し直して毎回失敗**していた。

### 直し方

ROM は書き換わらないので、世代は固定値でよい。`setImmutableRange` を足し、
`setFastRom` と同じ場所 (`bus.cpp` の `publishFastRam`) で教える。
**窓と同じ場所なら、片方だけ更新して食い違うことがない。**

固定値は `kImmutable` (0xFFFE)。「まだ書かれていない RAM ページ (0)」と
統計上区別が付く方を選んだ。

### 効果

| | 前 | 後 |
|---|---:|---:|
| 実効クロック | 5520 | **6494 kHz** |
| ブロック | 3,339,560 | 4,626,454 本 |
| **翻訳失敗** | 4,573,780 | **1,944** |
| 実行可能メモリ | 2,572 | **16,352 / 16,384** |

**翻訳失敗が -99.96%。** これまで「初めて見る番地が数千種ある」と
読んでいたものの大半は、**同じ ROM 番地を何度も試して失敗し続けていた**
だけだった。

### 実行可能メモリを増やしても効かない (実測)

使い切ったので 16KB → 20KB にして測った:

| | 16KB | 20KB |
|---|---:|---:|
| クロック | 6494 | 6493 kHz |
| ブロック | 4,626,454 | 4,631,082 本 |
| タグ外れ | 1,136,740 | 1,137,771 |

**変化なし。** どちらも使い切るが、ブロック数もタグ外れも同じ =
`codeFull_` が立った後も既に翻訳済みのブロックで十分回っている。
**容量は律速ではない。** 16KB へ戻した (内部 SRAM を 4KB 節約)。

### 教訓

**「翻訳失敗が多い」の内訳を最後まで詰めていなかった。**
負のキャッシュを別表にしても 440 万件残ったとき、「初めて見る番地が
数千種」と結論したが、実際は**同じ番地の繰り返し**だった。
飽和ページを覚えない規則が、ROM 番地に対して裏目に出ていた。

「なぜ覚えられないのか」を 1 段掘れば、Tier A より先に見つかっていた。

## Tier B (読みガード) と、世代の飽和 (2026-08-19)

| | クロック | ブロック長 |
|---|---:|---:|
| ROM 対応まで | 6493 | 1.17 |
| Tier B (素) | 6316 | 1.50 |
| **+ 飽和対策** | **7134** | **1.50** |

### Tier B 単体では遅くなった

ブロック長は 1.17 → 1.50 と設計の予測どおり伸びたのに、クロックは
6493 → 6316 と**下がった**。翻訳失敗が 1,944 → 220 万に激増していた。

### 犯人は世代の飽和だった

失敗地点を 6 つに分けて数えたら、**99.6% が I9 (世代が kAlwaysStale)**。
さらに番地を 1MB 刻みで数えたら**全部 $000000 台 (メインメモリ)**。

つまり「範囲外」ではなく **飽和**。世代は 16bit で、1KB ページに 65,536 回
書くと `kAlwaysStale` で止まる。スタックやワーク領域なら数秒で届く。
**飽和したページ上のコードは永久に翻訳を拒否される。**

Tier B の前は 1,944 件だったのに激増したのは、Tier B が悪いのではなく
**翻訳を試みる番地が増えた**から。読み形が積めるので、以前は諦めていた
番地でも `plan()` を呼び、そこが飽和ページだと落ちる。

### 直し方: 飽和が溜まったら世代を捨て直す

`resetGenerations()` は最初からあったが、**誰も呼んでいなかった**。
「キャッシュを全部捨てた後にしか呼んではいけない」ので、runner の
`reset()` と同時に呼ぶ。閾値 64 回にしたのは、1 回の飽和で全部捨てると
正常なブロックまで再翻訳になるため。

実測で 6316 → **7134 kHz**、翻訳失敗 220 万 → **474**。世代を捨て直したのは
起動から 25 秒で 1 回だけ。

### 教訓: 統計は「1 つのカウンタ」では足りない

`translateFail` が 1 つしか無かったので、6 つの失敗地点のどれで落ちて
いるか分からなかった。**分けて数えたら 5 分で分かった**。

同じ轍を 2 度踏んでいる (以前も「翻訳失敗が多い」の内訳を詰めずに
「初めて見る番地が数千種」と誤読した)。**失敗のカウンタは、原因の
分類と同じ粒度で持つ。**

### 制約の強制: a12 以降を触ったら落ちる

攻撃が「`kTmpE = 12` に変えても全テストが通る」を見つけた。ミニ解釈器は
16 本すべて持つので、ホストでは a12 が普通のスクラッチに見える。実機では
**祖先フレームを壊し**、窓のオーバーフローで初めて症状が出る。

解釈器が a12-a15 に触ったら落ちるようにした。**既存の全テストが
そのまま制約の検査**になる。変異で確認済み。

## Tier C (書きガード) は効かなかった (2026-08-19)

| | クロック | ブロック長 |
|---|---:|---:|
| Tier B まで | 7134 | 1.50 |
| **Tier C** | **7059** | **1.50** |

**ブロック長が 1 ミリも動かず、クロックは 1% 下がった。**

### 実装は正しい

書き形 (MOVE Dn,<mem> / CLR <mem>) は planner にもエミッタにも入り、
`s8i` はアセンブラの出力とバイト単位で一致、テストも全部通る。
**動くが効かない。**

### 容量ではない

実行可能メモリを使い切っていた (16,316 / 16,384) ので 20KB にしたが、
7059 → 7058 kHz で**変化なし**。20KB も使い切る。
ROM 対応のときと同じ結論で、容量は律速ではない。

### 終端理由を測ったら、そもそも翻訳が走っていなかった

終端理由のカウンタを入れたら、4,799,568 ブロック実行に対して
**終端は 158 回**しかなかった。カウンタは `translate()` の中にあるので、
**キャッシュが温まった後はほとんど翻訳が起きていない**。

つまりブロック長は**起動直後に翻訳されたブロックで決まっており**、
そこに書き形がほとんど含まれていない。段 0 の「切断理由の 26.5% が書込」は
**インタプリタの実行分布**であって、**JIT が翻訳する範囲の分布ではない**。

### 何を学んだか

**「切断理由の割合」から「Tier の効果」を予測してはいけない。**
段 0 の分布は全命令に対するもので、JIT がブロックにできる範囲は
そこよりずっと狭い。狭い範囲の中での切断理由を測っていなかった。

Tier A が +3.6%、Tier B が +10% (飽和対策込み)、Tier C が -1% という
実測は、この読み違いの帰結として一貫している。ROM 対応が +18% と
突出したのは、切断ではなく**翻訳そのものが拒否されていた**問題だったから。

### 残す判断

Tier C は**入れたまま残す**。理由:

- 正しさは検証済み (テスト全通過、実機で Human68k が動く)
- クロックの -1% は誤差の範囲を少し超える程度で、害が小さい
- Tier D (RTS/JSR) が入ると書き形が要る (JSR はスタックへ書く)
- 消すと再実装のコストが高い

**ただし「効く」と主張してはいけない。** 効いていないことを記録する。

## 次の的を「JIT の視野の中で」測り直した (2026-08-20)

Tier C が効かなかったのは、**段 0 の分布 (インタプリタの実行分布) から
Tier の効果を予測した**から。JIT が翻訳できる範囲はそれよりずっと狭い。
今度は JIT 側の統計で測った。

### 命令の 59% はインタプリタが実行している

| | 命令数 | 割合 |
|---|---:|---:|
| ネイティブ | 7,916,262 | 41% |
| **インタプリタへ落とした** | **9,116,947** | **59%** |

**被覆率が 41% しかない。** これが速度の主因で、ブロック長でも
固定費でもない。

### direct chaining は思ったほど効かない

分岐で終端したブロックは実行の **60%** で、これは direct chaining の的。
しかし全体への寄与は薄まる:

```
16.4 サイクル (ブロックの固定費) × 60% (分岐終端) × 41% (ネイティブの割合)
= 4.0 ホストサイクル / 命令
```

1 命令 346 ホストサイクルに対して **約 1%**。**被覆率を上げる方が効く。**

### 落とした命令の内訳 (JIT 側の実測)

| グループ | 割合 |
|---|---:|
| **$4 (misc)** | **41%** |
| $6 (分岐) | 13% |
| $2 (MOVE.l) | 12% |
| $D (ADD) | 8% |
| $0 (即値/ビット) | 7% |
| $B (CMP/EOR) | 6% |

**$4 が突出。** 段 0 の $4 の内訳と照らすと、TST / CLR / LEA は Tier A で
対応済みなので、落ちているのは **RTS 8.4% + MOVEM 6.1% + JSR 2.4%**。

### 結論: Tier D は的として正しい

ただし理由が違う。「切断理由の 30.3%」ではなく「**落とした命令の 41% が
$4 で、その大半が RTS/MOVEM/JSR**」だから。

**MOVEM が RTS に次いで大きい**のは想定外だった。設計は MOVEM を
「多重アクセスの途中で窓を割る場合の部分実行状態が複雑」として除外して
いるが、被覆率の観点では無視できない。

### 教訓

**「何が的か」は、その手段が働く範囲の中で測る。**
段 0 の分布は全命令に対するもので、JIT の視野とは違った。
Tier C はその読み違いで 1 段まるごと空振りした。

## 段 0-D の実機計測 — 「動いているが効いていない」

CoreS3 実機、Human68k 起動後に JIT を入れて 45 秒。

```
[jit] ブロック 11106642 本 / 命令 16942090
[jit] 分岐で終端 5459916 (実行の 49%)
[jit] 世代を捨て直した 1 回
[jit] 負のキャッシュで省いた再翻訳 263 回
[jit] 落とした: 割込 4093 / 未対応 14815821 / 翻訳失敗 218
[jit] 鍵外れ: タグ 873939 / 写像 0 / 世代 262130 / 飽和 1514835
[jit] ガード脱出 0 (0 進捗 0 / 自ページ 0)
実効 7270-7282 kHz
```

| 段階 | 実効速度 |
|---|---:|
| インタプリタ単体 | 5386 kHz |
| JIT (段 0-C まで) | 7260 kHz |
| **JIT (段 0-D 込み)** | **7278 kHz** |

**段 0-D はほぼ横ばい。** ただし `ガード脱出 0` なので、RTS/JSR のガードは
一度も落ちていない = 実装は正しく動いている。効かなかったのは別の理由。

### 1 ブロックあたり 1.525 命令

16,942,090 / 11,106,642 = **1.525**。段 0-C の 1.32 から伸びてはいるが、
**ブロックを呼ぶ手間 (窓の照合と call0 の往復) を 1.5 命令で割っている**
状態に変わりはない。JIT が担った命令は 16.9M / 31.8M = **53.3%**。

### 鍵外れがブロック実行の 23.9% を占める

| 理由 | 回数 | 実行に対する割合 |
|---|---:|---:|
| **飽和** | 1,514,835 | **13.6%** |
| タグ | 873,939 | 7.9% |
| 世代 | 262,130 | 2.4% |
| 写像 | 0 | 0% |

**飽和が最大**で、しかも「世代を捨て直した」が **45 秒で 1 回**しかない。
閾値 `kSaturationResetThreshold = 64` に対して飽和は 151 万回起きている
のだから、本来なら何度も走っているはずである。

### 「飽和」の 151 万件は、飽和ではなくスロット衝突だった

最初はこう推論した — 「負のキャッシュが飽和ページを永久凍結している」。
**これは誤りだった。** `rememberFailure` は `kAlwaysStale` を明示的に
弾いている (block_runner.cpp:40-49) ので、飽和ページは負のキャッシュに
載らない。`selfPageExit` も 0 なので `kAnyGen` の経路も通っていない。

実際の原因は鍵照合の 1 行目にある (block_runner.cpp:294)。

```cpp
const std::uint16_t nowGen = map.generation(slot->page << CodeGenMap::kPageShift);
```

**世代を `entryPc` のページからではなく `slot->page` から引いている。**
`slot->page` は「そのスロットに以前入っていたブロック」のページ番号で、
空きスロットなら **0** である。

ページ 0 は $000000-$0003FF = **例外ベクタ表と Human68k のワーク領域**。
起動後わずかで 65,536 回書かれて飽和する。飽和すると、
**どのスロットのどの取りこぼしでも** `nowGen == kAlwaysStale` になる。

`if-else` の順序 (block_runner.cpp:309-322) は `kAlwaysStale` を先に見るので、
**本来 `keyMissTag` に入るべきスロット衝突が、まとめて `keyMissStale` に
化けていた**。

### 正しい読み方

| 見かけの理由 | 回数 | 実体 |
|---|---:|---|
| 飽和 1,514,835 | | **スロット衝突** |
| タグ 873,939 | | スロット衝突 |
| **合計** | **2,388,774** | **実行の 21.5%** |

**正しさは壊れていない。** `slot->entryPc != entryPc` が必ず外すので、
別番地のコードを実行することは原理的にない。壊れているのは統計の帰属だけ。

しかし **21.5% がスロット衝突**という事実は、飽和とはまったく違う対策を
指している。`kJitSlots = 512` に対し、実測のブロックは 1110 万本を
異なる番地で回している。**表が小さすぎる。**

### 教訓 (統計の粒度、3 度目)

`translateFail` を 1 本のカウンタにしていたせいで原因を 2 度見失った、と
前に書いた。今回は逆で、**分けたのに分け方が間違っていた**。

`if-else` で理由を数えるとき、**判定の順序がそのまま帰属の優先順位になる**。
`kAlwaysStale` を先に見る順序には正しさ上の根拠があった (§5.5) が、
統計としては「衝突」を「飽和」で上書きしていた。

**正しさのための順序と、説明のための順序は別物。**

## 真犯人は「翻訳器が満杯で死んでいた」ことだった

スロット衝突を追っていたら、その手前にもっと大きな穴があった。
**収支を閉じただけで見つかった。**

```
deferUnsupported = 14,815,821   (「未対応命令で降りた」)
  negativeHit    =        263
  translateFail  =        218
  → 無勘定       = 14,815,340   (99.997%)
```

`translate()` が nullptr を返す経路のうち、カウンタが付いていないのは
`codeFull_` の早期 return **1 箇所だけ**。つまり「未対応命令」に見えて
いたものの 99.997% は、**コード領域が満杯で翻訳を試みもしなかった**回数
だった。

### 回復経路がデッドロックしていた

- `codeFull_ = true` にするのは実行可能メモリを使い切ったとき
- `false` に戻すのは `reset()` だけ
- `reset()` を呼ぶのは飽和閾値の分岐だけ
- **その分岐は `codeFull_` の早期 return より後ろにある**

`kJitCodeBytes = 16KB` は起動直後に埋まるので、計測した 45 秒のほぼ
全期間で翻訳器は停止していた。「JIT が 7278 kHz」という数字は、
**JIT がほとんど動いていない状態の数字**だった。

### 確保順という別の欠陥も出てきた

直したビルドを焼いたら `JIT: 置き場が無いので有効にできません` が出た。
調べると **HEAD 素でも同じ**で、私の変更とは無関係だった。

`ExecMemory::acquire` は `MALLOC_CAP_EXEC` を要求する。これは**実行できる
IRAM** からしか取れない。ところが確保順が

1. スロット 20KB (`MALLOC_CAP_INTERNAL`)
2. 負のキャッシュ 16KB (`MALLOC_CAP_INTERNAL`)
3. 実行可能メモリ 16KB (`MALLOC_CAP_EXEC`) ← ここで失敗

だった。`MALLOC_CAP_INTERNAL` は DRAM でも IRAM でも満たせるので、
**先に取ると実行可能な側を食う**。しかも失敗しても JIT を諦めるだけ
なので警告 1 行で済み、さらに IPL-ROM まで内部 SRAM から溢れて PSRAM
へ落ちていた (インタプリタ単体より遅い状態で起動していた)。

**希少な順に取る**のが確保順の原則。実行可能メモリを最初に取るよう直す。

### 索引を直したつもりが直っていなかった

スロット索引を `negative_cache.h` と同じ `((pc >> 1) ^ (pc >> 11))` に
したが、これでは**直そうとした当の周期が残る**。

512 スロット (マスク `0x1FF` = ビット 0-8) では、`pc` のビット 10 は
`(pc >> 1)` でビット 9 へ行って**マスクの外へ落ち**、`(pc >> 11)` にも
乗らない。つまり索引から完全に消える。結果、ちょうど 1KB 離れた 2 番地は
**必ず衝突したまま**だった。

| 索引式 | 1KB 周期 16 番地 | 2KB 周期 16 番地 |
|---|---:|---:|
| `(pc >> 1)` | 1 スロット | 1 スロット |
| `^ (pc >> 11)` | **8 スロット** | 16 スロット |
| `^ (pc >> 10)` | **16 スロット** | 16 スロット |

`>> 10` ならビット 10 が索引のビット 0 に入って完全に散る。

**「散らした」と「散った」は別**。式を移植しただけでは、マスク幅が違えば
効かない。テストが「16 個が 8 個に散る」を「半数以上」で通していたのも
同じ穴で、全数を要求する形に直した。

### 教訓: 収支を閉じる

保守的なフォールバックの盲点 (「諦めすぎても正しさは壊れないので、
正しさのテストでは永遠に見えない」) への一般解が 2 つ見つかった。

1. **勘定を閉じる。** 「諦めた回数」と「理由別カウンタの合計」が一致する
   ことは、正しさとは独立に検査できる。無勘定の早期 return を足した瞬間に
   破れる。今回の欠陥はこれ 1 本で 45 秒ログの時点で機械的に暴けた
2. **生存性を What にする。** 「いつか回復する」は safety テストの語彙に
   存在しない。「満杯後も有限回以内に翻訳される」を明示的に問う

既存 694 テストが 1 件も検出できなかったのは、3 層の盲点が重なったため:
全失敗経路がインタプリタに落ちる (正しさは無傷) / 飽和には 65,536 回の
書き込み、凍結には 16KB 分の翻訳が要る (単体テストの規模を超える) /
カウンタが 1 件も assert されていなかった (テスト対象ですらなかった)。

### 段 0-E M1 (MOVEM の planner) のゲート測定

同一条件の A/B (ホスト 400M サイクル、実行命令 39,329,755 で一致):

| | ベースライン | M1 |
|---|---:|---:|
| ブロック内で実行される命令の割合 | 32.60% | **38.65%** |
| MOVEM の拒否率 | 15.902% | **0.036%** |
| 平均区間長 | 1.319 命令 | 1.366 命令 |

合格ラインは +4pt 以上と 0.5% 以下で、両方超えた (予測 38.66% と 0.01pt 差)。
MOVEM 2,381,725 件のうち 99.81% が積まれ、落ちたのは 5 本以上の 4,577 件だけ。

**ただしこれは planner の受理率であって、実機で JIT が回せる量ではない。**
上の満杯デッドロックが直るまで、実機の被覆率はこの数字とは別に測る必要がある。

## arena は増やせない。効いたのは「捨てる回数」だった

満杯デッドロックを直したら、**かえって遅くなった** (7278 → 5900 kHz)。
理由を測って詰めた記録。

### まず、増やせないことが分かった

`exec_memory.h` の冒頭に既に書いてあった。

> ESP32-S3 で `MALLOC_CAP_EXEC` が取れるのは IRAM の余りだけで、実測で 21KB
> しか無い。そもそも PSRAM は実行可能属性を持たない。

**これを読まずに 32KB と 96KB を焼いて測った。** どちらも
`exec memory 98304 bytes unavailable; JIT disabled` で JIT ごと無効になり、
インタプリタ単体の数字 (5300 / 5388 kHz) を「arena を増やしたら遅くなった」
と読みかけた。**確保に失敗しても警告 1 行で動き続ける設計**なので、
ログを見ないと気づけない。

実際に確保できる範囲で測ると:

| arena | 実効速度 | 満杯で諦めた | 満杯で捨てた |
|---|---:|---:|---:|
| 16KB | 5900 kHz | 15,991,974 | 1,952 |
| 20KB (上限) | 5745 kHz | 15,232,986 | 1,859 |

**25% 増やしても満杯は 4.7% しか減らない。** 容量では届かない。

### 効いたのは閾値だった

`kCapacityResetThreshold` = 「満杯のまま何回諦めたら全部捨てるか」を振る。

| 閾値 | 実効速度 | 捨てた回数 |
|---|---:|---:|
| 8,192 | 5900 kHz | 1,952 |
| 100,000 | **6890 kHz** | 192 |
| 1,000,000 | **6982 kHz** | 19 |

**捨てる回数がそのまま速度に効く。** つまり費用は「諦めている間の
取りこぼし」ではなく、**ホットセットを失うこと**だった。

実行は極端に集中していて (ホスト実測で上位 50 ブロックが動的実行の 96.6%、
上位 100 で 99.7%)、16KB に入る 100-160 本はほぼそのホットセットである。
8,192 回ごとに全部捨てると、6,075 ブロック実行ごとにホットセットを
全滅させて焼き直していたことになる。

### デッドロック版が速かった理由

`codeFull_` の凍結は、偶然にも **「起動時に翻訳して以後は一切捨てない」**
という縮退した正解を実装していた。翻訳コストがゼロで、ホットセットが安定
していたので 7278 kHz が出ていた。**壊れていたのは生存性だけ**で、
速度の観点では今より良かった。

採用値は **100,000**。1,000,000 との差は 1.3% しかない一方、回復までの
猶予が 10 倍違う。ほぼ全部の速度を取りながら生存性を残せる点を選ぶ。

### IPL-ROM の置き場は Human68k 稼働中の速度に効かない

内部 SRAM が足りず IPL-ROM が PSRAM へ落ちたので、切り分けて測った。

| IPL-ROM の置き場 | インタプリタ単体 |
|---|---:|
| 内部 SRAM | 5386 kHz |
| PSRAM | 5388 kHz |

**差はゼロ。** 「ブート中は毎命令フェッチ元だから内部 SRAM へ」という
元の設計判断は**起動中の分布に基づくもの**で、Human68k が動き出した後は
成り立たない (稼働中の ROM 実行は 19.3%)。128KB を明け渡してよい。

### 教訓: 定数を写したテストは、値を変えると嘘の失敗をする

生存性テストが `constexpr kThreshold = 8192;` と**実装の定数を写して**
いたので、閾値を 100,000 にした瞬間「32,768 回叩いても回復しない」と
落ちた。回復経路は正しく動いていて、**テストの前提だけが古かった**。

定数を `public` にして実値を読ませる形へ直した。索引式をテスト側に
写していて変異が素通りした件 (段 0-D) と同じ形で、**「実装を写す」
テストは実装を問うたことにならない**。

## 平均ブロックサイズを測ったら、チャーンではなく「先着順」だった

`translated` と `translatedBytes` を足して実測した。

```
[jit] 翻訳 19053 本 / 3170028 バイト (平均 166 バイト、98 本入る)
[jit] 満杯で捨てた 192
```

| 値 | 実測 |
|---|---:|
| 平均ブロックサイズ | **166 バイト** |
| 16KB に入る本数 | **98 本** |
| 21KB (EXEC 上限) でも | 129 本 |
| 1 回の充填で翻訳した本数 | 19,053 ÷ 193 = **99 本** |

### 詰め替えは起きていなかった

**充填 1 回あたり 99 本翻訳して、入るのが 98 本。** つまり 1 回の充填の
中では詰め替えが起きていない。arena は「最初に来た 98 本」で埋まり、
そこで止まる。

「同じ番地を何度も翻訳し直している」と考えていたのは**誤り**だった。
起きているのは先着順の占有で、**入っているのがホットセットである保証が
まったく無い** (起動経路のブロックが居座る)。

### 閾値を上げると速くなった理由の解釈も変わる

「捨てないほど良い 98 本を保持できる」ではなく、**捨てるたびに先着順で
埋め直すので、そのつど並びを引き直している**。捨てる回数が減るほど、
たまたま良い並びを引いた状態が長持ちする。

### 容量は足りている

ホスト実測「上位 50 ブロック = 動的実行の 96.6%」が正しいなら:

| | バイト数 | 16KB に |
|---|---:|---|
| 上位 50 本 | 8.1KB | **余裕で入る** |
| 上位 100 本 | 16.2KB | ぎりぎり入らない |

**容量ではなく「入れるものを選んでいない」ことが問題**である可能性が高い。
arena を増やせない (EXEC 上限 21KB) ことは、この読みなら制約にならない。

### 教訓: 「何回起きたか」だけでは原因が決まらない

「満杯で諦めた 1,929 万回」は、そのままでは 2 つの別の物語を許す。

1. ホットセットが入りきらず、詰め替えを繰り返している (容量不足)
2. 先着順で埋まって固定され、後から来たホットな番地が門前払い (選別の欠如)

どちらも「満杯で諦めた」に同じように現れる。**分けたのは平均ブロック
サイズという別種の量**で、これが無い間は容量を増やす方向 (誤り) に
賭けていた。

**回数の統計だけを増やしても、原因の候補は絞れない。**

### 容量 × 閾値の 2x2 を埋めた

20KB を最初に測ったのは閾値 8,192 のときで、**捨てまくっている状態の
数字だった**。閾値を上げてから測り直すと結論が変わる可能性があったので、
4 マス全部を埋めた。

| | 閾値 8,192 | 閾値 100,000 |
|---|---:|---:|
| **16KB (98 本)** | 5900 kHz | **6890 kHz** |
| **20KB (119 本)** | 5745 kHz | 6861 kHz |

**容量を 21% 増やしても差が無い。** 効くのは閾値だけ。

これで「容量は律速ではない」が 2 通りの条件で確認できた。arena が
EXEC 上限 21KB で頭打ちであることは、**制約として効かない**。

ただし注意: 20KB でも平均ブロックサイズが 171 バイトに増えている
(16KB では 166 バイト)。入る本数が増えると、より大きいブロックも
翻訳されるので平均が上がる。**「何本入るか」は固定値ではない。**

## 天井を計算する — この設計では 10000 kHz に届かない

実測 2 点から、被覆率を上げたときの速度が予測できる。

インタプリタ単体 5386 kHz、JIT ON 6890 kHz、被覆率 c = 0.517。
JIT 側の命令あたり相対コストを r とすると:

```
5386 / 6890 = c·r + (1 - c)
→ r = 0.578
```

つまり **JIT が担っている命令ですら、インタプリタの 1.73 倍速でしかない**
(ブロックの固定費込み)。ここから `speed(c) = 5386 / (1 - 0.422c)`。

| 被覆率 c | 予測速度 |
|---|---:|
| 0.517 (現状) | 6890 kHz |
| 0.70 | 7644 kHz |
| 0.85 | 8399 kHz |
| 0.966 | 9093 kHz |
| **1.00 (完全)** | **9319 kHz** |

**被覆率を 100% にしても 9319 kHz。** 10000 kHz には届かない。

届かせるには c ≥ 0.95 に**加えて** r を 0.578 → 0.539 (−7%) する必要が
ある。r 側の材料は direct chaining (命令あたり約 5 サイクル) とブロック長
(1.5 → 2.0 で約 4 サイクル) で、合計すればぎりぎり足りる勘定だが、
**両輪であって片輪では届かない**。

### この計算が変える優先順位

「1 ブロック 1.503 命令の壁」は律速ではない。ブロック固定費は
16.4 サイクル ÷ 1.5 命令 ≈ 11 ホストサイクル/命令で、**全体 346 の約 3%**。
一方、被覆の穴 (48%) は数十 % を握っている。

**c < 0.85 のうちはブロック長に触る価値がない。** direct chaining も
同様で、今の数字では 240MHz の 0.7% にしかならない (以前の評価 ~1% と
同水準)。ただし c ≥ 0.85 に達したら、r を削る数少ない材料として復活する。

### モデルの粗さ

c は命令数ベースで、落ちている命令 (RTS/MOVEM) はゲストサイクルが重い
ので、サイクルベースでは ±10-15% ずれる。それでも「10000 に届かない」
という結論は変わらない。

## admission ゲートは作らない — 「満杯 99.8%」は満杯の話ではなかった

arena に「入れるものを選んでいない」ことが問題だと考え、admission ゲート
(N 回ミスしてから翻訳する) の設計まで進めた。**着手直前にホスト計測で
上限を測って、やめた。**

### 測ったこと (P0)

entryPc ごとの実行回数と `requiredSize` を集め、**実行回数の多い順に詰めて
容量に収めたときの被覆率**を計算する。これが「最適に選抜したときの上限」。

| 容量 | 本数 | 被覆率 |
|---|---:|---:|
| **16KB** | 110-112 | **54.58%** |
| 20KB | 136-137 | 54.68% |
| 32KB | 204-205 | 54.83% |
| 256KB | 1,742 | 55.06% |
| **無限 (440KB, 全 2,872 本)** | 2,872 | **55.07%** |

**16KB と無限容量の差は 0.49 ポイントしかない。**

実機の実測は 51.7% (先着順) なので、**完璧な admission で取り返せるのは
2.9 ポイント = 速度にして +0.7%** (6970 → 7017 kHz)。スロット表 4 倍
(80KiB) と admission 表 (8KiB) を足す工事の見返りとしては合わない。

### なぜ「満杯 99.8%」に騙されかけたか

統計はこう出ていた。

```
[jit] 落とした: 割込 5233 / 未対応 19640861 / 翻訳失敗 2608
[jit] 満杯で諦めた 19596815
```

「未対応で降りた」の **99.8% が満杯由来**。ここから
「満杯を解消すれば 99.8% が翻訳される」と読みかけた。

**読み違いだった。** `codeFull_` の検査は `translate()` の**先頭**にある
(負のキャッシュ照合よりも、`plan()` よりも前)。だから arena が満杯なら、
**翻訳できない命令も『満杯で諦めた』として数えられる**。

> 満杯だから諦めた ≠ 満杯でなければ翻訳できた

早期 return の位置が、そのままカウンタの意味を決めていた。

### 本当の律速

異なり入口 6,251 本のうち、**planner が翻訳できるのは 2,872 本 (54.1%)**。
命令ベースの天井が 55%。arena も選抜も、この 55% の中で 0.5 ポイントを
争っていただけだった。

ホットセットは移動もしていない。定常状態のスライスでは翻訳可な異なり
入口が **112 本しかなく、その全部が 16KB に収まる**。上位 100 本
(14,809 バイト) で入口の 99.0% を取る。**16KB は曲線の膝のほぼ真上**。

### 教訓: 早期 return の位置がカウンタの意味を決める

「収支を閉じる」ことで満杯デッドロックを見つけたのは正しかった。だが
**収支が閉じていても、各項の意味が期待どおりとは限らない**。

`fullDeferred` は「満杯だった回数」であって「満杯でなければ翻訳できた
回数」ではない。前者から後者を導くには、**満杯でない状態で測り直す**
しかない。P0 がやったのはそれで、答えは「99.8% ではなく 3%」だった。

段 0-C の教訓 (「何が的かは、その手段が働く範囲の中で測る」) の別の形。
今回は範囲ではなく**カウンタの定義**が的を歪めていた。

## 訂正: 天井は 55.07% ではなく 61.07% だった

P0 のハーネスに欠陥があった。**飽和ページの回復を再現していなかった。**

実機の `block_runner.cpp` は、飽和ページを 64 回見たら
`reset() + resetGenerations()` で世代を 0 に戻す。P0 の影の実行器は
runner を通らないので、この回復が起きない。結果、**飽和ページが永久に
翻訳拒否として積み上がり**、落とした命令の 25.7% (3,934,937 件) を
占めていた。

実機と同じ回復を入れると、現状の天井は **61.07%**。

### admission を作らない判断は変わらない

容量の効果 (16KB と無限容量の差 0.49 ポイント) は飽和とは独立に測れて
いるので、そこは有効。実機 51.8% が先着順で天井に届いていないのも
変わらない。**「容量ではなく翻訳できる範囲が律速」という結論も同じ。**

変わるのは的の大きさで、余地は 3.3 ポイントではなく **9.3 ポイント**だった。

### 落とした命令の内訳 (実行回数で重み付け、飽和回復あり)

| グループ | 落とした % |
|---|---:|

## 段 0-E M2 (MOVEM のエミッタ) の実機計測 — 予測が当たった

| | 前 | 後 |
|---|---:|---:|
| 実効速度 | 6970 kHz | **7495 kHz** (+7.5%) |
| 被覆率 | 51.75% | **56.43%** (+4.68 pt) |
| 1 ブロックの命令数 | 1.503 | 1.562 |
| 平均ブロックサイズ | 164 バイト | 191 バイト |
| arena に入る本数 | 99 本 | 85 本 |

**予測 7460 kHz に対し実測 7495 kHz。** 速度モデル
`speed(c) = 5386 / (1 - 0.422c)` は 0.5% 以内で当たった。以後の判断は
このモデルで見積もってよい。

### staging が黙って翻訳を落としていた

書き形 MOVEM ×4 は実測 **1985 バイト**で、`kStagingBytes = 1536` に
収まらなかった。収まらないと `emitBlock` が false を返すだけなので、
**正しさは無傷のまま、この段が狙う形そのものを落とす**。

エミッタを書いても被覆率が伸びない形で失敗するので、
「MOVEM は効かなかった」と誤って結論しかねなかった。

定数を 2 か所に置くと片方だけ広げたときに被覆が静かに減るので、
`kMaxBlockBytes` をエミッタ側に 1 つだけ置いて runner が参照する形にした。

### 実装で踏んだこと: 書き形のビット順

設計は「i 昇順、bit i ↔ A7..D0」としていたが、**アドレスを昇順に歩く
実装ではこれは成立しない**。インタプリタはビット昇順でアドレスを*減らす*
ので、最も低いアドレスに載るのは*最後*に転送したレジスタ。昇順アドレスへ
写すにはビットを降順に辿る必要がある。

実装中に実際に踏んで、レジスタ順が丸ごと逆になった。差分テストが捕まえた。

### commit 値の退避先

`emitTouch` が世代の +1 を組むのに `kTmpB` を潰すので、commit 値を
`kTmpB` に置くと**最後の commit が「最後に触ったページの世代」を An へ
書く**。MOVEM は sr に触らないので `kTmpSr` (a10) が空いている。

### 教訓: 「収まらなければ諦める」は被覆を静かに削る

許可リスト方式では、あらゆる失敗が「インタプリタに任せる」に落ちる。
これは正しさを守る一方で、**容量やサイズの制約が被覆率を削ったことを
見えなくする**。

`requiredSize` が上限を超えたら false を返す経路には、**何を落としたかを
数える口**が要る。今回は実装者が最悪ケースのテストを書いていたので
気づけたが、書いていなければ「効かなかった」で終わっていた。

## 段 0-F (BSR) — 被覆率は伸びたが速度が付いてこない

| | 前 (M2) | 後 (BSR) |
|---|---:|---:|
| 実効速度 | 7495 kHz | **7620 kHz** (+1.7%) |
| 被覆率 | 56.43% | **62.38%** (+5.95 pt) |
| 1 ブロックの命令数 | 1.562 | **1.534** (減った) |
| 分岐で終端 | 44% | **54%** |

**速度モデルが初めて外れた。** 予測 7311 kHz に対し実測 7620 kHz
(モデルは c だけを見るので、今回は逆に**過小**評価している)。

### 原因: BSR は必ずブロックを終端する

被覆率が +5.95 ポイント伸びたのに速度が +1.7% しか出なかったのは、
**BSR がブロックを切るから**。分岐終端が 44% → 54% に増え、1 ブロック
あたりの命令数が 1.562 → 1.534 へ**下がった**。

命令を 1 つ翻訳対象に増やすと:
- 被覆率は上がる (その命令をネイティブで実行できる)
- **終端する命令なら、ブロックが短くなる** (固定費を割る命令数が減る)

この 2 つは逆向きに効く。**BSR は被覆率を最も稼ぐが、同時に最も
ブロックを切る命令**でもあった。

### モデルの限界

`speed(c) = 5386 / (1 - 0.422c)` は「命令あたりの相対コスト r が一定」
と仮定している。r はブロック固定費 ÷ 1 ブロックの命令数を含むので、
**ブロック長が変われば r も変わる**。

段 0-E (MOVEM) はブロック長を 1.503 → 1.562 と伸ばす側だったので
モデルが当たり、段 0-F (BSR) は縮める側だったので外れた。

**以後、終端する命令 (分岐系) を足すときはモデルを額面で信じない。**
非終端の命令 (Tier A 群: CMP / MOVEA / ADDA) はブロックを伸ばす側なので、
モデルはそのまま使える。

### direct chaining の位置づけが変わる

分岐終端が 54% になったことで、direct chaining (ブロック末尾から次の
ブロックへ直接飛ぶ) の的が以前より大きくなった。以前の評価は
「分岐終端 47% で 240MHz の 0.7%」だったが、54% かつブロックが短い
現状では割に合う可能性がある。

ただし**まず非終端の命令で被覆率を上げる方が安い**。Tier A 群
(CMP.w #imm,Dn / MOVEA.l <mem>,An / ADDA.l) はどれもブロックを
伸ばす側で、実測では上位 10 個で 84.40% に届く。

## 段 0-G (Tier A 群) — 10000 kHz が射程に入った

| | 前 (BSR) | 後 (Tier A) |
|---|---:|---:|
| 実効速度 | 7620 kHz | **8844 kHz** (+16.1%) |
| 被覆率 | 62.38% | **73.16%** (+10.78 pt) |
| 1 ブロックの命令数 | 1.534 | **1.950** |
| 分岐で終端 | 54% | 58% |

**この段だけで +16%。** 段 0-F でモデルが外れた理由 (「終端する命令は
ブロックを切る」) を踏まえ、**非終端の命令だけを狙った**結果。

### 両方が効いた

- 被覆率 +10.78 ポイント
- **1 ブロックあたりの命令数 1.534 → 1.950** (段 0-A から通して最大)

段 0-F では被覆率が伸びてもブロックが縮んで打ち消し合ったが、今回は
**同じ向きに効いた**。予測が外れた方向も逆で、モデル予測 7792 kHz に対し
実測 8844 kHz と**上回った**。

### r が改善した — 天井が上がる

命令あたりの相対コスト r を逆算すると **0.578 → 0.4656**。

r はブロック固定費 ÷ ブロック長を含むので、ブロックが伸びれば r 自体が
下がる。**被覆率と r は独立ではない。**

新しい r での予測:

| 被覆率 c | 予測速度 |
|---|---:|
| 0.7316 (現在) | 8844 kHz |
| 0.80 | 9408 kHz |
| **0.8634** | **10000 kHz** |
| 0.9218 | 10615 kHz |
| 1.00 | 11568 kHz |

**「被覆率 100% でも 9319 kHz」という以前の結論は、r が固定という仮定に
依存していた。** r が下がったので天井も上がり、**被覆率 86.3% で
10000 kHz に届く**。

実測の累積寄与では、上位 20 + 長さデコーダで 92.18% なので、**射程内**。

### 教訓: 「天井」は仮定ごと動く

天井の計算 (段 f85321e) は正しい手続きだったが、**その時点の r を固定した
条件付きの天井**だった。条件が変われば天井も変わる。

「この設計では届かない」と結論するときは、**何を固定した上での結論か**を
明示する必要がある。今回は「1 ブロック 1.5 命令のまま」が隠れた前提だった。

## 訂正 2: 「admission を作らない」判断の根拠が崩れた

段 0-H で予測 85.57% に対し実機 75.84% の乖離を調べたら、**判断の土台に

### 旧ハーネスは arena を一切模していなかった

| **満杯で捨てた** | **12** | **12** |

被覆率だけ 7.5 ポイント低いのは走行長の差 (伸ばすと実機側へ寄る)。

## 段 0-I (admission ゲート) — 実装したが撤回した

ホスト計測の予測は「68.4% → 80% 台、9300-9750 kHz」だったが、**実機では
どの構成も門なしに勝てなかった**。

| 構成 | 実効速度 | 被覆率 | 見送り |
|---|---:|---:|---:|
| **門なし (現行)** | **9060 kHz** | **75.84%** | — |
| 表 1024 / N=16 | 8688 kHz | 70.01% | 652,818 |
| 表 1024 / N=4 | 8064 kHz | — | 626,689 |
| 表 4096 / N=16 | 8844 kHz | — | 17,069 |
| 表 8192 (確保失敗) | 9006 kHz | — | 0 (門なしと同じ) |

### 何が起きたか

N=16 で被覆率が **5.83 ポイント下がった**。門がホットなブロックを弾いて
いる。しかも N を 16 → 4 に下げても見送り数がほぼ変わらない
(652,818 → 626,689) ので、**門は「同じものを」見送り続けている**。

原因は Misra-Gries の減算による飢餓。異なり番地 7,359 本に対し表が
1024 エントリしかないので、**ホットな番地のカウンタがコールドな番地に
削られ続けて N に到達できない**。

表を 4 倍にすると見送りが 652,818 → 17,069 へ激減したので、飢餓という
診断は正しい。**しかし速度は 8844 kHz で、依然として門なしに負ける。**

### 見送りをゼロに近づけるほど、門なしに近づくだけ

これが結論。表を大きくして飢餓を解消すると、門は「ほぼ何も見送らない」
状態に漸近する。つまり **admission がこの負荷で生む利得は無い**。

ホスト予測が外れた理由は未特定。ホストハーネスは arena を正しく模して
いた (機構指標が実機と一致) が、**「上位 50 本を選べれば 77% を取れる」
という集中度の測定と、「Misra-Gries が実際にその 50 本を選べるか」は
別の問題**だった。前者は選抜の上限、後者は選抜機構の性能。

### 内部 SRAM の制約も効いた

8192 エントリ (64KiB) は確保に失敗し、フォールバックで門が無効化された。
**この挙動自体は設計どおりに動いた** (確保失敗で JIT ごと死なせない)。
4096 エントリ (32KiB) が実際に置ける上限。

### 教訓: 「選抜の上限」と「選抜機構の性能」は別

「上位 50 本 (11.8KB) が 16KB に入り、門前払いの 77% を占める」は正しい
測定だった。だがそれは **理想的な予知能力があれば**の話で、実際の
機構 (頻度カウンタ + 閾値) がその 50 本を選べるかは別に確かめる必要が
あった。

段 0-C の「的はその手段が働く範囲の中で測る」の変奏。今回は範囲ではなく
**手段の能力**を確かめていなかった。

## direct chaining の設計 — 「焼き込み」ではなく「ループの短絡」

### 訂正: 「BSR は直結できない」は古い

2026-08-18 の検討に「BSR は戻り番地をスタックへ積むので直結できない
(除外して数えた)」とあるが、**段 0-F で BSR を実装した現在は成り立たない**。

`emitBsr` は戻り番地の push を**ブロック本体の commit 部で完結**させ、
出口は `kBranchTakenFlag` を立てるだけ。飛び先は翻訳時定数の
`BlockSlot::branchTarget` で、**BRA と同型**。`hasStaticBranchTarget` が
`kBranch || kBsr` を返すのがその証拠。

**BSR は直結の的に入る。** 分岐終端に占める割合は段 0-F の差分
(44% → 54%) から約 17-19% で、これがまるごと的に残る。

古い前提が 2 度使われていたので、ここで訂正を記録する。

### 採る形: ランナー内ディスパッチループ

生成コードに飛び先を焼き込む教科書的な direct chaining は**採らない**。
代わりに `BlockRunner::run()` 自身をループにする。

```
run(cpu, budget):
  loop:
    鍵照合 7 項 (現行と同一) → miss なら break
    callx0 runBlock
    guard 脱出・defer → break
    次 entryPc を決める (静的なら branchTarget、素通りなら pc-4、動的なら mailbox)
    mustDeferToStep() → break
    budget を超えたら break
```

**なぜこの形か:**

1. **pull 型が無傷。** 鍵照合を毎 hop、現行と同一の 7 項で踏む。
   「消し忘れたブロックを実行する」状態が原理的に存在しないという性質を、
   チェーンにそのまま延長できる
2. **パッチ管理が存在しない。** 生成コードに何も焼かないので、
   `reset()` も eviction も「スロットが空く」だけで次の hop の照合が外す。
   **無効化コードはゼロ行**
3. **ホストで検証できる。** `callx0` の 1 行以外は全部 C++ で、
   既存のテストがそのまま効く

### 焼き込み式を棄却する理由

飛び先を生成コードへ patch すると、捨てるときに逆リンクを辿って戻す
必要がある。これは **push 型そのもの**で、`code_gen_map.h` が push 型を
棄却した論理 (「1 つ漏らしても既存テストが検出できない」「症状が原因から
遠い」) がそのまま当てはまる。

加えて IRAM は 32bit アクセスのみで、Xtensa の J 命令は 3 バイト。
patch 先が語境界をまたぐと **実行中コードへの非アトミックな書き換え**になる。

### IRAM veneer も棄却 (凍結)

鍵照合を Xtensa 手書きにすると追加で hop あたり ~10 サイクル回収できるが、
**その正しさをホストで一切テストできない**。callx0/windowed の繋ぎ目で
「実機でしか分からない」失敗を 2 度踏んでいる形に、よりによって正しさの
根幹 (鍵照合) を持ち込むことになる。追加利得は約 0.7% で、割に合わない。

### 割り込み受理の遅れ

毎 hop で `mustDeferToStep()` を見るので、**保留済み割り込みの受理遅れは
1 ブロック (176 サイクル) のまま不変**。

チェーン中はデバイスが進まないので、`Machine` が「次の期限までの残り
サイクル」を budget として渡し、超えたら break する。**期限超過の上限も
1 ブロックのまま**で、保証のクラスは変わらない。

### 段階と撤退条件

| 段 | 内容 | Go 条件 |
|---|---|---|
| **D-0** | 命中率 f を実機カウンタで測る (挙動変更ゼロ) | 予測利得 ≥ +1.0% |
| D-1 | ランナー内ループ | 実測 ≥ 予測の 1/2 かつ ≥ +0.7% |
| D-2 | branchTo を定数ストアへ | +0.3% 以上 |
| D-3 | IRAM veneer | **凍結** |

撤退条件: D ≤ 25、または f ≤ 0.3 かつ D ≤ 60。

### 段 0-I の轍を踏まないための分離

admission は「上位 50 本が門前払いの 77% を占める」という**正しい測定**に
基づいて実装したのに、**機構がその 50 本を選べず撤回**した。

今回それに対応する分離:
- **上限** = 形の上で繋がる割合 (分布から出る)
- **機構の性能** = f (実際の索引・実際の 7 項照合・実際のスロット表・
  実際の arena での命中率)

f は**機構そのものを走らせないと出ない**ので、D-0 は「チェーンの hop が
踏む判定コードと同一の判定を、飛ばずに数えるだけ」の形で実機で測る。

## 段 D-1 (ランナー内ディスパッチループ) — 実装して撤退した

実装は設計どおり動いた。**機構は当たったのに、速度が逆に落ちた。**

| | 実測 (12 標本の平均) |
|---|---:|
| 基準 (HEAD) | **9072 kHz** (sd 50) |
| D-1 | **8848 kHz** (sd 34) |
| 差 | **-2.47%** |

予測は +4.3% (9480 kHz) だったので、**符号ごと外した**。撤退条件
(実測 ≥ 9140 かつ予測の 1/2 以上) を両方割ったので revert した。

### f は正しかった。f の使い方が間違っていた

まず確かめるべきは「機構が動いたか」で、**動いていた**。

```
[jit] チェーン長 1.096 本/呼 (呼び出し 19030006)
[jit] チェーン切れ: 鍵外れ 19006926 / 半端 0 / 受理 7017 / 期限 16109
```

1.096 は f = 0.717 が予告する 3.53 とかけ離れて見えるが、**分母が違う**。
1 本でも走った呼び出しだけで数え直すと:

```
1 本以上走った呼び出し = 19030006 - 7017 (受理) - 13121683 (未対応) = 5901306
20847939 / 5901306 = 3.533
```

**3.533 = 1/(1-0.717) にぴたりと一致する。** 直結は測ったとおりに当たって
いて、当たったときは測ったとおりに伸びている。

### 効かなかった理由: 呼び出しの 69% が 1 本も走らない

```
[jit] 満杯で諦めた 13120846 / 落とした: 未対応 13121683
```

**deferUnsupported の 99.99% が「arena が満杯」。** 実行可能メモリは
16356 / 16384 バイトで、常駐できるのは 1432 本。`run()` の呼び出し
19,030,006 回のうち **13,121,683 回 (69.0%) は 1 本も走らずに戻る**。

その 69% は、**回収する往復を 1 つも持たないのにループの費用だけを払う**。

| | |
|---|---:|
| 回収した hop | 1,817,933 (blocksRun の 8.7%) |
| 回収量 (43 サイクル/hop) | 7.82e7 = ホストの **0.54%** |
| 実測の悪化 | **-2.47%** |
| 差し引きの追加費用 | 4.34e8 = **22.8 サイクル / 呼び出し** |

**回収 0.54% に対して追加費用が 3.0%。** 1 呼び出しあたり 23 サイクルは、
ループ化で入口の早期 return が減り、状態 (spent / budget / entryPc) を
持ち回る形になったぶんとして桁が合う。

### 教訓: 「ブロック実行あたり」と「呼び出しあたり」も別の基準

段 D-0 の末尾で「基準を取り違えると 3 倍ずれる」と書いて、
`節約総量 ÷ ホストサイクル総数` へ直した。**その分子がまだ間違っていた。**

```
誤: 43 × blocksRun            (全ブロック実行が 1 往復ずつ節約する)
正: 43 × (blocksRun - runCalls)  (節約するのは 2 本目以降だけ)
```

f = 0.717 は「**次のブロックがスロットに居るか**」であって、
「次のブロックを直結で呼べるか」ではない。**1 本目は必ず呼び出しから
入る**ので、どれだけ f が高くても回収は
`blocksRun - runCalls` を超えられない。

arena が満杯で 69% の呼び出しが空振りしている今の状態では、この差が
8 倍つく。**D-0 の f はその 69% を分母に入れていなかった**
(f = 命中 / blocksRun で、blocksRun は走ったものしか数えない)。

正しい予測式は f ではなく **「1 呼び出しあたりの平均チェーン長 - 1」**:

```
回収 = 43 × runCalls × (平均チェーン長 - 1) ÷ ホストサイクル総数
     = 43 × 19030006 × 0.0955 ÷ 1.44e10 = 0.54%
```

**実装前にこの式で引けていれば、+4.3% ではなく +0.54% が出ていた。**
0.54% は Go 条件 (+0.7%) を最初から下回るので、着手しない判断になった。

### 直結そのものは棄却しない (条件付きで凍結)

律速は直結の機構ではなく **arena の容量**である。

- 満杯で諦めた 1,312 万回が消えれば、その 69% がまるごと「1 本以上走る
  呼び出し」に変わる。平均チェーン長は 1.096 から 3.53 へ動き、
  回収は 0.54% → **約 4.3%** (当初の予測どおり) になる
- つまり **D-1 は容量の問題が解けた後にだけ意味を持つ**

段 0-I (admission) を撤回したときの結論「的は小さくて濃い」と、
訂正 2 の「容量の効果は 19.68 ポイント」がここで繋がる。
**次に触るべきは arena の容量か eviction であって、直結ではない。**

### 実装は捨てるが、テストの形は残す価値がある

撤退で revert したが、実装中に確かめたことは記録に残す。

- **12 個の変異を全部落とした** (毎 hop の鍵照合 / 世代 / defer / budget /
  ガード脱出 / チェーン内翻訳 / 飛び先の採り方 / サイクルの積み方)
- そのうち **11 個は実行後の状態を 1 ビットも変えない**。チェーンが
  守っているものは「割り込みが遅れる」「期限を跨ぐ」「古いコードを走らせる」
  としか壊れず、**状態を比べるテストでは全部素通りする**
- 特に **「先行ブロックが次のブロックのページを書く」** は、pull 型が
  チェーンの内側で破れる唯一の形で、世代を hop の外へ持ち上げた瞬間に
  古いコードが走る。**変異を入れると実際に落ちた**

ホストで検査するために `runBlock` をホストのビルドだけ差し替える口を
作った (実機のビルドには存在しない)。**チェーンの 2 本目以降は
runBlock が戻ってからでないと踏めない**ので、これが無いと 1 行も
テストできない。再挑戦するときはこの形から始める。

### 教訓: 「機構が当たること」と「当たりが利得になること」も別

段 0-I で「**選抜の上限**」と「**選抜機構の性能**」を分けた。
今回はもう 1 段ある。

```
機構の性能 (f = 0.717)        ← D-0 で測った。正しかった
機構が出番を得る割合 (31%)     ← 測っていなかった
```

**f は「出番が来たときの打率」で、出番そのものの数ではない。**
打率が 7 割でも、7 割の打席が回ってこなければ得点は増えない。

D-0 は「チェーンの hop が踏む判定と同一の判定を、飛ばずに数える」形に
こだわって機構の性能を正確に測ったのに、**その機構が呼ばれない 69% を
数える欄がどこにも無かった**。runCalls を D-0 の時点で数えていれば、
実装前に気づけた。

という前提が D = 218.3 の実測で崩れたので、掃引して測り直した。

### 膝は 6。理由は「命令/ブロックが 6 で飽和するから」

つまり 6 より上は **得が飽和したまま損だけが伸びる**。

### 予測は方向は当たり、量を 2 倍以上外した

| | 予測 | 実測 |
|---|---:|---:|
| 膝の位置 | k=8 | **k=6** |
| 最良の速度 | 9600 kHz (+5.8%) | **9317 kHz (+2.7%)** |
| 命令/ブロック (最良) | 2.39 | **2.16** |

**外した原因は n の伸びの見積り。** 「1 命令進むごとに確率 p で切れる」
という幾何分布を仮定して p ≈ 0.40 を解き、k=8 で n = 2.39 と引いたが、
実測は 2.16 で頭打ちだった。

幾何分布は「切れる確率が命令ごとに独立で一定」を仮定している。
**実際は違う。** ブロックの先頭から数命令のうちに分岐や未対応命令が
来る確率が高く、そこを生き延びた区間はもともと長い直線区間なので、
**5 命令目・6 命令目まで来た時点で残りが尽きている**。
p が一定ではなく、後ろほど「もう切れる材料が残っていない」。

結果として飽和は予測 (k=8 で上限の 96%) よりずっと速く、**k=6 で
ほぼ完全に飽和**していた。

### 逆風 (常駐本数の減少) は予測どおり小さかった

事前に「バイト効率はほぼ変わらないはず」と書いた。実測でも:

| kMaxOps | バイト/命令 |
|---:|---:|
| 4 | 116 |
| 6 | 112 |
| 8 | 113 |

**1 本が長くなるぶん 1 本が覆う命令数も増える**ので、16KB で覆える
命令数は第一近似で不変。むしろ出口の固定部を割る命令数が増えるぶん
わずかに改善する。常駐本数 71 → 67 は「入る本数」が減っただけで、
「入る命令数」は減っていない。

**段 D-1 で恐れた「arena の逆風」は、この軸では効かなかった。**
D-1 の律速 (満杯で 69% が空振り) は kMaxOps では動かない別の問題である。

### 途中で見つけた 2 つの「黙って諦める」罠

どちらも**正しさを 1 mm も損なわないので、正しさのテストでは永遠に
落ちない**種類の欠陥。段 0-E の staging と同じ形。

#### 1. kMaxPendingGuards が kMaxOps から取り残されていた

```
constexpr size_t kMaxPendingGuards = 16;   // = 4 * 3 + 4 と書いてあった
```

コメントには「上限は 4 x 3 + 4 = 16」と**式が書いてあった**のに、
値は数値で固定されていた。kMaxOps を 5 にした瞬間に書き形 CLR が
溢れて `requiredSize` が 0 を返し、その形が丸ごと翻訳されなくなる。

**式を書いて数値で固定すると、式が飾りになる。** kMaxOps から導く形に
直した (`(kMaxOps - 1) * 3 + 4`)。

#### 2. staging の上限を写したテストが 1.7 倍ゆるかった

2 つのテストが `CHECK(need <= 1536)` と**旧い staging の値を写して**
いた。実物の `kMaxBlockBytes` は Tier E で 2560 へ広がっていたので、
**上限が 1.7 倍ゆるいまま「収まる」と言っていた**。

`kCapacityResetThreshold` を public にした判断 (定数を写したテストは
値を変えると嘘の失敗をする) の裏返しで、こちらは**嘘の成功**をしていた。
実物の定数を読む形へ直した。

### 本当の天井は kMaxBlockBytes ではなく Xtensa の分岐到達距離

書き形 MOVEM を 5 つ並べると `requiredSize` が 0 を返す。
kMaxPendingGuards を直しても変わらない。犯人は:

```
if (!canBranch12(disp))   // -2048..2047
```

**ガードは前方の出口の島へ飛ぶが、Xtensa の条件分岐の変位は 12bit
符号付きしかない。** 書き形 MOVEM は 1 命令で約 496 バイトなので、
5 つ並べると先頭のガードから最後の島までが 2048 バイトを超える。

これは定数を広げれば済む話ではない (**命令符号の幅なので動かせない**)。
届かない形は emitBlock が false を返して**その 1 本だけ諦める**。
諦めたブロックはインタプリタが実行するので正しさは損なわれない。

`kMaxBlockBytes = 2560` は**この 2048 より大きいので、実質的に効いて
いない**。次に kMaxOps を伸ばす人が見るべきはバイト数ではなく到達距離。

### 割り込み受理点のテストを新設した

`block_plan.h` が「伸ばす変更は受理点のずれを検査するテストを必ず通す
こと」と要求していたが、**そのテストは存在しなかった** (kMaxOps を
4 から動かした人が今までいなかったため)。4 件を新設した。

- 割り込みが保留なら runner はブロックへ入らない (翻訳すら試みない)
- **割り込みは呼び出しのたびに問われる** (「入口だけ」変異を捕まえる本体)
- halted と stopped も同じ扱いで降りる
- 計画は kMaxOps を超える命令を積まない (遅れの上限そのもの)

`runBlock` はホストで `std::abort()` するので、**翻訳を失敗させたまま
問う**。割り込みの検査は run() の最初の文でスロット索引よりも翻訳よりも
手前にあるので、これで全部通る。

### 変異を 8 個入れて全部落ちた

| 変異 | 結果 |
|---|---|
| M1 受理の検査をブロック入口だけにする | KILLED (3 件落ちた) |
| M2 mustDeferToStep が割り込みしか見ない | KILLED |
| M3 mustDeferToStep が割り込みを見ない | KILLED (2 件) |
| M4 kCapacity の判定が 1 ずれる | KILLED |
| M5 PlannedOp に欄を足して 20 バイトを超える | KILLED |
| M6 kMaxPendingGuards を 16 に固定し直す | KILLED (76 件) |
| M7 requiredSize が断らずに 1 を返す | KILLED (85 件) |
| M8 deferInterrupt を数えない | KILLED |

M1 が課題の名指しした変異で、新設したテストが捕まえている。

### 教訓: 「上限が主因でない」ことは上限を動かすまで分からない

段 0-D で区間の切れる理由の内訳 (分岐 43.3% / 呼出・復帰 30.3% /
書込 26.5%) を測っていた。**kCapacity はそこに載っていない。**

つまり「上限が主因ではない」ことは**既に測ってあった**のに、
`kMaxOps = 4` のコメントは「8 でも 16 でも実効的な差が出ない」と
別の (机上の) 根拠で同じ結論を書いていた。

実際に動かしてみると、4 → 6 には +2.7% があり (机上の見積りは
「差が出ない」だった)、6 → 12 には何も無かった (内訳が予告していた
とおり)。**片方だけ当たっていた。**

内訳の統計は「どこで飽和するか」を正しく予告したが、
「飽和点までにどれだけ得があるか」は予告しなかった。
D = 218.3 を測るまで、その得を評価する分母が無かったためである。

## 段 F/G の周辺 — 「不一致 26.7%」は統計の名前が招いた誤読

### 何が起きたか

段 F でバイト照合を入れたら、実機で **不一致が 26.7%** 出た。前回のホスト
計測では「世代が動いたブロックの **100.00%** で命令語は 1 バイトも変わって
いない」だったので、**両立しない**。

私は「命令語が書き換わっている」と読み、原因 (自己書き換え? DMA?) を
調べさせた。**誤読だった。**

実機のダンプ:

```
[probe] 不一致の内訳: 控え無し 661,577 / 読めず 0 / 実差 0
```

**実差 0 件。** 「不一致」の 100.00% が、**控えを持たないので照合を試みて
すらいない**ブロックだった。前回の計測は正しかった。

### 原因は表示の 1 語

`native_exec.h` のフィールドのコメントは正確に書いていた:

> verifyMiss は本当に書き換わったか、**控えを持たなかった**回数。

`main.cpp` の表示がこれを **「不一致」の 1 語**にまとめたのが誤読の原因。

**前者は本物の自己書き換え、後者は控えの語数不足で、打つ手がまったく違う。**
分けて数える形へ直した (`verifyMiss` と `verifyNoSnapshot`)。

### 犯人は 2 本だけだった

| PC | 回数 | count | verifyWords |
|---|---:|---:|---:|
| `$00FAB6` | 330,796 | 6 | **0** |
| `$00FB3E` | 330,792 | 4 | **0** |

どちらも同一 1KB ページにあり、そのページの世代が動くたびに 2 本そろって
外れる。控えが無い理由は `kMaxVerifyWords = 8` で、**段 E で `kMaxOps` を
4 → 6 に上げた結果、この 2 本が上限を割った**。

**前の段の変更が次の段の効果を削っていた。** 段ごとに測っていても、
段の間の相互作用は見えない。

### 教訓: カウンタの名前は、その値の読み方を決める

「収支を閉じる」「理由別に分ける」を積み重ねてきたが、**分けた項の名前が
2 つの意味を持つと、そこで読み違える**。

`verifyMiss` は「照合して違った」と「照合できなかった」を混ぜていた。
どちらも「照合が通らなかった」ではあるが、**対策が正反対**
(前者は諦めるしかない / 後者は控えを伸ばせば救える)。

**1 つのカウンタが 2 つの対策に対応するなら、それは分けるべき 2 つの
カウンタである。**

## 生成コードのサイズ — 容量を埋める方向は頭打ち

平均 240 バイトの内訳 (ROM 全域 26,244 本を発行して分解、比率のみ有効):

| 成分 | 割合 |
|---|---:|
| **命令本体** | **54.5%** |
| リテラルプール | 15.1% |
| 脱出の島 | 11.2% |
| ガード列 | 9.6% |
| 主出口 | 8.6% |

**短縮形の 32bit アクセス** (`l32i.n` / `s32i.n`) がエンコーダに既にあり
照合済みだったのに、エミッタが 1 か所も使っていなかった。44 か所を
置き換えて 244 → 240 バイト、arena に入る本数 67 → 68 本。

**速度は動かなかった** (9682-9774 は素の揺れの中)。

### リテラル共有は見送った

焼かれた語 201,174 に対し異なり値は 22,630 種で、**2 本以上に現れる値が
語数の 96.1%**。完全共有なら **-27.2 バイト/本** (67 → 75 本) になる。

見送った理由:

1. `l32r` の共有プールは **arena のリセットと結びつく新しい無効化契約**を
   作る。全部捨てるときプールも捨てないと「解放済みの値を読む l32r」が
   残る。これは G8 の epoch 保護の外側にある契約で、ドキュメントが名指し
   する「1 箇所漏らすと壊れる」型 (既に 2 度踏んでいる)
2. `requiredSize` の 2 パス構成が崩れる (1 本の必要サイズが arena の状態の
   関数になる)
3. **75 本でも足りない。** 上位 100 ブロックが動的実行の 99.7% を占める

**-4 バイトで 1 本しか増えず速度が動かなかった実測が、段 E-0 と訂正 2 の
「容量を埋める方向では届かない」を裏書きした。**
