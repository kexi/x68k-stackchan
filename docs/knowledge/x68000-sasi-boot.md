# X68000 の SASI 起動経路

SASI から Human68k を起動させるまでに必要なものを、IPL-ROM が実際に
何を読み・何と比較しているかで記録する。

**ここに書いた値はすべて実物の ROM から読み取ったもの。**推測で組むと
ほぼ確実に外れる。実際、最初は SCSI/SASI の一般的な仕様から類推して
実装したが、レジスタの位置もフェーズの値も転送方向もすべて違っていた。

## 全体の流れ

```
SRAM の設定を読む
  ↓ $ED0018 = 起動デバイス、$ED005A = SASI 接続台数
SASI の存在を確かめる ($C2 コマンド)
  ↓
LBA 4 を読んで "X68K" を検査
  ↓
LBA 0 から 4 セクタを $002000 へ読む
  ↓ 先頭バイトが $60 か検査
$002000 を実行 (ここからディスク側のブートコード)
```

## 1. SRAM の設定

| オフセット | 内容 | 値 |
|---|---|---|
| `$00`-`$07` | マジック | `82 77 36 38 30 30 30 57` |
| `$18` | 最優先起動デバイス | `$8000` = SASI 0 |
| `$5A` | SASI 接続台数 | 1 以上 |

マジックの先頭 2 バイトは **Shift_JIS の全角「Ｘ」**（`$82 $77`）。
半角の `'X'` ではない。ここを間違えると IPL-ROM がマジック不正と判断し、
SRAM 全体を工場出荷状態へ書き戻す。そのとき起動デバイスも `$0000`
（標準優先順位）に戻るので、SASI 起動の設定が消えて FD の走査へ落ちる。

接続台数は IPL-ROM が `$FF0B00` で `$000CB4` へ写し、SASI ドライバ
（`$FF9684`）が「ID < 台数か」で接続の有無を判定する。0 のままだと
ID 0 すら範囲外になり、セレクションまで到達しない。

## 2. SASI のレジスタ

`$E96000` から。**奇数アドレスにしか現れない。**

| アドレス | 用途 |
|---|---|
| `$E96001` | データ。コマンド・パラメータ・セクタ・ステータスの授受 |
| `$E96003` | ステータス。下位 5bit がフェーズ |
| `$E96005` | 割り込み許可 |
| `$E96007` | **セレクション**。ターゲット ID を書く |

セレクションが `$E96001` ではなく `$E96007` である点に注意。
`$E96001` はデータ専用で、セレクション前に書かれることはない。

## 3. フェーズの値

IPL-ROM は `$E96003` を読んで `AND.B #$1F` した値を、次の定数と
比較して待つ。ビットの意味を推測して組み立てるより、**この値そのものを
返す**方が間違えない。

| 値 | 意味 | IPL-ROM の待ち場所 |
|---|---|---|
| `$00` | バスフリー | `$FF96DA` の `BTST #1`（bit1 が 0 になるのを待つ） |
| `$07` | データイン（ターゲット → CPU） | `$FF97BE` |
| `$0B` | コマンド送出・データアウト | `$FF9842` / `$FF9890` / `$FF98BC` |
| `$03` | `$C2` のパラメータ送出待ち | `$FF991C` |
| `$0F` | ステータス（終了コードを読む） | `$FF970A` で `D6=$0F` |
| `$1F` | メッセージ（読んでバス解放） | `$FF971E` で `D6=$1F` |

**セレクション直後にいきなり `$0B` を返してはいけない。**
`$FF96DA` は bit1 が **0** になるのを待つが、`$0B` は bit1 が 1。
「セレクション成立」を表す中間状態を挟み、最初の読みで `$00` を
返してから `$0B` へ移る必要がある。

`$FF97BE` に `$07` を待つ経路と `$FF9842` に `$0B` を待つ経路の
両方があるが、コマンド送出で実際に呼ばれるのは `$0B` の側。
`$07` を返すとコマンドを 1 バイトも受け取れないまま止まる。

## 4. コマンド

コマンドは 6 バイト。`opcode / LBA上位 / LBA中位 / LBA下位 / 長さ / 0`。

| コード | 内容 |
|---|---|
| `$00` | TEST UNIT READY |
| `$01` | REZERO UNIT |
| `$08` | READ |
| `$0A` | WRITE |
| `$C2` | **X68000 固有**。ドライブパラメータ設定 |

`$C2` は IPL-ROM が最初に発行する（テンプレートは `$FF99AC`）。
6 バイトのコマンドの後に **10 バイトのパラメータ**が続く
（`$FF990E` で `D3=9` の `DBRA`）。これを受け切らないと次へ進まない。
しかもパラメータ待ちだけはフェーズ値が `$03` で、通常のデータ転送と違う。

## 5. データ転送は DMAC 経由

**SASI のデータは CPU が 1 バイトずつ読むのではない。**
DMAC (HD63450) のチャネル 1 が転送する。ここを実装しないと、
ブートセクタがメモリへ届かず `"X68K"` の検査で必ず失敗する。

IPL-ROM は READ を送った後 `$FF9944` で次の順に設定して起動する。

| レジスタ | 値 | 意味 |
|---|---|---|
| `$E84040` | `$FF` を書く | CSR をクリア（書いたビットが落ちる） |
| `$E84045` | `$B2` または `$32` | OCR。bit7 が転送方向 |
| `$E8404C` | アドレス | MAR。転送先 |
| `$E8404A` | バイト数 | MTC |
| `$E84047` | `$80` | CCR。bit7 で転送開始 |

`$FF9944` の実測はこう。**読み出しと書き込みで OCR の値が違い、
分岐して同じ続きへ合流する**。

```
FF9944: 13FC 00FF 00E84040   MOVE.B #$FF,$00E84040   ; CSR クリア
FF994C: 13FC 00B2 00E84045   MOVE.B #$B2,$00E84045   ; OCR（読み出し）
FF9954: 6010                 BRA $FF9966
FF9956: 13FC 00FF 00E84040   MOVE.B #$FF,$00E84040   ; CSR クリア
FF995E: 13FC 0032 00E84045   MOVE.B #$32,$00E84045   ; OCR（書き込み）
FF9966: 23C9 00E8404C        MOVE.L A1,$00E8404C     ; MAR
FF996C: 33C3 00E8404A        MOVE.W D3,$00E8404A     ; MTC
FF9972: 13FC 0080 00E84047   MOVE.B #$80,$00E84047   ; CCR、転送開始
FF997A: 4E75                 RTS
```

`$B2` と `$32` の差は bit7 だけ。**bit7 = 1 が「デバイス → メモリ」
（読み出し）**、0 が「メモリ → デバイス」。逆に取ると 1 バイトも
転送されない。起動経路で使うのは `$B2` の側。

転送が終わったら **CSR の bit7 (COC) を立てる**。IPL-ROM は
`$FF9738` でこれを読み、立っていなければ「転送されなかった」と
判断して `$E84047` へ `$10`（中断）を書く。

```
FF9738: 1039 00E84040   MOVE.B $00E84040,D0
FF973E: 0800 0007       BTST #7,D0
FF9742: 6608            BNE (正常)
FF9744: 13FC 0010 00E84047  MOVE.B #$10,$00E84047   ; 中断
```

**READ は要求されたセクタ数をまとめて返す。** 1 セクタずつ返すと
1024 バイトの DMA が 256 バイトで止まり、`$002000` に読み込まれる
ブートコードが尻切れになる。

## 6. ディスクの構造

IPL-ROM が求めるのは次の 2 点だけ。FAT も パーティションテーブルも
起動には要らない。

### LBA 4: 識別セクタ

IPL-ROM はまず LBA 4 から 256 バイトを読み（`$FF91E6` の `MOVEQ #4,D2`
で LBA=4、`$FF91E8` の `MOVE.L #$100,D3` で長さ 256）、次を検査する。

| オフセット | 内容 |
|---|---|
| `$00` | `"X68K"` (`$5836384B`)。`$FF91FA` の `CMPI.L` |
| `$04` | 総セクタ数。`$FF920E` で `$9FD9` 以上か見る |

読み込み先は **スタック上の一時バッファ**（`$FF91DE` の
`LEA -$100(A7),A7`）。そのため検査は `$4(A7)` / `$8(A7)` という
形になっていて、ROM を読むと一見オフセットが 4 ずれて見える。
`$FF91F2` で `MOVE.L D0,-(A7)` が挟まっているぶんなので、
**バッファ先頭からのオフセットは表のとおり `$00` と `$04`**。

### LBA 0: ブートコード

LBA 0 から **4 セクタ (1024 バイト)** が `$002000` へ読み込まれ、
そのまま実行される。

**先頭バイトは `$60` (BRA) でなければならない。**
`$FF02BE` の `CMPI.B #$60,(A1)` で検査され、違えば `JMP` されずに
次の起動デバイスへ行ってしまう。壊れたセクタを実行しないための約束。

**LBA 4 が識別用で LBA 0 が実行される**、という順序が直感に反する。
「ブートセクタ = LBA 0」と思い込んで LBA 0 に識別子を置くと、
IPL-ROM は LBA 4 を見に行くので永遠に一致しない。

## 7. ブートコードから使える IOCS

ブートコードが動く時点で IOCS ベクタは張られており、SASI の
ドライバも使える。`TRAP #15` で呼ぶ。

| `D0` | 名前 | 引数 |
|---|---|---|
| `$47` | B_RECALI（REZERO / ドライブの準備） | `D1`=デバイス (`$8000`+ID) |
| `$46` | B_READ（実際の読み出し） | `D1`=デバイス (`$8000`+ID) / `D2`=LBA / `D3`=**バイト数** / `A1`=転送先 |

**`$47` と `$46` を取り違えない。** 資料によっては `$47` を「B_READ」と
呼ぶものがあるが、この ROM で実際にデータを運ぶのは **`$46`** の方。
`$47` はドライブを頭出しするだけでバイトを 1 つも転送しない。
`$47` だけ実装して `$46` を忘れると、「エラーは返らないのに転送先が
ゼロのまま」という切り分けにくい症状になる。

IPL-ROM 自身が `$FF029C` で **両方を順に呼んでいる**（実測。ROM を
逆アセンブルして確認）。

```
FF029C: 4282            CLR.L D2             ; LBA = 0
FF029E: 263C 00000400   MOVE.L #$400,D3      ; 1024 バイト
FF02A4: 43F9 00002000   LEA $002000,A1       ; 転送先
FF02AA: 7047            MOVEQ #$47,D0        ; ← まずドライブの準備
FF02AC: 4E4F            TRAP #15
FF02AE: 4A00            TST.B D0
FF02B0: 661C            BNE (失敗なら次のデバイスへ)
FF02B2: 7046            MOVEQ #$46,D0        ; ← ここが本当の読み出し
FF02B4: 2F09            MOVE.L A1,-(A7)
FF02B6: 4E4F            TRAP #15
FF02B8: 225F            MOVEA.L (A7)+,A1
FF02BA: 4A00            TST.B D0
FF02BC: 6610            BNE (失敗なら次のデバイスへ)
FF02BE: 0C11 0060       CMPI.B #$60,(A1)     ; 先頭が BRA か
```

`D3` はセクタ数ではなくバイト数。IPL-ROM は `$FF9676` で
`ADD.L #$FF` してから `LSR.L #8` し、256 で割ってセクタ数にしている
（`$FF9676: 2003 D0BC 000000FF E088` を実測で確認）。

なお IOCS ベクタの実体は `$FF1B32` からの 224 エントリのテーブルが
`$000400` へコピーされたもの。この ROM では `$46` → `$FF8ABE`、
`$47` → `$FF8B76`。

## 8. HUMAN.SYS は X 形式の実行ファイル

先頭 64 バイトがヘッダ。

| オフセット | 内容 | Human68k 3.02 の実測値 |
|---|---|---|
| `$00` | `"HU"` | `$4855` |
| `$04` | ロードアドレス | `$00006800` |
| `$08` | 実行開始アドレス | `$00006800` |
| `$0C` | text サイズ | `$0000A890` |
| `$10` | data サイズ | `$000033EA` |
| `$14` | bss サイズ | `$00000000` |
| `$18` | 再配置表サイズ | `$000007C6` |

ロードアドレスも実行開始アドレスも `$006800` で一致する。

ファイル全体は 58496 バイトで、`64 + text + data + reloc`
（`64 + $A890 + $33EA + $7C6 = 58496`）にちょうど一致する。
**メモリへ置くのは text + data の `$DC7A` バイトだけ**で、
末尾の再配置表は展開後のイメージには含めない。ここを含めたまま
書くと後続の領域を潰す。

再配置表は、**置き場所がヘッダの `load_addr` と違うときだけ**適用する。
表は「前回の位置からの差分」の並びで、差分 `$0001` は「次の 4 バイトが
32bit の差分」という脱出符号。指された場所の 32bit 値へ
`置き場所 - load_addr` を足す。

HUMAN.SYS はヘッダどおり `$6800` へ置くので差分は 0 になり、
**この経路では再配置表を読む必要がない**。実装
（`tools/make_sasi_image.py` の `to_memory_image()`）も
`base == load_addr` なら表を読まずに返す。

bss はヘッダの `bss_size` ぶんゼロを追加して表現する。3.02 では
`bss_size` が 0 なので実質何も足されないが、**他の版で 0 とは限らない**
ので、決め打ちせずヘッダの値を使う。

生のファイルをそのまま `$6800` へ読み込むとヘッダごと実行してしまい、
`"HU"` (`$4855`) が命令として解釈されて暴走する。ヘッダを外して
メモリ上の姿へ展開してから置く（`tools/make_sasi_image.py` が担当）。

## 9. HUMAN.SYS が起動した後に見るもの

ここまで通ると HUMAN.SYS は $6800 から動き出す。その先で使うワークを
記録しておく。どれもアドレスが決め打ちなので、値が入っていないと
黙って先へ進まない。

| アドレス | 用途 | 読む場所 |
|---|---|---|
| `$000812` | キーバッファの**残数**（word） | `$FF177C` の `CMPI.W #$40` |
| `$000814` | キーバッファの**書き込み位置** | `$FF1786` / `$FF179E` |
| `$000818` | キーバッファの**読み出し位置** | `$FF6032` / `$FF6054` |
| `$00081C` | キーバッファの**先頭**（`$00089C` で折り返す） | `$FF1792` / `$FF605E` |
| `$000BC2` | キーボードの動作モード | `$FF42BC` の `CMPI.B #2` |
| `$000BCA` | キー**文字列**の残数（`$000BCC` が読み出し位置） | `$FF32BA` / `$FF3300` |
| `$000CB4` | SASI の接続台数 | `$FF9684` の `CMP.B` |

**`$00081C` は「残数」でも「書き込み位置」でもなくバッファの先頭。**
一度ここを残数と書いていたが誤り。4 つが連番で並んでいて紛らわしいので、
役割を取り違えたまま実装すると「積んだのに読めない」形で詰まる。
実測した命令は次のとおり。

```
FF177C: 0C79 0040 00000812   CMPI.W #$40,$000812   ; 満杯か
FF1786: 2079 00000814        MOVEA.L $000814,A0    ; 書き込み位置
FF178C: 5488                 ADDQ.L #2,A0
FF178E: B1FC 0000089C        CMPA.L #$00089C,A0    ; 末尾を越えたら
FF1794: 6506                 BCS +6
FF1796: 207C 0000081C        MOVEA.L #$00081C,A0   ; 先頭へ折り返す
FF179E: 23C8 00000814        MOVE.L A0,$000814
FF17A4: 5279 00000812        ADDQ.W #1,$000812     ; 残数 +1
```

キー入力の流れ:

```
MFP が受信割り込みを上げる
  ↓ $FF15EA (割り込みハンドラ)
UDR ($E8802F) からスキャンコードを読む
  ↓ $FF1644 → $FF17AC / $FF17D4 / $FF1878
スキャンコードを ASCII へ変換
  ↓ $FF177C
$00081C 起点のリングバッファへ積み、残数 ($000812) を増やす
  ↓
IOCS $00 ($FF32BA) が $FF6032 の待ちを抜ける
  戻り値 D0 = キーコード<<16 | ASCII
```

`$FF6032` は IOCS `$00` の入口そのものではなく、その中から呼ばれる
取り出しルーチン。入口は `$FF32BA`（`$FF1B32` のベクタテーブルで確認）。
`$FF32BA` はまず `$000BCA`（キー文字列の残数）を見て、そちらが残って
いれば `$000BCC` の指す文字列から 1 バイト返し、`$FF6032` までは
降りてこない。**`$000BCA` はキーバッファの残数ではない**（残数は
`$000812`）。ファンクションキー展開などの「積まれた文字列」の残り。

### `$000BC2` の比較は関門ではない（ただし場所は `$FF42BC`）

一度「`$FF42BA` の `CMPI.B #2,$000BC2` がキー入力の関門」と書いたが
**誤り**。訂正すると次の 2 点。

第一に、**アドレスは `$FF42BA` ではなく `$FF42BC`**。`$FF42BA` は
その手前の `TST.W $000ADE` に対する `BNE` の位置。実測すると
`$FF42AC` から 3 つのテストが並んでいて、どれも同じ場所へ抜ける。

```
FF42AC: 4A39 00000BC4   TST.B $000BC4
FF42B2: 665A            BNE $FF430E
FF42B4: 4A79 00000ADE   TST.W $000ADE
FF42BA: 6652            BNE $FF430E      ← $FF42BA はこの BNE
FF42BC: 0C39 0002 00000BC2  CMPI.B #2,$000BC2
FF42C4: 6648            BNE $FF430E      ← 飛び先は $FF430E
```

第二に、**飛び先は `$FF430C` ではなく `$FF430E` で、そこは `RTS` では
ない**。`$FF430C` の `4E75` は手前のルーチンの終端で、1 バイトずれて
読むと「RTS するだけ」に見えてしまう。実際の `$FF430E` は次のとおり。

```
FF430E: 4A39 00000BC4   TST.B $000BC4
FF4314: 66F6            BNE $FF430C      ; $0BC4 が空くまで待つ
FF4316: 4A39 00000BC3   TST.B $000BC3
FF431C: 6716            BEQ $FF4334
FF431E: 13FC 0001 00000BC4  MOVE.B #1,$000BC4
...
```

つまり「モード 2 用の特殊処理を飛ばして即 RTS」ではなく、**別の
キーボード処理へ合流している**。とはいえ結論は変わらず、
**ここはキー入力の関門ではない**。通常のキー処理は上の
`$FF15EA` → `$FF177C` → バッファの経路を通り、この比較は経由しない。
キーが届かないときにここを疑うと時間を溶かす。

`$000BC2` に 2 を書くのは IOCS `$7D`（`$FF4138`）を `D1=1` で
2 回呼んだときだが、**Human68k は起動時にこれを 1 へ戻す**ので、
そこを触っても意味がない。

MFP の UDR は `$E8802F`。MFP のレジスタは奇数アドレスにしか現れないので、
レジスタ番号 n は `$E88000 + n*2 + 1` に見える。

**キー入力が届かないときの切り分け**:

1. MFP の IPRA に受信割り込みが立つか → 立たなければ IERA/IMRA の設定か
   `receiveKeyboardByte` の問題
2. 割り込みハンドラ (`$FF15EA`) が実行されるか → されなければ CPU の
   割り込みマスクか acknowledge の順序
3. `$FF179E` に到達するか → すればバッファへ積まれている
4. `$FF6048` の `RTS` で `D0` に値が入るか → 入れば `IOCS $00` の待ちを
   抜けられている

## 10. Human68k の起動時メニュー

HUMAN.SYS が動き出すと、$F75E で起動オプションの選択待ちに入る。

```
AND.W #$DF,D0        ; 押されたキーを大文字へ
CMP.B #'A',D0        ; $F762
CMP.B #'R',D0        ; $F768
CMP.B #'I',D0        ; $F76E
どれでもなければ再入力
```

選べる項目は `D7` のビットで決まる。`D7` は $F710 の先 ($F8D6) で
**IOCS $2F (SRAM 読み出し) を D1=$0D で呼んだ値**。読めた値が
$10 未満または $80 以上なら既定値 $10 に置き換えられる ($F722)。

| ビット | キー | $D7 を設定する場所 |
|---|---|---|
| bit4 | `A` | $F792 で `CLR.B D7` |
| bit5 | `R` | $F786 で `MOVE.B #1,D7` |
| bit6 | `I` | $F77A で `MOVE.B #2,D7` |

既定値 $10 では `A` しか選べない。

### IOCS `$FF` は踏んではいけない（過去 2 回書き間違えた）

この番号については訂正が 2 段階ある。**最終的な結論は「IOCS `$FF` は
エラー停止であり、呼ばれたら異常」。**

1. 最初「IOCS `$FF` = システム終了」と書いた → 誤り。
2. 次に「`$FF059A` を読むとキーボードのワークをクリアして RTS するだけ
   なので無害」と訂正した → **これも誤り**。`$FF059A` は IOCS `$FF`
   ではない。

ベクタテーブルの実測でこう決着した。IPL-ROM は `$FF0028` 付近で
`$FF1B32` からの 224 エントリを `$000400` へコピーしたあと、
末尾 3 本を個別に上書きしている。

```
FF002E: 23FC 00FF058E 000007FC   MOVE.L #$FF058E,$000007FC  ; IOCS $FF
FF0038: 23FC 00FF01B6 000007F8   MOVE.L #$FF01B6,$000007F8  ; IOCS $FE
FF0042: 23FC 00FF059A 000007F4   MOVE.L #$FF059A,$000007F4  ; IOCS $FD
```

ベクタテーブルの先頭は `$000400` なので、`$0007FC` は
`($7FC-$400)/4 = $FF` 番。よって:

| IOCS | 実体 | 中身 |
|---|---|---|
| `$FF` | `$FF058E` | **エラー停止**。文字列を出して無限ループ |
| `$FE` | `$FF01B6` | 再起動系（`LEA $2000,A7` から始まる） |
| `$FD` | `$FF059A` | キーボードのワークをクリアして RTS |

`$FF059A` を IOCS `$FF` だと思い込んだのが誤りの原因。1 本ずれていた。

IOCS `$FF` の実体はこれだけ。

```
FF058E: 43F9 00FF08FB   LEA $FF08FB,A1   ; 「エラーが発生しました。」(Shift_JIS)
FF0594: 6100 6C88       BSR $FF721E      ; 文字列出力
FF0598: 60FE            BRA $FF0598      ; 無限ループ
```

`$FF0598` は落とし穴ドキュメントで「エラー停止ループ」として挙げている
のと同じ場所。**エミュレータで IOCS `$FF` が呼ばれたら、それは何かを
実装し損ねた合図**であって、正常系ではない。「終了処理だから握り潰して
よい」と扱うと、本当のエラーが見えなくなる。

一方 `$FF059A`（IOCS `$FD`）は、キーボード関係のワーク
（`$000ADE` を word で、`$000BC4` / `$000BC5` を byte で）クリアし、
MFP の割り込み許可を設定して RTS する。こちらは無害。

```
FF059A: 4279 00000ADE   CLR.W $000ADE
FF05A0: 4239 00000BC4   CLR.B $000BC4
FF05A6: 4239 00000BC5   CLR.B $000BC5
FF05AC: 08F9 0004 00E88013  BSET #4,$00E88013   ; MFP IERB
```

## 12. Human68k のファイルシステム

IPL-ROM が求めるのは LBA 4 の識別子と LBA 0 のブートコードだけだが、
**起動後の Human68k は自分でパーティションと FAT を読む**。ここが
合っていないと COMMAND.X が見つからず、HUMAN.SYS 内蔵の非常用
ミニシェル (`#`) に落ちる。

### パーティションの bit24 は「登録しない」の印

LBA 4 のパーティションテーブル (+$8 の開始セクタ) の最上位バイトは
フラグで、**0 でなければならない**。

```
0080C0: 0800 0018   BTST #24,D0
0080C4: 6600        BNE $80B4      ← 立っていたら次のエントリへ
```

`BNE` で飛ぶので、立っていると**そのパーティションを読み飛ばす**。
「起動可能の印」と読んで立てると SASI の登録数が 0 になり、
ドライブ A: がフロッピーへ落ちる。

**症状が原因から遠い**。ブートコードは IOCS `$46` で直接読むので
HUMAN.SYS だけは起動でき、COMMAND.X の探索だけが空の FD を見て
失敗する。「起動したのにコマンドが動かない」という壊れ方になる。

### セクタ長は 1024 バイト固定

SASI ドライバは論理セクタ番号を**無条件に 4 倍する**。

```
01102E: E58A   ASL.L #2,D2
```

SASI の物理セクタは 256 バイトなので、**Human68k から見た 1 セクタは
1024 バイト**。しかも Human68k は**ディスク上の BPB を読まない**。
`$10E4C` の内蔵テーブルを返し、FAT のセクタ数を自分で計算する
(`$80F6`〜`$8138`)。こちらが実機の値に合わせるしかない。

20MB なら FAT16 / 40 セクタ×2 / ルート 512 エントリ。クラスタ数が
`$FF7` を超えるので FAT12 は使えない。

### FAT16 のエントリはビッグエンディアン

```
00EE2E: 0828 0007 000D   BTST #7,$D(A0)
```

このビットが 0 だと `ror.w #8` を通らず、68000 の素のワード読み
(ビッグエンディアン) になる。PC の FAT と同じつもりでリトル
エンディアンで書くと、クラスタ 60 の次が `$003D` ではなく
`$3D00` (15616) と読まれ、そこが 0 なので「シークエラー」になる。

### FAT の終端は $FFFF の完全一致

```
00B508: 0C40 FFFF   CMPI.W #$FFFF,D0
```

`>= $FFF8` ではない。予約エントリも幅に合わせる。

## 13. 画面が読めないときは IPL-ROM 内蔵フォントを使う

CGROM は無償公開の対象外で入手できない (公式配布は `iplrom.dat` のみ)。
無いと字形が取れず、Human68k が文字を書いても**全ドット埋めの矩形**に
しかならない。何が出ているのか読めず、起動しているのか止まっているのかの
判断がつかない。

IPL-ROM には 6×12 の ANK フォントが 254 文字ぶん入っている。

| 項目 | 値 |
|---|---|
| 開始アドレス | **`$FFD018`** (ファイルオフセット `$1D018`) |
| 1 文字 | 12 バイト (1 バイト 1 ライン、上位 6bit が有効) |
| 添字 | **文字コードそのもの** (オフセットなし) |

**資料にある `$FFCFF6` は誤り**。そこには 68000 の命令列がある。
「下位 2bit が常に 0 の連続領域がちょうど 254×12 バイト」という条件で
ROM 全域を走査すると特定できる。

IOCS が ANK を読むのは `$F3A800 + コード*16` (8×16、1 バイト 1 ライン)。
6×12 も 8×16 も最上位ビットが左端なので、1 バイトをそのまま写せば
左寄せになる。2 ライン下げるとベースラインが合う。

字形の無い領域 (漢字など) は 0 のままにする。ベタ塗りより空白の方が
何が起きているか読める。

## 実装の順序

依存関係があるので、この順に実装すると手戻りが少ない。

1. **SRAM のマジックと起動デバイス** — ここが違うと SASI 経路に
   そもそも入らない。トレースを見ても「FD を探している」ようにしか
   見えず、SASI の実装をいくら直しても意味がない
2. **SASI 接続台数** — セレクションまで到達しない
3. **セレクションとフェーズ** — コマンドが 1 バイトも届かない
4. **`$C2` の 10 バイトパラメータ** — READ まで進まない
5. **DMAC** — データがメモリへ届かない
6. **ディスクの構造 (IPL-ROM 側)** — LBA 4 の識別子と LBA 0 の
   ブートコード。ここまでで HUMAN.SYS が起動する
7. **ディスクの構造 (Human68k 側)** — パーティションの bit24、
   セクタ長 1024、FAT16 のバイト順。ここが合って初めて COMMAND.X が
   読める。`A>` プロンプトが出るのはここまで来てから

各段階で「どこまで進んだか」は `--trace-disk` で分かる。
`[disk] read lba=4` が出れば 5 まで、`lba=0 count=4` が出れば 6 まで
到達している。
