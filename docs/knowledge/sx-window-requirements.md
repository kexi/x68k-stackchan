# SX-Window を動かすために足りないもの

## この文書の位置づけ

**Human68k 3.02 は SASI から起動し、`A>` のプロンプトまで到達した (実測)。
一方 SX-Window は依然として起動していない。SX-Window そのものが
この環境に存在しないため、起動を試すことすらできていない。**

この 2 つを混同しない。**Human68k が起動したことは SX-Window が
動くことを一切意味しない。** Human68k は OS の土台で、SX-Window は
その上に乗る GUI であり、別個の (そして著作物として別に入手が要る)
ソフトウェアである。

### 2026-08-04 の訂正: 「メディアが無い」は誤りだった

この文書は以前「ディスクイメージはこの作業環境のどこにも存在しない」と
書いていた。**これは誤りだった。** 探索が `.hdf` `.hds` `.xdf` `.dim`
`.d88` `.2hd` `.hdm` `.img` という**拡張子**に限られていたためで、
`/tmp/h302/` に Human68k 3.02 の配布ファイル一式 (80 ファイル、1.2MB)
が**展開済みのディレクトリとして**置かれていた。ディスクイメージでは
なく生のファイル群だったので、拡張子の網に掛からなかった。

教訓: **「イメージが無い」と「起動できる材料が無い」は別**。
`tools/make_sasi_image.py` は元々「LZH を展開した生ファイル群から
イメージを組む」ために書かれたツールで、材料はその形で存在していた。
次に同じ判断をするときは、拡張子ではなく `human.sys` / `command.x`
というファイル名で探す。

### 何が起動して、何が起動していないか

| 対象 | 状態 | 根拠 |
|---|---|---|
| Human68k 3.02 | **起動した**。`A>` まで到達し `dir` が動く | 下記「Human68k の起動」 |
| SX-Window | **未起動**。現物がこの環境に無い | `/tmp/h302/` は Human68k の基本セットのみ。`sx` 系のファイルは 0 件 |

`verified` を `partial` のままにしているのは、SX-Window に関する
G-1〜G-5 が依然として**予測**だからである。Human68k の起動は
`confirmed` に格上げしてよいが、この文書の主題は SX-Window なので
全体としては `partial` を維持する。

## 結論の要約

| 区分 | 状態 |
|---|---|
| 画面まわり (G-VRAM / パレット / プライオリティ合成) | **足りている見込み**。デモで通しで動いた |
| マウス (SCC + 割り込み) | **足りている見込み**。デモで割り込み経由まで動いた |
| メインメモリ 2MB | 足りている |
| **フロッピー (FDC)** | 読み書きと割り込みは実装済み。**起動はまだできない**。下記 G-1 |
| **SASI からの起動** | **実測で確認**。Human68k 3.02 が `A>` まで起動した |
| **Human68k の FAT 読み出し** | **実測で確認**。`dir` がルートディレクトリを列挙した |
| **SX-Window 本体** | **入手できていない**。これが現在の最大の欠落 |
| CPU 命令 | Human68k の起動に要る範囲は通った。SX-Window の範囲は未知。下記 G-4 |
| FM 音源 / ADPCM | 未実装。SX-Window の起動自体は妨げない見込み |

## Human68k の起動 (実測)

`tools/make_sasi_image.py` に `/tmp/h302/` を食わせて 20MB の SASI
イメージを作り、起動した。

```sh
just make-hdd /tmp/h302 /tmp/human.hdf
just run --hdd /tmp/human.hdf --cycles 400000000 --dump-text
```

結果 (テキスト画面の抜粋):

```
######## ### ###### version 3.02
Copyright 1987,88,89,90,91,92,93 SHARP/Hudson

Command version 3.00

A>
```

`--keys 'dir\n'` を足すと COMMAND.X が応答する:

```
A>dir
                        A:\
     3                 87K Byte            20168K Byte
HUMAN              SYS      58496
COMMAND            X        28382
CONFIG             SYS         20
```

**これは「プロンプトの絵が出た」のではない。** `dir` は COMMAND.X が
FAT を辿ってルートディレクトリを列挙した結果で、ファイル名も
サイズも配布物の実際の値と一致する (`human.sys` 58496 バイト、
`command.x` 28382 バイト)。つまり Human68k のファイルシステム層が
生きて動いている。

### 通ったディスク経路 (`--trace-disk`)

```
[disk] read lba=4 count=1      # IPL-ROM が識別子 "X68K" を検査
[disk] read lba=0 count=4      # ブートコード 1024B を $002000 へ
[disk] read lba=8 count=221    # HUMAN.SYS を $006800 へ (ブートコードが直接読む)
[disk] read lba=4 count=1      # Human68k がパーティションテーブルを読む
[disk] read lba=836 ...        # 以降 FAT / ルートディレクトリ / COMMAND.X
```

[x68000-sasi-boot.md](x68000-sasi-boot.md) が予測していた順序
(LBA 4 の識別が先、実行されるのは LBA 0) が、そのとおりに観測された。

### 検証に使った現物

| 対象 | MD5 | 備考 |
|---|---|---|
| `/tmp/h302/human.sys` (58496 B) | `023fc17478ecb6a00a41da4bb04de1a8` | Human68k 3.02 |
| `/tmp/h302/command.x` (28382 B) | `1c2bf1153d84eaeb941a1385257d8d81` | Command 3.00 |

**`/tmp/h302/` は永続しない。** `/tmp` は OS の再起動で消えるので、
この結果を再現するには配布物を再取得する必要がある。イメージ自体も
著作物を含むためリポジトリには置けない。

### まだ確かめていないこと

- `--keys` で送れるのは COMMAND.X の内部コマンドまでしか試していない。
  `bin/` 以下の外部コマンド (`chkdsk.x` など) の実行は未確認
- CONFIG.SYS は `make_sasi_image.py` が生成する最小構成
  (`SHELL = \COMMAND.X` の 1 行) を使っている。配布の CONFIG.SYS が
  読み込むデバイスドライバ群は**イメージに入っていない**。
  したがって「Human68k が完全な構成で起動する」ことは示せていない

## 実際に走らせたもの

イメージが無いので、SX-Window が使うのと同じハードウェア経路を
自前の 68000 プログラムで叩くデモを書いた
(`host/gui_demo.cpp`、`--gui-demo out.ppm` で起動)。

**これは SX-Window ではない。** 描いているのは自作の窓であって、
SX-Window のコードは一行も動いていない。示せるのは
「SX-Window が依存する経路が、通しで叩いても絵になる」ところまで。

走った内容と結果:

```
[gui-demo] 1880418 命令を実行しました
[gui-demo] マウス: SCC 有効=1 レポート受理=1
[gui-demo] ゲストが計算したカーソル位置: (296, 260)
```

- 16 色 512x512 モード設定 → パレット 7 色 → プライオリティ → `$C00000` 経由で描画
- 重なった 2 枚の窓 (タイトルバー・閉じるボタン・立体枠・影)
- テキスト面のメニューバーがグラフィック面の手前に合成される
- **マウスが割り込み経由で届く**: ゲストが SCC の WR1/WR2/WR3/WR5/WR9 を
  設定 → `STOP #$2000` で待つ → ホストが `Machine::moveMouse(96, 120)` →
  SCC がベクタ `$54` で受信割り込み → ハンドラが 3 バイトを読んで
  カーソル座標を更新。ゲストが計算した `(296, 260)` は
  ホストが与えた移動量と一致する

検査は `test/test_gui_demo.cpp` が同じ生成器を使って行う
(目視した絵とテストが見る絵をずらさないため、生成を共有している)。

### この過程で分かったこと

**IPL-ROM 既定のプライオリティ (`$FF642E` の `$06E4` = TX が奥) のままだと、
不透明な背景を塗るグラフィック面がテキスト面を丸ごと覆う。**
`GraphicRaster::composite` は
`graphicPriority() >= textPriority()` でどちらを後に描くか決めており
(`src/x68k/core/video/graphic_raster.cpp`)、グラフィックが手前だと
テキストは 1 ドットも見えない。SX-Window はメニューやテキストを
テキスト面に置くはずなので、`$E82500` を TX が手前になる値にする
必要がある。デモは `$0104` (TX=0 / GR=1) にした。

## 足りないもの (詳細)

### G-1. フロッピーは読めるようになったが、まだ起動はできない

**これが最大の関門。** SX-Window の配布形態はフロッピー
(システムディスク + アプリケーションディスク) で、通常は
フロッピーから起動するかインストーラでハードディスクへ導入する。
どちらもフロッピーの読み出しが要る。

**2026-08-04 追記: ここは大きく進んだ。以下は更新後の状態。**

実装済みになったもの:

- **READ/WRITE DATA が DMAC ch0 経由で実際に転送する**。単一・複数セクタとも
  終端カウントまで続く。SEEK / RECALIBRATE / SENSE INTERRUPT STATUS /
  SENSE DRIVE STATUS / READ ID も動く
- **ST3 のレディビットを立てる** (メディアがあるとき)
- **イメージを受け取る口がある**。`Machine::setFloppyDisk()`、
  ホストは `--fd0` / `--fd1`、実機は `/sd/x68k/fd0.xdf`。
  形状はファイル長から決める (2HD 1,261,568 = 77x2x8x1024 ほか)
- **割り込みが配線された**。MFP ではなく **I/O コントローラ ($E9C000)** 経由。
  ROM は `$FF0CAE` でハンドラ表を `$000180` (= ベクタ `$60`) へ写し、
  `$E9C003` にベクタベース `$60` を、`$E9C001` に許可 `$06` を書く。
  `$FF1130` が実際に走ることを `--watch 0x000C8F` で確認済み
  (`PC=$FF11A0` でフラグが立つ)

**それでもフロッピーからは起動しない。** 実測でどこまで進むか:

本物の 2HD 起動ディスク (Human68k 3.02 の `human302.xdf`、`X68IPL30` 署名、
FAT12) を入れて 6 億サイクル回すと、halt もせず画面も出ない。

- FDC は status `$80` (コマンド待ち、アイドル) で正常に待っている
- 割り込みハンドラは走っている (`$000C8F` = 1)
- ROM が待つ完了フラグ `$0009E1` も**実際に立つ**
  (`$FF909E` で `$80`、`$FF90F0` で `$40`、`$FF909E` で `$C0`)
- しかし `$002000` にブートセクタは載らず、`$000C90` は 0 のまま
- PC は `$FF9058` / `$FF906E` / `$FF9074` / `$FF908A` を回り続ける

**さらに追った結果 (2026-08-04)**:

- ROM は **READ を一度も発行しない**。`--trace-disk` を付けても
  `[fd0]` の認識行以降、セクタ要求が 1 件も出ない。失敗しているのは
  データ転送より手前
- モータ制御 `$0009E1` は `$80` → `$40` → `$C0` → `$80` と**上下を繰り返す**
  (`$FF909E` / `$FF90D4` / `$FF90F0`)。回して止めてを延々やっている
- 割り込みハンドラは毎回走り、`$000C90` に `ST0=$20` を積む。
  `$20` は SeekEnd 単独で、RECALIBRATE の**正常終了**。エラーではない

つまり「FDC は正しく応答しているのに ROM が先へ進まない」状態。
`$FF908A` の `TST.B D0 / BEQ` はモータ ON の分岐で、D0 は D1 の上位バイト
(呼び出し元が渡すドライブ番号)。ここが 0 だとモータを回さずに抜ける。

**モータ待ちの仕組み (2026-08-04 追記)**:

`$FF90A4` が `BTST #6,$0009E1` でモータ回転完了を見て、立っていなければ
`$09C2` を `$09C4` へ写して待つ。`$09C4` は MFP のタイマ割り込み
(`$FF1350` のハンドラ、`$FF136C` で減算) が 1 ずつ減らす。

**タイマは正しく動いている。** `--watch 0x0009C4` で
`$C8 → $C7 → $C6 → ...` と減るのを確認した。ただし 0 に到達する前に
`$FF8988` が `$C8` (200) へ戻す。`$FF8978` は

```
3002        MOVE.W D2,D0
6604        BNE  +4
303C 00C8   MOVE.W #$C8,D0    ; 既定 200
30C0 30C0   MOVE.W D0,(A0)+ x2 ; $09C2 と $09C4 へ
```

で、これは**タイムアウトの再武装**。再試行のたびに張り直しているので、
再試行の原因ではなく結果。

**FDC 側のシーケンスは正しい (2026-08-04 実測)**:

RECALIBRATE → SENSE INTERRUPT STATUS を直に叩いて確かめた。

```
idle                = $80
RECALIBRATE 直後     = $80   (結果フェーズを持たないのが正しい)
SENSE INT 発行後     = $D0   (RQM|DIO|CB)
  1 バイト目 -> $20         (ST0 = SeekEnd | unit0)
  2 バイト目 -> $00         (PCN = 0)
  以後       = $80
```

ROM のハンドラ ($FF11DC) が待つのは
`BTST #7 (RQM)` → `BTST #6 (DIO)` の順で、上のとおり満たしている。
**FDC の応答手順そのものは実機の要求どおり。**

したがって再試行の原因は FDC の外側にある。ハンドラは $C90 に
ST0 を積むところまで到達しており ($FF1196)、その後の判定
($FF117C の `BTST #7,D0` = ST0 の bit7) で分岐した先が、
どちらも RECALIBRATE (`MOVEQ #7,D2`) をもう一度投げる形になっている。

**ROM の吸い出しループも正常に抜ける (2026-08-04 実測)**:

`$FF11DC` は次の形で、**1 バイト読めたら非 0 を返す**
(`MOVEQ #-1,D3` の後に `RTS`)。呼び出し側 `$FF1198` の `BNE -6` は
それを見て回り続け、**0 が返ったとき (= RQM 待ちでタイムアウトしたとき)**
だけ抜ける。

このループを手で再現した結果:

```
iter0 status=D0 RQM=1 DIO=1 CB=1  read=$20
iter1 status=D0 RQM=1 DIO=1 CB=1  read=$00
iter2 status=80 RQM=1 DIO=0 CB=0  -> 抜ける
```

2 バイト吸って正しく抜ける。**ここも実機の要求どおり。**

つまり FDC 側は、コマンド受理・結果フェーズ・ステータス遷移・
吸い出しの終了条件まで、検査できる範囲すべてで正しく振る舞っている。
再試行の原因は FDC の外側にある。

**再試行の正体 (2026-08-04 実測)**:

トレースで実際のループを捕まえた。`$FF0320`:

```
787F        MOVEQ #$7F,D4      ; 128 回まで
7044        MOVEQ #$44,D0      ; IOCS $44
4E4F        TRAP #15
0800 001D   BTST #$1D,D0       ; 戻り値の bit29
6606        BNE +6             ; 立っていれば先へ
51CC FFF4   DBRA D4,-12        ; 立っていなければ再試行
6050        BRA +$50           ; 使い切ったら諦める
```

`BTST #$1D` は結果バイトを `ROR.L #8` で上位へ回した後の bit29 =
**結果バイトの bit5**。ST3 の Ready ビット (`$20`) にあたる。

トレースでは `$FF89F0` が `$E94003` から **`$0A`** を読み、
`ROR.L #8` で `$0A000000` になっている。bit29 は 0 なので再試行に入る。

**ただし SENSE DRIVE STATUS を直に叩くと `$78` (Ready 込み) を返す。**
値が違うので、ROM が読んでいるのは SENSE DRIVE STATUS の結果ではなく
別のコマンドの結果。`$0009EF` のコマンド列は `$04 → $04 → $00 → $00` と
変化しており、`$04` (SENSE DRIVE STATUS) 以外も投げている。

**`$0A` の正体が判明した (2026-08-04)**:

IOCS `$44` の実体は `$FF89BA` (実行時にベクタ `$000510` を読んで確認)。
中身は素直に SENSE DRIVE STATUS を投げている:

```
$FF89CA: 123C 0004   MOVE.B #$04,D1     ; SENSE DRIVE STATUS
$FF89D8: 7001        MOVEQ #1,D0        ; パラメータ 1 バイト
$FF89DE: (RQM|DIO|CB を待つ)
$FF89F0: 1039 00E9 4003  MOVE.B $E94003,D0   ; ST3
```

ユニット選択の値を 0-7 で振って ST3 を測ると:

| パラメータ | ST3 | Ready |
|---|---|---|
| `$00` (ドライブ 0) | `$78` | 1 |
| `$01` (ドライブ 1) | `$19` | 0 |
| **`$02` (ドライブ 2)** | **`$0A`** | **0** |
| `$03` (ドライブ 3) | `$0B` | 0 |

**トレースの `$0A` はドライブ 2 の応答だった。** X68000 は FD を 4 台まで
持てるので、ROM は 0-3 を順に調べる。イメージを差していないドライブが
Ready を返さないのは**正しい振る舞い**で、ここはバグではない。

`--fd0` と `--fd1` の両方にイメージを差しても起動しないので、
再試行の原因は「Ready が返らないドライブがある」ことではない。

**呼び出し側が渡す D1 の中身 (2026-08-04)**:

`$FF0310` が走査の入口で、次を組み立ててから IOCS `$44` を呼ぶ:

```
323C 9370        MOVE.W #$9370,D1   ; ← 起動デバイス指定
7401             MOVEQ #1,D2
263C 0000 0400   MOVE.L #$400,D3    ; 1024 バイト
43F9 0000 2000   LEA $002000,A1     ; ブートセクタの転送先
787F             MOVEQ #$7F,D4      ; 128 回まで
7044             MOVEQ #$44,D0
4E4F             TRAP #15
```

`$9370` は sram.h の規約どおり **「FD の 3 番目を最優先」**
(`$9x70` の x がドライブ番号)。bit12 が立っているので
`$FF89BA` の `BTST #12,D1` は真になり、`BSR +$6AC` = **`$FF9070`**
(モータ ON の経路) へ進む。

**走査はドライブ 3 から 0 へ降りる。** これで
「コマンド列が `$04 → $04 → $00 → $00` と変化する」ことと、
途中で `$0A` (ドライブ 2 の ST3) を読んでいたことの説明が付く。

成功したときの続きも読めた:

```
$FF033A: 7047        MOVEQ #$47,D0   ; IOCS $47 = ドライブの準備
         4E4F        TRAP #15
         0800 001E   BTST #$1E,D0    ; bit30
         6646        BNE +$46
         704A        MOVEQ #$4A,D0   ; IOCS $4A = 読み出し
         4E4F        TRAP #15
```

**走査の実測 (2026-08-04)**: `$FF0330` で D0/D1/D4 を採ると:

```
D1=$9070 (ドライブ0) -> D0=$78000000   bit29=1  成功
D1=$9170 (ドライブ1) -> D0=$19000000   bit29=0  128 回再試行
D1=$9270 (ドライブ2) -> D0=$0A000000   bit29=0  128 回再試行
D1=$9370 (ドライブ3) -> D0=$0B000000   bit29=0  128 回再試行
```

走査は**ドライブ 0 から昇る** (前に「3 から降りる」と書いたのは誤り。
`$9370` は `$FF0310` が積む初期値ではなく、走査の途中の値だった)。

回数を数えると `$78000000` (成功) が 3 回、それ以外が各 130 回前後。
**ドライブ 0 は Ready を返して `BTST #$1D` も成立している**のに、
ROM はそこで止まらず次のドライブへ進む。

20 億サイクルまで延ばしても画面は出ない。単に遅いのではない。

**成功経路まで到達していることを確認 (2026-08-04)**:

`$FF0330` の `BNE` は成立していて、その先まで進んでいた。

```
$FF033C  D0=$78000000   ; ドライブ 0 レディ
$FF0344  D0=$20000000   ; IOCS $47 (準備) の戻り。bit30 が 0 = 成功
$FF034A  D0=$00000000   ; IOCS $4A (読み出し) の戻り
```

IOCS `$4A` の実体は `$FF8C9A` (ベクタ `$000528`)。中で
`BTST #27,D0` のエラー判定も通り、`D1=$9040` (コマンド `$0A` = READ DATA)
を組み立てて `$FF8FE0` の送出ルーチンへ入る。

**しかし FDC には READ DATA が届かない。** `$0009EE` のコマンド列を
見ると `$04` (SENSE DRIVE STATUS) / `$07` (RECALIBRATE) / `$0F` (SEEK)
だけで、`$0A` も `$46` も現れない。

**DMAC も起動していない。** `$E84007` (ch0 起動) と `$E8400C` (転送先) を
watch しても書き込みが 1 件も無い。つまり ROM はこの経路で **非 DMA 転送**
を前提にしている。RQM を立てる修正 (コミット 2c672a9) はその前提に
合わせたもので、方向は合っている。

**IOCS `$4A` の中を 1 命令ずつ追った (2026-08-04)**:

```
$FF8CAE  D0=$0000004A  D1=$00009070   ; 入口
$FF8CBC  D0=$20000000  D1=$00009040   ; D1 にコマンド $0A を合成
$FF8CC0  D0=$20000000  D1=$0000904A   ; ドライブ番号を合成
$FF8CC6  D0=$00000001                 ; BSR $FF9006 の直前
$FF8CCA  D0=$0000FFFF
$FF8CCE  D0=$0000FF00
$FF8CD2  D0=$00000000                 ; 0 を返して抜ける
```

`D1=$904A` (READ DATA) まで正しく組み立てている。**しかし
コマンド格納ルーチン `$FF8FE0` は一度も呼ばれない** (PC を張って確認)。
`$0009EE` に書かれるのは `$04` / `$07` / `$0F` だけ。

`$FF9006` は次の形で、**メインステータスの下位 5bit が 0 になるのを待つ**:

```
1039 00E9 4001   MOVE.B $E94001,D0
C03C 001F        AND.B #$1F,D0
66F4             BNE -12
4E75             RTS
```

本エミュレータはアイドル時 `$80` (下位 5bit = 0) を返すので、
ここは即座に抜ける。**待ちで詰まっているわけではない。**

**`$FF8C44` が読む値が 0 になっている (2026-08-04、ここが核心)**:

`$FF8C44` は次の形で、`$C90 + ドライブ*8` の **ロングワード**を返す:

```
3001             MOVE.W D1,D0
E048             LSR.W #8,D0        ; D1 の上位バイト
C0BC 0000 0003   AND.L #3,D0        ; ドライブ番号
E740             ASL.W #3,D0        ; x8
41F9 0000 0C90   LEA $0C90,A0
D1C0             ADDA.L D0,A0
2010             MOVE.L (A0),D0     ; ← 4 バイト読む
4E75             RTS
```

割り込みハンドラ側 (`$FF1194`) は `MOVE.B D0,(A2)` で **1 バイト**書く。
つまり ST0 は最上位バイトに入り、`$20` なら `$20000000` になって
`BTST #30` / `BTST #29` が成立する、という設計。

**実測すると `$C90` は最終的に 0 になっている。** `--watch 0x000C90`:

```
$000C90 <- $20  (PC=$FF1196)
$000C90 <- $20  (PC=$FF1196)
$000C90 <- $00  (PC=$FF1196)   ← 0 で上書きされる
```

ドライブ 1 の枠 (`$C98`) には**一度も書かれない**。つまり 4 ドライブ分の
結果がすべて `$C90` に書かれ、最後の 0 が残っている。

ハンドラは書き込み先を **ST0 の下位 2bit (ユニット番号)** から決める。
本エミュレータの `pendingSt0_` がユニット番号を正しく載せていないと、
別ドライブの結果が `$C90` を潰す。SENSE INTERRUPT STATUS 単体では
`$20` / `$80` を正しく返すので、疑うのは各コマンドが
`pendingSt0_` に載せる `unitSelect()` の値。

**ユニット番号は正しかった (2026-08-04)**:

RECALIBRATE を各ドライブへ投げて SENSE INTERRUPT STATUS を読むと:

```
ドライブ 0 (メディア有) -> ST0=$20  ユニット=0  OK
ドライブ 1 (メディア無) -> ST0=$69  ユニット=1  OK
ドライブ 2 (メディア無) -> ST0=$6A  ユニット=2  OK
ドライブ 3 (メディア無) -> ST0=$6B  ユニット=3  OK
```

**どのドライブも自分の番号を正しく載せている。** `unitSelect()` は
疑いから外れる。SEEK も `$20` (SeekEnd) を返し `$00` にはならない。

`$C90` への書き込みは `$20` / `$20` / `$00` の 3 つが 1 組で繰り返す。
3 番目に ST0=`$00` を返すコマンドがあり、それが最後に残って
`$FF8C44` の読み出しを 0 にしている。**その 3 番目が何かは特定できていない。**

`$00` は「正常終了・ユニット 0・SeekEnd なし」で、本エミュレータが
どのコマンドでこの値を作るのかがコード上すぐには見当たらない。
ハンドラ側 (`$FF1130`) が SENSE INTERRUPT STATUS を複数回投げていて、
2 回目以降に何か別の値を得ている可能性がある。

**書き込み元は 1 箇所だった (2026-08-04)**:

`$C90` の変化を 1 命令ずつ追うと、`$20` と `$00` の**両方が同じ命令**
`$FF1198` (= `$FF1130 + $68`、`MOVE.B D0,(A2)`) から書かれている。
`$20` → `$00` → `$20` → `$00` と交互に繰り返す。

つまりハンドラが 2 回走るたびに、1 回目は `$20`、2 回目は `$00` を
書いている。

**FDC 側の SENSE INTERRUPT STATUS は正しい。** RECALIBRATE の後に
4 回続けて投げると:

```
#1 ST0=$20 PCN=$00
#2 ST0=$80 PCN=$00   (無効コマンド = 保留無し)
#3 ST0=$80 PCN=$00
#4 ST0=$80 PCN=$00
```

2 回目以降は `$80` を返す。しかも ROM は `$FF1176` の
`CMP.B #$80,D0 / BEQ` で `$80` のときは store を**飛ばす**ので、
`$80` が `$C90` に書かれることはない。

**`$00` は PCN だった (2026-08-04、因果が繋がった)**:

ハンドラを 1 命令ずつ追うと、`$FF1198` の store は
**「直前に読んだバイト」**を書いている。`$FF11FE` の
`MOVE.B (A1),D0` が結果フェーズから 1 バイトずつ取り出す吸い出しループで、
SENSE INTERRUPT STATUS は **ST0 と PCN の 2 バイト**を返す。

```
run3: ... D0=$20 で $C90 <- $20   (ST0)
      ... D0=$00 で $C90 <- $00   (PCN = 現在シリンダ 0)
```

**つまり PCN が ST0 を上書きしている。** `$C90` に最後に残るのは
常に PCN で、RECALIBRATE 直後はトラック 0 なので必ず `$00`。

これは ROM 側の作りとしては筋が通っている。実機の SENSE INTERRUPT
STATUS も 2 バイトを返すので、同じことが起きるはず。したがって
**`$C90` の最終値が `$00` であること自体は異常ではない可能性が高い**。

**A2 の追跡で store の形が確定した (2026-08-04)**:

`$FF1198` は `MOVE.B D0,(A2)+` で、A2 は `$C90` → `$C91` と進む。
つまりハンドラは **ST0 を `$C90` へ、PCN を `$C91` へ**順に書く。
1 バイトを上書きしているのではなく、2 バイトを並べている。

(`$FF1134`-`$FF11B0` の間の A2 は `$E94003` = FDC のデータポートで、
こちらはコマンド送出用。同じ A2 を使い回しているので、
トレースを見るときは値で区別する必要がある。)

`$FF8C44` の `MOVE.L ($C90)` はこの 4 バイトをまとめて読むので、
上位から ST0 / PCN / ... の並びになる。ST0=`$20` なら
`$20xxxxxx` となり `BTST #29` (bit29 = ST0 の bit5) が成立するはず。

**ただし起動が落ち着いた後に `$C90..$C97` を読むと全部 0 だった。**
トレース中は `$20` が書かれているので、**後から誰かが 0 で消している**。
`$C8F` (フラグ) は `$01` のまま残る。

**計測が食い違っている (2026-08-04、注意)**:

`$C90` を書く PC は `$FF1196` の 1 箇所だけ (1137 回)。別のクリア
ルーチンは存在しない。`$C91` にも同じ PC から PCN が書かれており、
ハンドラは ST0 → `$C90`、PCN → `$C91` と正しく並べている。

**にもかかわらず、走行を止めて `$C90..$C97` を読むと全部 0 になる。**
watch では `$20` が書かれているのが見えるのに、サンプリングすると
0 しか出ない。40M サイクルでも 120M サイクルでも同じ。

この 2 つは両立しないので、**どちらかの計測が信用できない**。
考えられるのは
(a) watch の表示アドレスが 1 バイト境界で丸められていて、実際には
    `$C91` への書き込みを `$C90` と表示している
(b) サンプリング側が別の Machine インスタンスを見ている
のどちらか。

**食い違いの原因が判明した (2026-08-04)**: `--watch` の仕様だった。

`SystemBus::notifyWatch` はコールバックへ **アクセスの先頭アドレスと
アクセス全体の値**を渡す。監視しているバイトのアドレスと値ではない。

```
$C91 を watch して $C91 へ MOVE.B $AA  -> addr=$000C91 value=$AA
$C91 を watch して $C90 へ MOVE.W $1234 -> addr=$000C90 value=$1234
                                            (実メモリは $C90=$12 $C91=$34)
```

つまり `--watch 0x000C90` で見えていた `$20` / `$00` は、
**`$C90` への `$20` と `$C91` への `$00` (PCN)** をどちらも
「`$C90` への書き込み」として表示していたもの。矛盾ではなかった。

**サンプリング側が正しい。** `$C90..$C97` は実際に全部 0 で、
`$FF8C44` の `MOVE.L` も `$00000000` を読む。したがって
`BTST #30` は成立せず、IOCS `$4A` は READ を出さずに戻る。
**「`$C90` が 0 だから先へ進まない」という見立ては生きている。**

`--watch` を使うときの注意として憶えておくこと。ワード/ロング
アクセスの一部を監視していると、表示アドレスが監視対象と
ずれる。バイト単位で確かめたいときは値の側で判断しない。

**`$00` の出どころが確定した (2026-08-04)**:

信頼できる計測 (`--watch` ではなく 1 命令ごとに `$C90` を読む) で追うと:

```
$C90: $00 -> $20   PC=$FF1198 D0=$00000020   (SEEK/RECAL の SE)
$C90: $20 -> $00   PC=$FF1198 D0=$00000000   (転送完了)
```

同じ命令が 2 回書いている。`$00` は `Fdc::dmaComplete()` の

```cpp
pendingSt0_ = isClean ? unitSelect() : (kSt0AbnormalTermination | unitSelect());
```

から来る。ドライブ 0 の正常終了は `unitSelect()` = **`$00`**。

**これは uPD72065 の仕様どおり**で、バグではない:

```
ST0 bit7-6 IC = 00 (正常終了)
    bit5   SE (Seek End)      ← シーク系のみ
    bit4   EC / bit3 NR / bit2 HD / bit1-0 US
```

READ DATA の完了に SE は立たない。ドライブ 0 の正常終了は `$00`。

**問題は上書きの順序**。ROM は `$FF0330` で `BTST #$1D` (= ST0 の bit5
= SE) を見る。SE が立つのは SEEK / RECALIBRATE の完了だけなので、
ROM が読みたいのは**シーク系の結果**。ところが後続の転送完了が
同じ `$C90` を `$00` で上書きするため、SE が消えている。

**犯人は READ ID だった (2026-08-04、修正済み)**:

`pendingSt0_` を書く各所に一時的な `fprintf` を仕込んで対応を取ると:

```
[set] RECAL media=1
[senseint] ST0=$20     ← RECALIBRATE の SE
[set] SEEK ok -> $20
[senseint] ST0=$20     ← SEEK の SE
[senseint] ST0=$00     ← 直前に [set] が無い
```

3 つ目の直前に代入のログが無く、**READ ID** がメディアありのとき
`pendingSt0_ = unitSelect()` (ドライブ 0 なら `$00`) を積んでいた。
uPD72065 の READ ID は自前の結果フェーズを持つコマンドで、
SENSE INTERRUPT STATUS が返す値ではない。正常時の上書きをやめた。

**`dmaComplete()` は一度も呼ばれていない**ことも分かった。
非 DMA 転送なので当然だが、先にそこを疑って直しかけたのは無駄だった。

修正後:

```
$C90 の最終値 = $20 (以前は $00)
$FF034A の D0 = $20000000 (以前は $00000000)
$FF8CD2 の D0 = $20000000 (以前は $00000000)
```

`BTST #$1E` (bit30 = IC の下位) は 0 なので**正常終了として通る**。
走査はドライブ 0 を成功として抜け、ドライブ 1 へ進むようになった。

**残る問題と、修正が生んだ副作用 (2026-08-04)**:

READ ID の修正で走査は進むようになったが、**ブートセクタは読まれない**。
IOCS `$4A` の中を追うと理由が分かった:

```
$FF8CCA: BSR $FF8C44     ; $C90 のドライブ状態を読む -> $20000000
$FF8CCE: BTST #30,D0     ; bit30 = IC の下位
$FF8CD2: BEQ +10         ; 0 = 正常終了 -> 成功として抜ける
$FF8CDE: MOVEM.L (SP)+
$FF8CE2: BRA +$3F2       ; 転送せずに戻る
```

`$FF8C44` が返すのは **`$C90` に残っている前回の割り込み結果**。
READ ID の上書きを止めたことで、そこには SEEK の `$20` (Seek End) が
残り続ける。ROM はそれを「今回の転送の結果」と解釈し、
bit30=0 = 正常終了と見て**転送せずに成功を返す**。

**つまり修正は片方の詰まりを解いた代わりに、偽の成功を作った。**
`$C90` は「直前の割り込みの結果」を保持する場所なので、
READ DATA を投げる前に古い値が残っていること自体が問題になる。

実機では READ DATA が自前の結果フェーズを返し、その完了割り込みが
`$C90` を更新する。本エミュレータは非 DMA 転送で READ DATA を
まだ実際には走らせていないので、`$C90` が更新されない。

**次の一歩**: `$FF8CC6` の `BSR $FF9006` の前後で、ROM が READ DATA を
FDC へ送るのはどの経路か。`$FF8FE0` (コマンド格納) が呼ばれない以上、
そこへ至る分岐が別にあるはず。`$FF8CC4` の `MOVEQ #1,D0` から
`$FF8CC6` の `BSR` までを 1 命令ずつ追う。

**ここで調査を止めた。** 推測で `pendingSt0_` を触ると、同じ `$C90` を
使う SASI 起動の経路 (現に動いている) を壊しうる。

**ここで調査を止めた。** 推測で `pendingSt0_` を触ると、同じ `$C90` を
使う SASI 起動の経路 (現に動いている) を壊しうる。

**ここで調査を止めた。** 推測で `pendingSt0_` を触ると、同じ `$C90` を
使う SASI 起動の経路 (現に動いている) を壊しうる。
候補は (a) ST0 に SeekEnd 以外に必要なビットがある、
(b) SENSE INTERRUPT STATUS の返し方が実機と違う、
(c) モータの回転待ち時間を見ている、のいずれか。
実機のタイミング (回転待ち) を持っていないことが効いている可能性が高い。

**旧: 次に追うべき場所** (逆アセンブル済み):

```
$FF9050: MOVE.B (A1),D1 / BTST #7,D1 / BEQ -8    ; RQM 待ち
         BTST #6,D1 / BNE -14                     ; DIO が落ちるのを待つ
$FF9070: BTST #7,$0009E1 / BNE +10                ; 完了フラグ監視
$FF9086: MOVE.W D1,D0 / LSR.W #8,D0               ; D0 = D1 の上位バイト
$FF908A: TST.B D0 / BEQ +$48                      ; 0 なら下を飛ばす
         AND.B #3,D0 / OR.B #$80,D0
         BSET #7,$0009E1
         MOVE.B D0,$E94007                        ; ドライブ選択 + モータ
```

`$FF908A` の D0 が 0 のままだと完了フラグが立たず、ROM は再試行を続ける。
ハンドラが積む ST0 と SENSE INTERRUPT STATUS の返し方を実機と
突き合わせるのが筋。

**試して効かなかったこと**: SRAM の起動デバイスを標準優先順位にする。
ROM は `$FF0144` の `MOVE.W $ED0018,D1` で**非常に早く**読むので、
`reset()` の後に書いても間に合わない。CPU だけ再リセットしても同じだった。

### G-2. SASI 経由なら起動しうるが、SX-Window 導入済みのイメージが要る

SASI からの Human68k 起動は実績がある
([x68000-sasi-boot.md](x68000-sasi-boot.md) が
プロトコルとディスク構造を実測で押さえている)。
したがって **SX-Window がインストール済みの `.hdf` があれば、
フロッピーを迂回して試せる可能性がある**。これが現状で最も現実的な経路。

ただし前提として:

- ~~Human68k が起動して `A>` に到達すること~~ →
  **2026-08-04 に達成した**。上記「Human68k の起動」を見よ。
  この前提はもう関門ではない
- SX-Window は Human68k 2.0 以降を要求する。起動したのは 3.02 なので
  この条件は満たす
- 導入済みイメージは 20MB 級になる。`Machine::kSasiMaxSectorsPerCommand`
  は 256 セクタ / コマンドで、転送バッファは 64KB。容量そのものの上限は
  `DiskImage` 実装側に依存する

### G-3. 画面モードは 16 色しか通しで確かめていない

SX-Window は **256 色 768x512** を標準的な画面モードとして使う。

`VideoController` は `k16Color` / `k256Color` / `k65536Color` を持ち、
`test_gvram_bus.cpp` が 256 色経路のバス折り込みを見ている。
だが **今回のデモは 16 色 512x512 でしか通しの動作を確かめていない**
(1 ドット = 1 ワードで命令列が素直になるため)。

256 色モードは 1 ドット 1 バイトで G-VRAM の折り込み方が 16 色と変わる。
768x512 は 512x512 を超えるので、CRTC のパラメータ設定
(`$E80000` 系の水平/垂直タイミング) も別経路になる。
**ここは未検証で、詰まる可能性がある。**

### G-4. 未実装命令に当たれば即停止する

`M68k::unimplemented()` はエミュレータを停止させる
(`Machine::isHalted()` / `haltedOpcode()`)。
SingleStepTests のベクタで 68000 の適合性は取っているが、
**SX-Window が実際に使う命令の網羅性は未知**。
デモの範囲 (MOVE / MOVEA / ORI / EXT / ADD / SUBQ / BNE / STOP) は動いた。

Line-A / Line-F は例外ベクタへ落ちる実装があるので
(`m68k.cpp` の `vector::kLineA` / `kLineF`)、そこは停止しない。

SX-Window は 68000 用に書かれているので、
68020 固有命令や MMU は要らないはず (X68000 Expert は 68000)。

  README は「未実装」としている。SX-Window は起動時に音を鳴らさないので、
  レジスタ書き込みが無視されても止まらない見込み
- **スプライト / BG**: `sprite.cpp` と `sprite_raster.cpp` がある。
  SX-Window のマウスカーソルは**スプライトではなくソフトウェア描画**が
  基本なので、必須ではない見込み

## イメージを入手したときの試し方

```sh
# 1. まず Human68k が A> まで来るか (これは 3.02 で達成済み)
just run --hdd <image>.hdf --cycles 400000000 --dump-text

# 2. 来たら SX-Window を起動 (キー入力を送る)
just run --hdd <image>.hdf --cycles 2000000000 --keys "SX\n" --ppm /tmp/sx.ppm

# 3. 停止したら未実装命令の可能性。命令語が表示される
```

止まった位置の切り分けは
[x68000-emulator-pitfalls.md](x68000-emulator-pitfalls.md) の
症状別の表が使える。
