# X68000 エミュレータ実装の落とし穴

実物の IPL-ROM で起動を試して初めて分かった問題を記録する。いずれも
**合成 ROM や 68000 の命令テストベクタでは検出できなかった**もので、
症状は「何も起きずに固まる」「原因不明の暴走」という形でしか現れない。

同じ轍を踏まないため、症状 → 原因 → 見分け方の順で残す。

## 1. RESET 命令が $000000 の ROM 写像を解除する

**症状**: 777 命令でサブルーチンから戻れなくなる。RTS がスタックから
読んだ戻り先が明らかにおかしい値になる。

**原因**: X68000 はリセット直後、ベクタを読むために `$FF0000` の内容が
`$000000` へ写像される。これを解除するのは**エリアセット (`$E86001`) への
書き込みではなく、`RESET` 命令**だった。IPL-ROM は `$FF001A` で `RESET` を
実行して通常のメモリ配置へ切り替える。

68000 としての `RESET` は外部へ信号を出すだけで CPU 自身は何もしないため、
「何もしない命令」として実装しがちだが、機種固有のこの反応を落とすと
RAM を読んでも ROM の値が返り続ける。

**見分け方**: RTS の戻り先が奇数だったり、明らかに ROM 内のコードを
指していたら、RAM が読めていない可能性を疑う。バス経由で読んだ値と
実際の RAM の内容を突き合わせると一発で分かる。

## 2. 写像されるのは ROM の先頭ではなく $FF0000 側

**症状**: リセット直後に `SSP=FFFFFFE3` のような無意味な値になり即座に暴走。

**原因**: `$000000` へ写像されるのは IPL-ROM の先頭 (`$FE0000`) ではなく
`$FF0000` の側。リセットベクタと起動コードはそこに置かれており、実行は
`$FF0010` から始まる。

**見分け方**: リセット直後の SSP と PC を出す。実機は `SSP=$002000`,
`PC=$FF0010` になる。

## 3. 例外フレームの書き込み位置にアドレスマスクをかけてはいけない

**症状**: 割り込みからの復帰で PC の上位バイトにゴミが乗る
(`$00FF0544` になるべきところが `$1EFF0544`)。

**原因**: 例外フレームを積むとき、SP に `0x00FFFFFE` のマスクをかけていた。
奇数 SP でも書けるようにという配慮だったが、RTE 側は `read32(a7)` で
読み戻すので、書き込み位置と読み出し位置が 1 バイト食い違う。

**見分け方**: PC の上位 8bit が 0 でなくなった瞬間を捕まえる。
そこから遡ると例外処理に行き着く。

## 4. MFP は自動ベクタではなく自前のベクタ番号を返す

**症状**: 起動が進んだ後、画面に「エラーが発生しました。リセットして
ください。」(Shift_JIS) を出して停止する。

**原因**: X68000 の MFP (MC68901) は自動ベクタ (24+level) ではなく、
VR レジスタの上位 4bit と割り込み番号を組み合わせたベクタ番号を返す。
自動ベクタで処理すると、IOCS が未初期化ベクタ用に埋めている
「上位バイト = ベクタ番号」の値 (`$1EFF0540` のような形) を PC に
読み込み、不正ベクタのハンドラへ飛んでしまう。

**見分け方**: 割り込み受理の瞬間に飛び先を出す。IOCS のベクタテーブルを
ダンプすると `$43FF0540`, `$44FF0540` のように上位バイトだけが違う値が
並んでいるのが見える。これが「未初期化」の印。

**関連**: この仕組みのため、PC は 32bit のまま保持し、丸めるのは
バスへ出す瞬間だけにする必要がある。PC 自体を 24bit に丸めると
68000 のテストベクタ (32bit の PC を期待する) が落ちる。

## 5. MFP の送信状態レジスタは空きビットを立てておく

**症状**: `$FF61C8` のポーリングループから抜けられない。

**原因**: IPL-ROM はキーボードへコマンドを送る前に TSR (`$E8802D`) の
bit7 (送信バッファ空き) を待つ。0 で初期化していると永久に待つ。
エミュレータは送信を即座に完了したものとして扱うので、常に空いて
いることにしてよい。

## 6. GPIP の bit1/bit2 は L にしておく

**症状**: `$FF103C` のポーリングループから抜けるのに時間がかかる
（タイムアウトするまで無駄に回る）。

**原因**: IPL-ROM は起動時に GPIP (`$E88001`) の bit1 (EXPON: 拡張ボード) と
bit2 (POWER: 電源スイッチ) が 0 になるのを待つ。全ビットを H (`0xFF`) で
初期化すると、どちらも立ちっぱなしでループが空回りする。

拡張ボードも電源スイッチの押下も無い状態を表すため、この 2 ビットは
L にしておく。

### GPIP のビット割り当て（X68000）

| bit | 用途 |
|---|---|
| 0 | （未使用） |
| 1 | EXPON（拡張ボード） |
| 2 | POWER（電源スイッチ） |
| 3 | OPMIRQ（FM 音源の割り込み） |
| 4 | V-DISP（垂直帰線） |
| 5 | （未使用） |
| 6 | CIRQ（RTC アラーム） |
| 7 | HSYNC（水平同期） |

## 7. FDC のステータスは「応答するが完了しない」に留める

**症状**: FDC のステータス (`$E94001`) に 0 を返すと `$FF9054` で永久に待つ。
かといって `$D0` を返すとエラー停止する。

**原因**: IPL-ROM は FDC の応答を 2 段階で待つ。

| アドレス | 待つもの |
|---|---|
| `$FF9054` | RQM (bit7) が立つ |
| `$FF89DE` | RQM \| DIO \| CB (`$D0`) が揃う |

`$D0` をそのまま返すと「FDC が応答した」と誤認され、続きのコマンド処理へ
進んで最終的にエラー停止する。**RQM だけを立てる**と「コマンドは受け付ける
が結果が返らない」状態になり、IPL-ROM はタイムアウトして次の起動デバイス
(SASI) へ移る。ドライブ未接続を表現するにはこの形が合う。

**教訓**: 未接続のデバイスは「全く応答しない」でも「完全に応答する」でも
なく、**その中間**を返す必要がある場合がある。ポーリングの条件を読んで
どこで止めるかを決める。

## 8. アドレスレジスタと PC は 32bit で保持する

**症状**: 68000 のテストベクタが軒並み落ちる
(`A0: got 00C321E4 want F9C321E4`)。

**原因**: 68000 のアドレスバスは 24bit だが、**内部のレジスタは 32bit**。
上位 8bit が捨てられるのはバスへ出す瞬間だけ。レジスタ側でマスクすると
`A0` に `$F9C321E4` を入れて読み出したときに `$00C321E4` が返るという
実機と違う挙動になる。

## 9. 応答しない領域は 0 ではなくバスエラーを返す

IPL-ROM は「バスエラーが起きるかどうか」で装置の有無を調べる。SCSI ROM
($FC0000) の検出がそれで、$FF0236 から次のことをする。

```
FF0236: 2079 00ED000C   MOVEA.L $ED000C,A0   ← SRAM の ROM 起動アドレス
FF023E: 43F9 00FF0264   LEA $FF0264,A1       ← 自前のバスエラーハンドラ
FF0244: 2479 00000008   MOVEA.L $000008,A2   ← 元のベクタを控える
FF024A: 23C9 00000008   MOVE.L A1,$000008    ← バスエラーベクタを差し替え
FF0250: 2650            MOVEA.L (A0),A3      ← ROM 起動アドレスから読む
FF0260: 4E93            JSR (A3)             ← 読めたら呼ぶ
```

未実装領域で 0 を返すと「ROM がある」ことになり、$000000 へ飛んで暴走する。
「何も繋がっていないアドレスはバスエラー」が正しい。

**注意すべき点が 2 つある。**

第一に、`read32` は 16bit バス上では 2 回の `read16` に分かれる。エラー
フラグは 2 回目で上書きされるので、1 回目の結果を控えて OR を取らないと
上位ワードのエラーを取りこぼす。`read16` が `read8` 2 回に分解される経路も
同じ。

第二に、I/O 空間 ($E80000-$EBFFFF) を「未実装だからバスエラー」にしては
いけない。IPL-ROM も IOCS も存在しないデバイスのレジスタを初期化しに来る
ので、ここでエラーを起こすと起動が進まない。バスエラーにしてよいのは
アドレスデコードのどれにも当たらない領域だけ。

## 10. 起動可能なディスクが無いと IPL-ROM は無限に待つ

これはバグではなく実機どおりの動作だが、トレースだけ見ると無限ループに
見えるので記録しておく。

IPL-ROM は起動デバイスを次の形で走査する ($FF01F8)。以下は ROM の実測。

```
FF01F8: 323C 9070   MOVE.W #$9070,D1   ← デバイス番号 (FD 0)
FF01FC: 7044        MOVEQ #$44,D0      ← IOCS $44 = B_DRVCHK
FF01FE: 4E4F        TRAP #15
FF0200: 0800 001D   BTST #$1D,D0       ← bit29 を見る
FF0204: 6692        BNE $FF0198        ← 使えるドライブなら起動処理へ
FF0206: D27C 0100   ADDI.W #$0100,D1   ← 次のドライブ (+$100 刻み)
FF020A: B27C 9470   CMPI.W #$9470,D1
FF020E: 66EC        BNE $FF01FC        ← 4 台ぶん繰り返す
FF0210: 60E6        BRA $FF01F8
```

**刻みは 1 ではなく `$0100`**、判定するのは `D0` の **bit29**、
比較の上限は `$9470`。デバイス番号は `$9070`/`$9170`/`$9270`/`$9370`
の 4 つ（FD 0〜3）。一度「`ADDI.W #1`、`CMPI.W #4`」と書いていたが
誤りで、IOCS `$44` に渡す値がまるで違ってしまう。

FD 0〜3 を調べて全部だめなら、次の起動デバイスへ進み、それも尽きると
`$FF01F8` へ戻る。実機で言えば「ディスクを入れてください」の待ち状態。

**見分け方**: `--trace-last 4000` を取ってユニークな PC を数える。100 個
以下の有限集合をぐるぐる回っていて、その中に `TRAP #15` ($4E4F) が
含まれていれば、この走査ループ。デバイスの応答バグではないので、
FDC や SASI の実装をいくら直しても抜けない。起動可能なイメージが要る。

## 11. SRAM のマジックは全角の「Ｘ」で始まる

IPL-ROM が検査する 8 バイトは `82 77 36 38 30 30 30 57`。先頭 2 バイトは
半角の `'X'` ($58) ではなく **Shift_JIS の全角「Ｘ」**。

半角で置くとマジック不正と判断され、IPL-ROM が SRAM 全体を工場出荷状態へ
書き戻す。そのとき起動デバイス ($ED0018) も $0000 に戻るので、SASI を
最優先に設定していても消える。

**症状が原因から遠い。** 見えるのは「ディスクから起動できません」の
表示と FD の走査ループで、SRAM が書き戻されたことはトレースからは
分からない。SASI の実装を疑って時間を溶かしやすい。

**確かめ方**: 実行後に SRAM の中身を読む。$ED0000 が
`82 77 36 38` になっていれば IPL-ROM に書き戻されている。
自分で書いた値が残っていればマジックは受理されている。

## 12. 推測でデバイスのビットを組み立てない

SASI のプロトコルを SCSI の一般的な仕様から類推して実装したが、
レジスタの位置もフェーズの値も転送方向も**すべて違っていた**。

| 推測した内容 | 実際 |
|---|---|
| セレクションは `$E96001` へ書く | `$E96007` |
| コマンドフェーズは `$07` | `$0B` |
| ステータスは `$03` | `$0F`、メッセージは `$1F` |
| DMAC の OCR bit7 は「メモリ → デバイス」 | 「デバイス → メモリ」 |
| データ転送は CPU が読む | DMAC 経由 |

**IPL-ROM が実際に比較している値を読む方が速い。** ROM を逆アセンブルして
`AND.B #$1F` の直後の `CMP.B #$xx` を拾えば、待たれている値がそのまま出る。

詳細は [X68000 の SASI 起動経路](x68000-sasi-boot.md) にまとめた。

## 13. 「ブートセクタ」は LBA 0 とは限らない

X68000 の SASI 起動では、識別子 `"X68K"` は **LBA 4** にあり、
実行されるブートコードは **LBA 0** にある。しかも先頭バイトは
`$60` (BRA) でなければ実行されない。

「ブートセクタ = LBA 0」と思い込むと、LBA 0 に識別子を置いてしまい、
IPL-ROM は LBA 4 を見るので永遠に一致しない。

**確かめ方**: `--trace-disk` でどの LBA が読まれたかを見る。
`read lba=4 count=1` だけで止まっていれば識別子が合っていない。
`read lba=0 count=4` まで来ていれば識別は通り、ブートコードの
内容が問題。

## 14. IOCS 番号は「近くにあるルーチン」から推測しない

**症状**: IOCS `$FF` を「無害なワーククリア」と判断して握り潰したところ、
本当のエラーが握り潰されて、原因が分からないまま先へ進んだように見える。

**原因**: ROM をアドレス順に眺めて「この番号はこのルーチンだろう」と
当たりを付けたのが誤り。この ROM では `$FF058E` と `$FF059A` が
12 バイトしか離れていないが、番号は `$FF` と `$FD` で別物。

**確かめ方**: 推測せずベクタテーブルを引く。IOCS のコールベクタは
`$000400` から 4 バイト刻みなので、**番号 n の実体は `$000400 + n*4`**。
IPL-ROM は `$FF1B32` からの 224 エントリを `$000400` へコピーし、
そのあと末尾 3 本を個別に上書きしている。

```
FF002E: 23FC 00FF058E 000007FC   ; ($7FC-$400)/4 = $FF
FF0038: 23FC 00FF01B6 000007F8   ; = $FE
FF0042: 23FC 00FF059A 000007F4   ; = $FD
```

同じ理由で、`$FF6032` を「IOCS `$00` の入口」と書いていたのも誤り。
入口はテーブルが指す `$FF32BA` で、`$FF6032` はその中から呼ばれる下請け。

番号ごとの実体と、この読み違えで何が起きたかは
[SASI 起動経路](x68000-sasi-boot.md#iocs-ff-は踏んではいけない過去-2-回書き間違えた)
にまとめてある。

**教訓**: ROM のアドレスの近さは番号の近さを意味しない。
1 本ずれたまま「訂正した」と思い込むのが一番たちが悪い。

## 15. 分岐先はバイト境界を合わせてから読む

**症状**: `$FF42BC` の `BNE` の飛び先を `$FF430C` と読み、そこが
`4E75` なので「`RTS` するだけの無害な分岐」と結論した。実際の飛び先は
`$FF430E` で、`RTS` ではなくキーボード処理の待ちループだった。

**原因**: 分岐変位の足し算をずらした。`$FF430C` の `4E75` は
**手前のルーチンの終端**で、そこから 2 バイトずれた `$FF430E` が
本当の飛び先。68000 の命令は可変長なので、1 命令ずれて読むと
まったく別の意味になる。

```
FF430C: 4E75            RTS              ← 手前のルーチンの終端
FF430E: 4A39 00000BC4   TST.B $000BC4    ← 本当の飛び先
FF4314: 66F6            BNE $FF430C
```

**見分け方**: 分岐変位は **「命令の次のアドレス」に足す**。
`BNE.S` (`66 xx`) なら「オペコードのアドレス + 2 + 符号付き xx」。
求めた飛び先が直前のルーチンの `RTS` を指していたら、たいてい
ずれている。逆アセンブラに通して境界を合わせるのが確実。

## 16. 例外フレームに積む PC は命令の種類で違う

68000 は例外の種類によって、スタックへ積む PC が違う。

| 例外 | 積む PC |
|---|---|
| TRAP / TRAPV / CHK / ゼロ除算 / 割り込み | **次の命令**のアドレス |
| 不当命令 / A-line / F-line / 特権違反 | **例外を起こした命令そのもの** |

一律で「次の命令」を積むと、後者が 1 ワードずれる。

**なぜ Human68k で致命的になるか**: Human68k は DOS コールを **F-line 命令**
(`.dc.w $FF00+n`) で発行する。F-line ハンドラ (`$8598`) は積まれた PC を
A5 に取り、`move.w (a5)+,d0` で**命令語そのものを読んで**コール番号を得る。
1 ワード先を積むと、後続の命令語をコール番号として読んでしまう。

実際に起きたこと: `$799E` の `$FF25` (`_INTVCS`) が、次の `$79A0` にある
`addq.l #$6,a7` (`$5C8F`) と誤読された。`$FF00` 未満なので「不正な DOS
コール」と判定され、不当命令ベクタ経由で Human68k のエラー処理へ落ちる。

**症状が原因から遠い**。見えるのは「中止＜Ａ＞ 再実行＜Ｒ＞ 無視＜Ｉ＞」
の画面で、これを起動メニューだと思い込むと延々別の場所を探すことになる。
実際にはエラー処理画面で、そこに来ている時点で例外が起きている。

**見分け方**: `$00F700` (Human68k のエラー処理) に到達しているかを数える。
到達していれば、その手前で何かの例外が起きている。`$11214` の Shift_JIS
文字列「エラー($xx)が発生しました(SR=$xx:PC=$xx)」が何を報告しているかも
手がかりになる。

## 17. 「転送が途中で止まったのに成功に見える」形のバグに注意

このプロジェクトで 3 回別々の場所で踏んだ。共通するのは
**転送量と完了通知が別々に管理されていて、途中で食い違う**こと。

| 場所 | 症状 |
|---|---|
| SASI の READ | 要求セクタ数を黙って切り詰め、`bufferLength` とずれた |
| DMAC | 1 バイトも転送できなくても完了ビット (COC) を立てた |
| FAT の配置 | HUMAN.SYS の生コピーと領域が重なり、中身が壊れた |

どれも「転送は完走した」ように見えるので、原因が転送側にあると気づけない。
DMAC の例では転送量もアドレスも正しく、読み込んだ先の中身だけが違った。

**予防**: 完了を通知する側は「要求ぶん全部転送できたか」を条件にする。
切り詰めや打ち切りが起きたらエラーを返す。黙って減らさない。

**見つけ方**: 転送先のメモリと、元のファイル・イメージの同じ位置を
突き合わせる。3 者 (メモリ / ファイル / イメージ) を比べると、
読み込みの問題かイメージ生成の問題かが分かれる。

## 起動の進み方を測る目安

実測値（EXPERT 用 IPL-ROM v1.0、HDD なし）。ここより手前で止まったら
上記のどれかを疑う。

| 到達点 | 命令数の目安 | 関連するアドレス |
|---|---|---|
| IOCS ベクタテーブルの初期化 (256 エントリ) | 約 780 | `$FF0510` |
| テキスト VRAM のクリア開始 | 約 3,800 | `$FFABC0` |

## デバッグの道具立て

`host/main.cpp` (`just run`) に用意してある。

- `--trace-last N`: 停止直前の N 命令だけを出す。全トレースは数百万行に
  なって使えないが、止まった理由は直前の流れに出る。
- `--stats`: 実行した命令を上位 4bit のグループごとに数える。
  どの命令群が使われているかで、実装の優先順位を決められる。
- `--ppm PATH`: テキスト画面を PPM で書き出す。依存ライブラリが要らない。
- `--dump-text`: テキスト画面を ASCII に逆引きして出す。画像を見ずに
  「何が表示されているか」を機械的に確かめられる。

### 実機の画面は VRAM から読み戻せる

実機のデバッグで最初に困るのは「LCD に何が出ているか分からない」こと。
写真を撮ってもらう以外の手が無いと、確認のたびに人の手が要る。

テキスト画面はビットマップなので「どの文字が書かれたか」は VRAM を見ても
直接は分からないが、**CGROM の 8x16 ANK 字形と 1 セルずつ照合すれば逆に
引ける** (`src/x68k/core/video/text_scrape.cpp`)。ANK は 256 通りしかなく、
総当たりでも十分に速い。

これを USB シリアル経由で出す口を付けると、実機の画面をホストと同じように
テキストで確認できる。

```
 5|A>dir
10|HUMAN              SYS      58496
11|COMMAND            X        28382
```

16x16 の漢字は 2 セルにまたがるので ANK としては当たらない。どの字かまでは
分からなくてよく、「漢字が出ている」ことが分かれば CGROM が効いているかの
判断はつく。CGROM が無ければここが空白のままになる。

**Why not 画面を画像で送るか**: 768x512 のビットマップはシリアルには
大きすぎる。ASCII なら 1 行 96 バイトで済む。

### 実機へキーを送るときは押下と解放の間隔を空ける

MFP のキーボード受信は 1 バイトしか保持しない。押下 (`$xx`) と解放
(`$xx|$80`) を続けざまに書くと、CPU が読み出す前に上書きされて**入力が
丸ごと消える**。実効 3〜4MHz では 1 バイト読むのに数フレームかかる。

ホスト側 (`--keys`) は 200 万サイクルの間隔を空けている。実機でも同様に、
キューに溜めて数フレームおきに 1 イベントずつ送る必要がある。
「打ったのに何も起きない」ときは、まずここを疑う。

IPL-ROM が出力しようとしている文字列を読むと、エラーの内容が直接分かる
(Shift_JIS でデコードする)。文字列出力ルーチンは `$FF721E` で、
`A1` が文字列の先頭を指す。

### 詰まったときの手順

実際にこの順で原因へ辿り着いた。

1. **`--trace-last` で止まった位置を見る。** 同じアドレスが並んでいれば
   ポーリングループ。3〜4 命令の繰り返しなら、その中の `MOVE.B (xxx).L,Dn`
   が待っている I/O。

2. **ROM をダンプして絶対アドレスを読む。** `1039 00E9 4001` なら
   `$E94001` を読んでいる。どのデバイスかはメモリマップで引く。

3. **何を待っているかを読む。** `BTST #n` なら bit n、`AND.B #$xx` +
   `CMP.B #$xx` なら複数ビットの組み合わせ。

4. **その値を返すよう直す。** ただし「完全に応答する」と誤認されて先へ
   進みすぎることがある (FDC がまさにそれ)。ポーリングの条件を全部読んで
   から決める。

5. **エラー停止ループ (`$FF0598`) に来ていないか確認する。** 来ていたら、
   その手前の `BSR` が出力しようとした文字列を読む。エラーの内容が分かる。

### 実行領域の集計が効く

どのアドレスが何回実行されたかを 1KB 単位で集計すると、どこで回っているか
が一目で分かる。ポーリングループは桁違いに多く実行される。

```
FF0400: 10293068 回   ← ウェイトループ
FF1000:  7980105 回   ← 割り込みハンドラ
FF0C00:   787924 回
```
