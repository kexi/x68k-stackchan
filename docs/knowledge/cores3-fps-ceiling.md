# 何が律速していたか

実機 CoreS3 で fps が 20.8 から動かなかった。ゲスト側を 4bit にして
描画を 360,768 -> 81 cycles にしても 20.8 のままだったので、
ゲストでも合成でもないと分かっていた。

Core0 (表示コア) を計測して分解した。5 秒間:

| 項目 | 時間 | 占有 |
| --- | ---: | ---: |
| LCD 転送 (pushFrame) | 3,291.8ms | 65.8% |
| M5.update + キー + コンソール | 76.4ms | 1.5% |
| **vTaskDelay と顔処理** | **1,631.8ms** | **32.6%** |

ループは 5 秒で 204 周しか回らず、そのうち転送できたのは 102 枚。
**残り 102 周は「フレームが無い」ので 16ms 眠っていた。**

  102 枚 x 32.3ms + 102 回 x 16ms = 4,927ms ≒ 5,000ms

と辻褄が合う。**5 秒のうち 1.6 秒 (32%) を寝て過ごしていた。**

# 直し方

`vTaskDelay(pdMS_TO_TICKS(16))` を `vTaskDelay(1)` にする。1 行。

LCD 転送は 1 枚 32.3ms かかり、その間に Core1 は次のフレームを作り終えて
いる。16ms 眠ると、出来上がっているフレームを取りに行くのが遅れる。

完全に消さないのは、1 tick も譲らないと idle task が走れずウォッチドッグが
鳴るため。1 tick (1ms) なら譲りつつ待ちは最小になる。

**実機で 20.8 -> 26.6fps。** 転送枚数は 5 秒で 102 -> 133 枚に増えた。

# 残る壁は 31fps。これは構成上の上限

転送 1 枚 32.2ms は変わらない。逆算すると実効 38.2MHz で、
CoreS3 の ILI9342C を 40MHz で駆動したときのほぼ上限にあたる。
SPI クロックを上げる余地は無い。

時間は `pushImageDMA` の**中**にある。`waitDMA()` を後ろから外して
非同期化を試したが fps は変わらなかった (26.58 -> 26.56、誤差)。
待ちではなく変換が支配的だという証拠なので、この変更は戻した。

変換が要るのは `setSwapBytes(true)` のため。フレームバッファは PSRAM に
あり、M5GFX 0.2.26 は PSRAM から直接 DMA できない (ESP32-S3 の
`esp_cache_msync` を持たない) ので、内部の DMA 可能バッファへ画素を
写してから送る。このコピーが 32.2ms である。

内部 RAM へ置ければ変換は要らなくなるが、**入らない**:

- フレームバッファ 1 枚 320x240x2 = 153,600 byte、2 枚で 300KB
- 実機の内部 RAM 空き **49,619 byte** (最大ブロック 31,744)

**訂正**: ここで「30fps には 33.3ms 以内が要るところ 32.2ms しか余裕が無く
ぎりぎり」と書いたのは誤りである。32.2ms は 33.3ms より**短い**ので、
転送時間の側は 30fps を妨げていない。1.1ms の余裕がある。
上限は 31.0fps で、30fps はその内側にある。

届いていない理由は転送ではなく、**フレームバッファが 2 枚しかないこと**である。

Core0 は転送中の 32.2ms のあいだ 1 枚を掴んだままになる (`isFrontInUse_`)。
残る 1 枚に Core1 が書いても、front が使用中のうちは publish できない。
実測で backpressure が 490 回/5秒 立っており、Core1 は 1 枚 2.43ms で
描けているのに置き場所が無くて待っている。

その結果 1 枚あたり 37.6ms かかっている (転送 32.2ms + 隙間 5.4ms)。
この 5.4ms は「転送が終わってから次を publish するまで」の往復である。

## 効かなかった対策 (記録)

- **RenderBudget の interval を 33,333 -> 25,000us**: 26.6fps のまま変わらず。
  生産周期が律速ではなかった。33,333 へ戻した。
- **転送直後に眠らない**: 26.6fps のまま。空振りはむしろ 569 -> 771 回へ増えた。
  転送から戻った時点で次の 1 枚が用意できていないため。
- **waitDMA の非同期化**: 26.58 -> 26.56fps。時間は待ちではなく
  `pushImageDMA` の中の変換にある。

## 30fps へ届かせるには

フレームバッファを **3 枚**にする。転送中でも Core1 が書いて publish できる
ようになり、隙間の 5.4ms が埋まって 31.0fps まで出せる。

PSRAM は 3.7MB 空いており 1 枚 150KB は入る。ただし `FrameChannel` は
`writeBuffer_` / `frontBuffer_` の 2 変数で 2 枚を前提にしており、
`TiledCompositor` も buffer index 0/1 で世代を持つ。両方の不変条件を
触る変更になる。

余裕は 1.1ms (3.4%) しかないので、転送が 1 度でも遅れれば 30 を割る。

# 3 枚化の試行と、実機が応答しなくなった件 (2026-09-07)

上記の方針どおり 3 枚化を実装し、ホストテストは全て通した。しかし実機へ
書き込んだところ**シリアル出力が一切出なくなり、esptool でも接続できなく
なった** (`No serial data received`)。ポートは列挙されたままなので、
USB-serial は生きていてアプリだけが起動に失敗していると見ている。

`develop-stack-chan` の「通信が失われたら書き込みを止める」規則に従い、
リトライを止めた。**原因は特定できていない。**

## 実装した内容 (ホストテストは通過)

- `FrameChannel` を 3 スロットのリングへ。各枚が Free / Writing / Ready /
  InTransfer のどれか 1 つを持つ状態機械にした
- `TileGenerations::kBuffers` を 2 -> 3
- 3 枚目を PSRAM へ確保し、compositor の buffer 添字を 3-way の探索にした
- テストを 5 件追加。「転送中でも次の 1 枚を書ける」「公開待ちが複数ある
  ときは古い方から渡す」「3 枚すべて埋まったら貸せない」など

パッチは `/tmp/x68k-backup-20260907/triple-buffer.patch` と
`git stash@{0}` の両方に保持している。

## 原因として調べたが否定されたもの

- **PSRAM 不足**: 起動直後の空きは 8.4MB。1 枚 150KB は問題にならない
- **TileGenerations の肥大**: `buffers_` は 2,400 -> 3,600 byte の +1.2KB
  だけで、しかも実体は PSRAM 上に置かれる
- **JIT スロットの確保失敗**: 40,960 byte を内部 SRAM に要求し、reserve 後の
  最大連続空きは 31,744 しかない。ただし取れなければ半分へ落とす
  フォールバックがあるので、これだけでは起動不能にならないはず

## 次に確かめること

電源を入れ直して復旧させたうえで、

1. まず `app-before.bin` (退避済み、4,194,304 byte) を書き戻して 26.6fps の
   状態に復帰させる
2. 3 枚化を**段階的に**入れる。まず `kBuffers` だけ 3 にして起動を確認し、
   次に FrameChannel を差し替える。一度に両方入れたので切り分けができていない
3. 起動ログの `[mem:after reserve]` を見て、内部 SRAM の空きが 3 枚化の前後で
   どう変わるかを実測する

**一度に 2 つの変更を入れたことが、切り分けを不可能にした。** 実機で試す
変更は 1 つずつにする。


# 到達 (2026-09-07): 実機 30.6fps

3 つを順に直して届いた。**どれか 1 つでは届かない。**

| 段 | 変更 | fps |
| --- | --- | ---: |
| 0 | (開始時) | 20.8 |
| 1 | Core0 の待ちを 16ms -> 1 tick | 26.6 |
| 2 | フレームバッファを 2 -> 3 枚 | 27.4 |
| 3 | 転送直後は眠らず続けて送る | 27.8 |
| 4 | 生産周期 33,333 -> 25,000us | **30.6** |

段 4 は以前**単独で試して効かなかった**。当時はバッファが 2 枚で
backpressure が 490回/5秒 立っており、そちらが真の律速だったため。
3 枚にして backpressure=0 になって初めて、生産周期が律速に浮上した。

**順序が意味を持つ。** 効かなかった対策を「効かない」と結論づけるのは、
その時点の律速に隠されていただけかもしれない。

## 最終的な内訳

- LCD 転送 32.29ms/枚 (これが律速。31.0fps が理論上限)
- 転送以外の Core0 の仕事 0.017ms (ほぼゼロ)
- backpressure 0 (Core1 は待っていない)

30fps に必要な 33.33ms に対し、転送 32.29ms + 0.017ms で収まっている。

# 16bit high-color も 30fps だった (2026-09-07)

4bit の 30fps 到達後、16bit でも測ったところ **30.6fps** だった。
追加の最適化は要らなかった。

| モード | fps | ゲスト速度 |
| --- | ---: | ---: |
| 4bit | 30.6 | 9.84 MHz |
| **16bit high-color** | **30.6** | 4.8-5.5 MHz |

2 回の測定で 30.79 / 30.73 / 30.58 / 30.59 fps。画面は目視で高色の
ゲームプレイ (写実的な山・空) を確認した。

## なぜ「16bit は届かない」と考えたのが誤りだったか

ホスト計測で 16bit のゲストは 410,056 cyc/frame かかる。vsync 階段では
N=3 に落ちるので、**ゲスト自身のフレームレートは 18.48fps** である。
ここから「16bit は 30fps に届かない」と考えたが、これは誤りだった。

**エミュレータはゲストのフレーム完成を待たない。** Core1 は自分の周期
(RenderBudget 25,000us) で GVRAM の *現在の内容* を合成し、Core0 が LCD へ
送る。ゲストが 1 フレームを描き終えていなくても送る。

したがって:

    ゲストのフレームレート ≠ デバイスの表示フレームレート

デバイスは GVRAM の現状を 30fps で映しているだけである。ゲストが遅ければ
同じ絵が 2 回映るだけで、表示レートは落ちない。

**律速は両モードとも LCD 転送 32.3ms で、そこは色数と無関係。**
だから 4bit も 16bit も同じ 30.6fps になる。

## 教訓

「ゲストが 1 フレームを何 cycle で描くか」と「画面が 1 秒に何回書き換わるか」は
別の量である。前者から後者を導く前に、両者を繋ぐ経路 (ここでは FrameChannel と
RenderBudget) が同期しているのか非同期なのかを確かめること。
