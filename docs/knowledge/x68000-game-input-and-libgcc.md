# X68000 で自作ゲームを書くときに詰まる 4 つ

[gcc-to-human68k-x.md](gcc-to-human68k-x.md) の続き。`.X` が動くように
なった後、**ゲームらしいことをしようとして**詰まった箇所。

## 1. IOCS のキー入力は「待つ」ので毎フレーム呼べない

ゲームは毎フレーム「いま押されているか」を知りたい。ところが:

- **IOCS `_B_KEYINP` ($00)** — キーが来るまで戻らない。当然
- **IOCS `_BITSNS` ($04)** — 資料では「キーの押下状態をビットで返す」
  とされるが、**この IPL-ROM では待つ経路へ入る**。実地で確かめた

どちらも `$FF6032` のループへ入って戻ってこない。

```
FF6032: 6116        BSR $FF604A
FF6034: 4840        SWAP D0
FF6036: 67FA        BEQ $FF6032      ; 0 の間ずっと回る
...
FF604A: 4280        CLR.L D0
FF604C: 4A79 000812 TST.W $000812    ; キーバッファの残数
FF6052: 671C        BEQ (0 を返して戻る)
```

**症状**: ゲームが起動して初期化まで通るのに、最初のフレームから
先へ進まない。トレースを見ると PC が ROM 内 (`$FF60xx`) にあり、
自分のコードのアドレスが出てこない。

### 直し方: IOCS のキーバッファを直接読む

IOCS の受信割り込みが積んだ先を、待たずに舐める。配置は
[x68000-sasi-boot.md](x68000-sasi-boot.md) の 9 節に実測がある。

| アドレス | 用途 |
|---|---|
| `$000812` | 残数 (word) |
| `$000814` | 書き込み位置 (long) |
| `$000818` | 読み出し位置 (long) |
| `$00081C` | バッファの先頭。`$00089C` で折り返す |

1 要素 2 バイトで、**上位バイトにスキャンコード**が入る。
キーボードは押下でスキャンコード、離鍵で **bit7 を立てた**同じコードを送るので、
バッファを空になるまで舐めて押下状態の表を更新すればよい。

```c
for (int guard = 0; guard < 64; ++guard) {   // 上限は付ける (下記)
    const uint16_t count = peek16(0x000812u);
    if (count == 0) return;

    uint32_t rp = *(volatile uint32_t *)0x000818u;
    rp += 2;
    if (rp >= 0x00089Cu) rp = 0x00081Cu;      // IOCS 側と同じ折り返し

    const uint8_t code = (uint8_t)(peek16(rp) >> 8);
    *(volatile uint32_t *)0x000818u = rp;
    poke16(0x000812u, (uint16_t)(count - 1));

    s_down[code & 0x7F] = (code & 0x80) ? 0 : 1;   // bit7 = 離鍵
}
```

**上限を付ける理由**: 残数と読み出し位置は IOCS の受信割り込みも触る。
こちらが減らしている最中に割り込みが増やすと、条件次第で抜けられなくなる。
バッファは 64 要素なので、それを超えて回るのは何かがおかしいとき。

**Why not MFP の UDR ($E8802F) を直接読むか**: IOCS の受信割り込みが
先に読んでしまうので、こちらには回ってこない。

## 2. `%` と `/` が libgcc を呼び、-nostdlib のバイナリで落ちる

68000 に **32bit の除算命令が無い** (`DIVU`/`DIVS` は 32÷16)。gcc は
`__divsi3` / `__modsi3` / `__umodsi3` を呼ぶ。

`-nostdlib` でリンクすると undefined reference になるので libgcc を
足したくなるが、**足しても落ちる**。

**症状が原因から遠い**: 落ちるのは除算そのものではなく、その先。
「10 進に直して画面に出す」ような、一見なんでもない関数を呼んだ瞬間に
戻ってこなくなる。除算を書いた自覚が無いので原因に辿り着きにくい。

実際に踏んだ形:

```c
static void put_num(char *buf, int value, int digits) {
    for (int i = digits - 1; i >= 0; --i) {
        buf[i] = (char)('0' + (value % 10));   // ← __modsi3
        value /= 10;                            // ← __divsi3
    }
}
```

`frame % 30`、`frame % 10000` のような何気ない剰余も同じ。

### 直し方: 除算を書かない

桁数がたかだか 4 桁なら引き算で足りる。

```c
static const int kPow10[5] = {1, 10, 100, 1000, 10000};
for (int i = 0; i < digits; ++i) {
    const int unit = kPow10[digits - 1 - i];
    int d = 0;
    while (value >= unit && d < 9) { value -= unit; ++d; }
    buf[i] = (char)('0' + d);
}
```

「N フレームごと」も剰余ではなくカウンタで数える。

**見つけ方**: リンク時の undefined reference に `__divsi3` / `__modsi3` /
`__umodsi3` / `__udivsi3` が出たら、そこが候補。出ないようにするために
libgcc を足すと、症状が実行時へ移るだけで解決しない。

## 3. GPIP4 は垂直帰線中に **L** になる (アクティブ L)

MFP の GPIP bit4 が垂直帰線。**帰線中は 0** で、表示中が 1。

```cpp
// src/x68k/core/dev/mfp.cpp:328
if (active) {
    reg_[kGpip] = static_cast<u8>(before & ~kGpipVDisp);   // 帰線中は L
}
```

逆に読むと「いつまでも来ない帰線」を待ち続けて固まる。しかも
**トレースの PC が自分のコードの中を指す**ので、原因が絞りやすいようで
「なぜこのループから出ないのか」に見えて時間を使う。

```c
static int in_vblank(void) {
    return (peek8(0xE88001u) & 0x10u) == 0;   // 0 のときが帰線中
}
```

**待つ側には上限を付ける。** 1 フレームぶんの仕事が重くなると、呼んだ
時点で既に帰線を通り過ぎていることがある。上限が無いと次の帰線まで
丸ごと待つか、条件次第で抜けられない。落ちるより 1 フレーム飛ばす方がよい。

## 4. テキスト/スプライトパレットは 16 色しか無い

実機は 16 色 x 16 ブロックだが、**このエミュレータは 16 色だけ**
(`video.h` の `kTextPaletteCount = 16`)。

パレットブロック 1 を使うつもりで `$E82200 + 16*2` へ書くと、
**折り返してブロック 0 を壊す**。実際にこれで画面全体が灰色になった。
絵は正しく出ているのに色だけが全部同じになるので、
「描画が壊れた」と思い込むと合成やパターン定義の側を疑ってしまう。

同じ絵の色違いが要るなら、**パターンを分ける**。PCG は 256 個あって
たいてい余っている。直し方は `sprite_raster.h:12-24` にある。

## 5. `--dump-text` で読むなら数字だけにする

`--dump-text` はテキスト画面のセルを CGROM の字形と照合して ASCII へ
逆引きする。CGROM が無い環境では IPL-ROM 内蔵の 6x12 で代替されるが、
**そこに字形が無い文字は落ちる**。`X=` のようなラベルを入れると、
落ちた分だけ桁がずれて機械で切り出せなくなる。

数字と空白だけの固定長で出すと確実に読める。

```
0120 0168 1 1 0030     <- world_x, y, on_ground, alive, frame
```

なお自前のビットマップをテキスト VRAM へ直接書くのは**うまくいかない**。
逆引きは CGROM の字形との一致で判定するので、自作の字形は全部 `#` になる。
DOS `_PRINT` で実物の IOCS に描かせるのが確実。
