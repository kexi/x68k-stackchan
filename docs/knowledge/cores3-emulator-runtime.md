# CoreS3 実機でエミュレータを動かすときの知見

ホストで動いたエミュレータをそのまま実機へ持っていくと、**ホストでは
起きない種類の問題**にぶつかる。実際に踏んだものだけを記録する。

## 1. `taskYIELD()` ではウォッチドッグから逃げられない

エミュレーションのホットループで CPU を明け渡すとき、`taskYIELD()` を
毎スライス呼ぶとリセットのループに入る。

**理由**: `taskYIELD()` は同じ優先度のタスクへ譲るだけで、**アイドル
タスクは優先度 0 なので回ってこない**。ESP-IDF のタスクウォッチドッグは
アイドルタスクが一定時間走らないことを検出して落とすので、譲っている
つもりでも殺される。

**直し方**: `vTaskDelay(1)` を使う。これはブロック状態に入るので
アイドルタスクが走れる。

```cpp
g_machine.run(kSliceCycles);
vTaskDelay(1);   // taskYIELD() ではだめ
```

**代償**: `vTaskDelay(1)` は最低 1 tick 待つ。速度が要るなら
「N スライスに 1 回だけ待つ」形にする。

**注意 (2026-08-04 追記)**: 「既定 10ms なので実効 2MHz が上限」という
記述が長く残っていたが、本プロジェクトの `sdkconfig.defaults` は
`CONFIG_FREERTOS_HZ=1000` を設定済みで **tick は 1ms**。20000 サイクルの
スライスなら delay 由来の上限は 20MHz であって、2MHz ではない。
tick を短くする手は既に打ち終わっている。実際の律速は下の 8 節にある
とおりインタプリタ本体で、delay の寄与は 16% ぶんしかない。

### リセットループに入ると書き込めなくなる

繰り返しリセットしている間は esptool が接続できない。

```
A fatal error occurred: Failed to connect to ESP32-S3: No serial data received.
```

**USB ケーブルを抜き差しする**のが最も確実。CoreS3 のリセットボタンの
長押しは**電源オフ**であって、ダウンロードモードではない。

## 2. 実機の画面は VRAM から読み戻せる

実機のデバッグで最初に困るのは「LCD に何が出ているか分からない」こと。
写真を撮ってもらう以外の手が無いと、確認のたびに人の手が要る。

テキスト VRAM はビットマップなので「どの文字が書かれたか」は直接には
分からないが、**CGROM の 8x16 ANK 字形と 1 セルずつ照合すれば逆に引ける**。
ANK は 256 通りしかなく、総当たりでも十分に速い。

これを USB シリアルへ出す口を付ければ、実機の画面をホストと同じように
テキストで確認できる。

```
 5|A>dir
10|HUMAN              SYS      58496
11|COMMAND            X        28382
```

16x16 の漢字は 2 セルにまたがるので ANK としては当たらない。どの字かまで
分からなくてよく、「漢字が出ている」ことが分かれば CGROM が効いているかの
判断はつく。

実装は `src/x68k/core/video/text_scrape.cpp`。core 側に置いてあるので
ホスト (`--dump-text`) と実機で同じコードが動く。

## 3. シリアル入力は VFS ではなくドライバを直接叩く

シリアルからキーを受け取りたいとき、`getchar()` は既定でブロックする。
入力待ちで画面更新ごと止まるので、非ブロッキングにする必要がある。

**やってはいけない**: `fcntl(fileno(stdin), F_SETFL, O_NONBLOCK)`。
これを入れたところ**ログ出力まで巻き添えで止まった**。VFS 側の口が
塞がるらしく、`ESP_LOGI` も `printf` も出なくなり、実機が生きているのか
死んでいるのかも分からない状態になる。

**正しくは**: USB Serial JTAG ドライバから直接読む。

```cpp
usb_serial_jtag_driver_config_t cfg = USB_SERIAL_JTAG_DRIVER_CONFIG_DEFAULT();
usb_serial_jtag_driver_install(&cfg);

std::uint8_t buf[32];
const int n = usb_serial_jtag_read_bytes(buf, sizeof(buf), 0);  // timeout 0
```

`CMakeLists.txt` の `REQUIRES` に `esp_driver_usb_serial_jtag` が要る。

**出力は VFS のままにしておく**。両方をドライバに寄せると `ESP_LOG` の
行が混ざって読めなくなる。

## 4. キーは押下と解放の間隔を空けて送る

MFP のキーボード受信は 1 バイトしか保持しない。押下 (`$xx`) と解放
(`$xx|$80`) を続けざまに書くと、CPU が読み出す前に上書きされて**入力が
丸ごと消える**。

実効 3〜4MHz では 1 バイト読むのに数フレームかかる。キューに溜めて
数フレームおきに 1 イベントずつ送る。

```cpp
// 押下 → 4 フレーム待つ → 解放 → 4 フレーム待つ → 次の文字
```

「打ったのに何も起きない」ときは、まずここを疑う。ホスト側の `--keys` も
200 万サイクルの間隔を空けている。

## 5. PSRAM のバッファを pushImageDMA に直接渡してはいけない

**症状**: 転送しても LCD が更新されない。にもかかわらず古い画面は表示され
続ける。`fillScreen` も効かない。

M5GFX (0.2.26 で確認) は、入力と出力がどちらも RGB565 だと「変換不要」と
判断し、**渡したポインタをそのまま SPI の DMA descriptor に設定する**。

```cpp
// Panel_LCD.cpp
if (param->no_convert) { write_bytes(src, wb * h, use_dma); }

// Bus_SPI.cpp の _setup_dma_desc_links
dmadesc->buf = (uint8_t*)data;   // DMA 可能メモリかの判定なし
```

この経路には次のどれも無い。

- `esp_ptr_dma_capable()` などの判定
- DMA 非対応時のバウンスバッファ
- ESP32-S3 向けの `esp_cache_msync()` (ESP32-P4 の `#if` 内にしかない)

ESP32-S3 は PSRAM DMA 自体には対応しているが、**CPU キャッシュと PSRAM の
同期はハードウェアが保証しない**。同期を挟まないと、CPU がキャッシュへ
書いた内容と GDMA が PSRAM から読む内容が食い違う。

**「古い画面だけ残る」理由**: 320x240x2 = 150KB はデータキャッシュ (64KB)
より大きいので、描画中のキャッシュ追い出しで偶然まとまったフレームが
PSRAM へ書き戻されることがある。それが最後に成功した転送として LCD の
GRAM に残り続ける。LCD は次の書き込みが来るまで内容を保持するので、
以後の転送が失敗しても画面は消えない。

**直し方**: `setSwapBytes(true)` を呼ぶ。変換が入ると M5GFX は内部の
`MALLOC_CAP_DMA` バッファへ画素を写してから送るので、PSRAM を直接
DMA する経路に入らない。

```cpp
M5.Display.setColorDepth(16);
M5.Display.setSwapBytes(true);   // これが無いと PSRAM を直接 DMA する
```

**Why not `esp_cache_msync` を自分で呼ぶか**: M5GFX の DMA 経路は外部 RAM
判定もエラー処理も持たないため、同期しても descriptor の扱いは変わらない。
内部バッファに寄せる方が確実。

**この症状の見分け方**: フレームバッファの中身をシリアルへ吸い出して
確かめられるようにしておくと切り分けが速い。「バッファは正しいのに
LCD が違う」と分かった時点で、描画ロジックではなく転送経路を疑える。
実際、これが分かるまで回転・座標・`fillScreen` を何度も疑って外した。

## 6. LCD は 320x240。等倍では読めない

Human68k の標準コンソールは 768x512、CoreS3 の LCD は 320x240。

等倍で左上を切り出すと 40 桁 x 15 行が入る。**桁数は稼げるが、2 インチの
画面に 8x16 ドットの文字が出るので実際には判読できない。**

2 倍に拡大すると 20 桁 x 7 行と狭くなるが、16x32 になって読める。
どちらが良いかは用途によるので、切り替えられるようにしておく。

**拡大時はダーティ行の追跡をやめて全画面を作り直す方が単純。** ダーティ
管理はテキスト VRAM のタイル行が単位で、拡大すると 1 タイル行が LCD 上の
複数行に伸びるため対応が煩雑になる。変換元が 1/zoom² に減るので、
全画面を作り直しても間に合う（等倍 3.8MHz → 2 倍 3.3MHz、13% の低下）。

## 7. メモリ配置の実測値

| 領域 | サイズ | 配置 |
|---|---|---|
| IPL-ROM | 128KB | **内部 SRAM**（ブート中の命令フェッチ元） |
| メインメモリ | 1MB | PSRAM |
| テキスト VRAM | 512KB | PSRAM |
| グラフィック VRAM | 512KB | PSRAM |
| CGROM | 768KB | PSRAM |
| フレームバッファ | 150KB | PSRAM |
| SASI 転送バッファ | 64KB 弱 | PSRAM |

起動直後の実測:

```
[mem:before reserve] internal free=300727 largest=241664 | psram free=8385100 largest=8257536
[mem:after  reserve] internal free=169651 largest=110592 | psram free=5280308 largest=5242880
```

**SASI の転送バッファは `Machine` に埋め込まないこと。** 埋め込むと内部
SRAM の `.bss` が 88KB まで膨らみ、その後 IPL-ROM 128KB を内部 SRAM へ
置こうとして失敗する。外から注入する形にして PSRAM に置く。SASI の転送は
DMA の完了待ちで一気に流すだけなので遅延に敏感ではない。

**外部注入にしたら `reset()` でポインタを消さないこと。** `sasi_ =
SasiState{}` のような初期化はポインタごと nullptr に戻す。ディスクが
1 セクタも読めなくなり、原因が分かりにくい。

## 8. 実効速度の実測

| 条件 | 実効クロック | 実機比 |
|---|---|---|
| 等倍表示 + ダーティ転送 | 3.8MHz | 38% |
| 2 倍拡大 + 全画面転送 | 3.3MHz | 33% |

いずれも `vTaskDelay(1)` を毎スライス、スライス 20000 サイクル、
IPL-ROM を内部 SRAM に配置した状態。

### 譲る頻度を落とした結果 (2026-08-04、実機で実測)

メインメモリ 2MB 化とグラフィック画面の重ね合わせを入れた後の値。
CoreS3 に実際に書き込み、シリアルログの `実効 NNNN kHz` を読んだ。

| 条件 | 実効クロック | 実機比 |
|---|---|---|
| `vTaskDelay(1)` を毎スライス | **2760 kHz** | 27.6% |
| 8 スライスに 1 回 | **3195 kHz** | 32.0% |

+15.8%。3 回ずつ流して、いずれも起動直後から数十秒で上の値へ収束することを
確認した (起動直後は 1500-2000 kHz あたりから上がってくるので、
最初の数回の報告だけを見ると読み間違える)。

**なぜ毎スライス譲ると遅いか。** `vTaskDelay(1)` は最低 1 tick 待つ。
1 スライス 20000 サイクルの実時間が 6.1ms なので、tick が無視できない
割合を占める。譲る回数を 1/8 にすれば、そのぶんがそのまま速度になる。

**なぜ 8 か。** 譲る間隔 = 8 スライス x 6.1ms ≒ 49ms。ウォッチドッグの
5 秒に対して 100 倍の余裕がある。合成が最も重いとき (23.5ms/スライス) でも
235ms で 21 倍。N を増やしても速度は頭打ちで、余裕を削るだけ。

**譲る口自体は消してはいけない。** 上の「7. ウォッチドッグ」にある通り、
`taskYIELD()` で済ませようとしてリセットループに入った。アイドルタスクは
優先度 0 なので、ブロックしない限り回ってこない。

**停止中 (スライス 0) は毎周譲ること。** アバターモード等で
`g_allowedSliceCycles` が 0 のとき、数え上げだけで間引くと 8 周が一瞬で
終わり、譲らないまま空回りする。これは `taskYIELD()` で踏んだのと同じ
「アイドルタスクが回らない」状態になる。

190 秒の連続稼働で、リセットもウォッチドッグの警告も出ないことを確認した
(uptime が 201 秒まで単調増加し、`rst:` が 1 度も出ない)。

### バスの仮想呼び出しを迂回した結果 (2026-08-04、実機で実測)

| 条件 | 実効クロック | 実機比 |
|---|---|---|
| 8 スライスに 1 回譲る (前節) | 3195 kHz | 32.0% |
| **+ メイン RAM の fast path** | **3711 kHz** | **37.1%** |

収束後 25 回の報告の平均 (3672-3737 kHz)。

`Bus::read16` などは仮想関数で、命令フェッチとオペランドアクセスのたびに
vtable を経由していた。インライン化されないので、短い関数なのに呼び出しの
コストが乗る。メイン RAM に収まるアクセスだけを CPU 側の生ポインタで
直接読む経路を足した。

**Why not 全部を非仮想にしないか**: テストがバスの差し替えに依存している
(test_bus.cpp / test_m68k_vectors.cpp が test double を渡す)。仮想の口は
残したまま、最も回数の多いメイン RAM のアクセスだけを迂回させる方が、
テスト可能性を壊さずに効果の大半を取れる。

**目標 (実機比 50% = 5000 kHz) には届いていない。** 37.1% まで。

別のエージェントが同じ迂回を独立に実装して **3679 kHz** を実測しており
(2 実装の 3711 / 3679 は測定のばらつきの範囲)、この梃子の効き幅は
**+15〜16%** で再現すると見てよい。

### 「オペランドが PSRAM にある」という診断は、少なくとも起動中は誤り

上で「メイン RAM 2MB がデータキャッシュ 64KB に収まらないのが律速」と
書いていたが、**アクセス位置を実際に数えたら前提が崩れた。**

CPU のメモリアクセスに 1 個ずつ印を付けて数えた (計測コードは一時的に
入れて外した)。IPL-ROM の起動から 2 億サイクル、アクセス 5719 万回:

| 領域 | 回数 | 割合 |
|---|---|---|
| **IPL-ROM** ($FE0000-) | 45218456 | **79.06%** |
| メイン RAM ($000000-$1FFFFF) | 10144085 | 17.74% |
| I/O ($E80000-$EBFFFF) | 1610981 | 2.82% |
| T-VRAM | 215936 | 0.38% |
| CGROM | 2432 | 0.00% |

**アクセスの 8 割は IPL-ROM で、これは既に内部 SRAM に置いてある。**
PSRAM を待っている場面は思っていたより遥かに少ない。

さらにメイン RAM の 17.74% は、その **全部が $000000-$00FFFF に入る**。
1KB 刻みで見るともっと狭い:

| 範囲 | RAM 内での割合 | 中身 |
|---|---|---|
| $01C00-$01FFF | **63.09%** | スーパーバイザスタック (SSP=$002000 の直下) |
| $00800-$00BFF | **35.09%** | IOCS ワーク |
| $00400-$007FF | 1.81% | IOCS コールベクタ |
| その他 | 0.01% | |

**実際に触られているメイン RAM は 3KB 弱しかない。** データキャッシュは
64KB あるので、この作業集合は最初から丸ごと収まっている。

**したがって「ゼロページと Human68k のワークを内部 SRAM へミラーする」
(Lead 2) は、起動中に関しては効かないと予測できる。**移し替える先の
3KB は既にキャッシュに載っており、PSRAM まで読みに行っていない。
IRAM 配置が効かなかったのと同じ構図 (既に速い場所を速くしようとしている)。

**この予測は実機で未検証。** 測ろうとした時点で CoreS3 が
esptool に応答しない状態になり (下の「書き込めなくなったとき」を見よ)、
USB を挿し直せる人が必要だった。次に触る人はまず Lead 2 を実測して、
この予測が当たっているかを確かめてほしい。**外れていた場合、
上の分布は起動中のものなので「Human68k のプロンプトに出てからは
RAM の比率が上がる」が説明になりうる**(プロンプト到達後の分布は
未計測。ディスクイメージがリポジトリに無く、ホストでは再現できない)。

### IPL-ROM も直接経路に載せた (実装済み・実機未計測)

上の分布から、最頻の行き先はメイン RAM ではなく **IPL-ROM (79%)** だと
分かったので、直接経路を ROM にも広げた (`M68k::setFastRom`)。
ROM は書けないので読み出しだけ。命令フェッチ (`refillPrefetch`) も
ここを通す。

これで「全アクセスの 79% + 17.7% = 約 97%」が仮想関数と
`SystemBus` の領域判定の両方を飛ばすことになる。

**実機での効果は未計測。** メイン RAM の迂回が +15.8% だったとき、
迂回できていたのは 17.7% ぶんだけだった。今回はその 4.5 倍の
アクセスを迂回するので、比例するなら大きいはずだが、
**比例する保証は無い** (ROM は既に内部 SRAM にあり、メイン RAM の
PSRAM 待ちとは事情が違う。効くのは仮想呼び出しと分岐を消した分だけ)。
ホストのテストと 68000 適合性テスト (127 スイート) は通っている。

残りを詰める候補:

- ディスパッチの構造そのもの (switch / 関数ポインタ表)
- ゼロページのミラー (上のとおり、起動中は効かない見込み)

### 1 スライスの内訳 (どこに時間が消えているか)

`esp_timer_get_time()` でスライスを区間に割って実測した (計測コードは
一時的に入れて外した)。定常状態 (プロンプト表示のまま放置) の
1 スライス = 20000 サイクル:

| 区間 | 時間 | 割合 |
|---|---|---|
| `Machine::run(20000)` | 5822us | 80% |
| `renderTo` | 273us | 4% |
| `vTaskDelay(1)` ほか | 1130us | 16% |

**律速はインタプリタ本体であって delay ではない。** 693 スライス中で実際に
描き直したのは 3 回だけなので、変換はほぼ効いていない (テキストだけの
コンソールはダーティが立たないと何もしない)。

この内訳から「delay を完全に無くしても 20000 / 6095us = **3.28MHz が上限**」
と計算できる。実測の 3200 kHz は既にこの上限へ張り付いており、
**delay 側の伸びしろは残っていない。**

### ホット命令の IRAM 配置は効かなかった

`step` / `execute` / `fetch` / メモリアクセス / 実効アドレス計算と、
実行頻度上位の命令グループ (misc 25.2%、分岐 22.3%、即値 13.8%、
MOVE 19.2% ほか。頻度はホストの `just run --stats` で採った) を
`.iram1` へ移した。IRAM の `.text` は 75219 → 85815 バイト (**+10.6KB**)、
DIRAM の残りは 213729 → 203133 バイト。

**速度は 2760 kHz のまま動かなかった。** 5 秒ごとの報告値がベースラインと
1 つずつ一致するほど完全に同じ。

**理由の見立て**: 命令キャッシュは 32KB
(`CONFIG_ESP32S3_INSTRUCTION_CACHE_32KB`) あり、インタプリタのホットループは
そこに収まっている。つまり元から Flash へ読みに行っていない。効いているのは
命令フェッチ側ではなく**オペランドが PSRAM にある**ことで、メインメモリ 2MB は
データキャッシュ 64KB に到底収まらない。コードをどこへ置いてもこの待ちは減らない。

印 (`X68K_HOT_PATH`) は残してある。IRAM は 200KB 余っていて害が無く、
SX-Window のように作業集合が広がる場面では効く可能性があるため。
**ただし「IRAM へ置けば速くなる」という期待は、この構成では実測で
否定されている。**次に触る人はまず上の内訳を採り直すこと。

### 50% (5MHz) に届かせるには

残るは `Machine::run` の 5822us を削る道しかない。1 スライスを 4000us まで
縮めれば 5MHz なので、**インタプリタを 1.46 倍速くする**必要がある。
効きそうな順に:

1. **ゼロページと Human68k のワーク ($0000-$2000) を内部 SRAM へミラー** —
   上の見立て (PSRAM のデータ待ちが律速) が正しければ、ここが最も直接効く。
2. **`Bus::read16` の仮想関数を外す** — 命令フェッチもオペランド読みも全部
   ここを通るのに `virtual` なので、間接呼び出しでインライン展開が効かない。
   `bus.h` は「将来 IRAM 配置の第一候補」と書いているが、上の結果からすると
   配置よりも**呼び出しの間接性を消す方**が効くはず。
3. スライスを 20000 より大きくする — delay は既に 1/8 なので上限 3.28MHz は
   動かない。伸びしろはほぼ無い。

進捗ログを定期的に出しておくと、**止まったのか遅いだけなのか**が
すぐ分かる。実機は画面を直接見られないので、この 1 行の価値が大きい。

```
I (50919) x68k: 147520000 サイクル実行 (実効 3314 kHz)
```

## 9. 音源を実機のスピーカーへ繋いだときの負荷 (2026-08-04、実機で実測)

YM2151 (OPM) と MSM6258V (ADPCM) を M5Unified のスピーカーへ繋いだ
(issue #8)。合成は Core1 (エミュレーション)、スピーカーへ流すのは
Core0 の専用タスク。

### コア割り当て

| 仕事 | コア | 理由 |
|---|---|---|
| 合成 (`Machine::renderAudio`) | Core1 | `Machine` の所有者。OPM のレジスタと ADPCM の FIFO は、ゲストが `$E90003` / `$E92003` へ書いている最中に変わる。別コアから読めば表示で避けたのと同じデータ競合になる |
| リング → `playRaw` | Core0 | Core1 はスライスの 80% を `Machine::run` に使っており、8 スライスに 1 回しか譲らない。ここに音声を置くと DMA が枯れる |
| I2S の背景タスク (`spk_task`) | Core0 (`task_pinned_core = 0`) | 既定の `~0` (任意) だとスケジューラが Core1 へ置きうる。同上 |

`stackchan-dapan` の「Wi-Fi/lwIP を Core0 に pin しないと音が途切れる」と
裏表の話。**詰まっているコアから音声を追い出す**のが要点で、本プロジェクトでは
詰まっているのが Core1 なので向きが逆になる。

受け渡しは `frame_channel.h` と同じ発想の固定長リング
(`platform/audio.h` の `AudioChannel`、512 サンプル x 4 枚)。
`Speaker_Class::playRaw` は**渡したポインタをコピーせず保持**し、しかも
前の 2 枚が再生待ちなら**空くまでブロックする** (`_set_next_wav`)。
エミュレーションのホットループから直に呼ぶと 68000 の実行が
スピーカーの再生速度に縛られるので、間にリングを挟む必要がある。

### 負荷 (待機中)

同じ起動の中で `'|'` を打って音源を ON/OFF し、5 秒ごとの
`実効 NNNN kHz` を読み比べた。焼き直さずに比べるのは、SD の中身や
PSRAM の割り付けといった起動ごとの差を混ぜないため。

| 条件 | 実効クロック (5 秒ごとの報告) | 平均 |
|---|---|---|
| 音源 ON | 3672 / 3676 / 3680 / 3709 / 3714 / 3716 / 3716 / 3724 / 3730 / 3735 / 3737 kHz | **約 3710 kHz** |
| 音源 OFF | 3695 / 3709 / 3709 / 3709 / 3709 / 3710 / 3711 / 3712 / 3728 / 3729 kHz | **約 3712 kHz** |

**差は 0.05% で、報告値のばらつき (±30kHz) に埋もれる。**
待機中の音源のコストは実測できない水準しかない。既定を ON にしてよい。

**なぜほぼゼロか。** `Machine::renderAudio` に「OPM の全スロットが無音で、
かつ ADPCM が停止中なら合成を省いてゼロで埋める」早期リターンを入れてある。
X68000 を触っている時間の大半 (起動中、コマンド入力待ち) はここを通るので、
Core1 が払うのは 512 サンプルのゼロ埋めだけになる。
`Opm::renderSamples` は元から同じ早期リターンを持つが、`renderAudio` は
FM と ADPCM を 1 サンプルずつ混ぜる都合で `renderOneSample` を呼ぶため、
その恩恵を受けられていなかった。

**鳴っている間のコストは未計測。** 上の値はすべて Human68k のプロンプトで
放置した状態のもので、実際に発音している区間の実効クロックは測れていない。

### 落とし穴: `playRaw` は失敗しても `true` を返す

`Speaker_Class::begin()` は既に走っていれば即 `true`、`_play_raw` は
`_task_handle` が無ければ何もせず `true` を返す (`Speaker_Class.cpp` の
`_play_raw` 1 行目)。`pin_data_out` が付いていない構成では
**「begin も playRaw も成功、しかし 1 サンプルも出ていない」**という
状態になり、ログ上は正常に見える。

判別には `isEnabled()` (= `pin_data_out >= 0`) と `isRunning()` を
両方確かめる。加えて、**1 秒あたりのブロック数**を出しておくと検算になる。
512 サンプル / 15625Hz なら正常は約 30 ブロック/秒で、桁違いに多ければ
`playRaw` が即戻っている。

CoreS3 の実測値は `pin_data_out=13 bck=34 ws=33` で、スピーカーは実在する。

### 出力レートは 15625Hz に揃える

OPM も ADPCM も既定の合成レートが 15625Hz なので、I2S 側も同じにする。
M5Unified の既定 (48000Hz) のままだと `playRaw` の内部でリサンプルが走る。
合成側を 48kHz へ上げるのは 3 倍のコストなので論外。

## 毎命令の呼び出しを削る (2026-08-04 実測)

USB が復活したので、ROM fast path 込みの状態を改めて計測し直した。

### 出発点の訂正

| | 実効 | 備考 |
|---|---|---|
| 旧記載 | 3711 kHz | 起動直後の揺らぎを拾った暫定値 |
| **再計測** | **3630 kHz** | 2 分・25 サンプルの定常値 |

起動直後は 1889 kHz から始まって 30 秒ほどで 3640 kHz に落ち着く。
短時間の計測は高めに出る。**定常値で比べること。**

### プロファイル

ホストで `sample` を 5 秒 (400M サイクル走行中)。`Machine::step` 配下
1942 サンプルの内訳:

| | サンプル | 割合 |
|---|---|---|
| `M68k::step` (CPU 本体) | 1366 | 70.3% |
| デバイス処理 (毎命令) | 576 | 29.7% |

`Machine::step` は 1 命令ごとに割り込み判定 3 回 + デバイス tick 3 回を
呼んでいた。平均 4 サイクルの命令に対して 6 回の関数呼び出し。

### 効いた変更

| 変更 | 実効 | 差分 |
|---|---|---|
| 出発点 | 3630 kHz | — |
| デバイス tick を quantum (8 サイクル) 単位へ | 4093 kHz | **+12.8%** |
| MFP の保留判定をインライン化 | 4200 kHz | **+2.6%** |
| SCC の保留判定をインライン化 | 4312 kHz | **+2.7%** |

合計 **+18.8%**。いずれも状態は完全に不変
(40746970 命令 / `$ED0000=82773638` / SR=270C)。

### ホストでは測れない

デバイス tick のまとめ込みは、**ホストでは 1.42s → 1.41s (誤差内)**。
ホストのコンパイラは呼び出しを潰せるので差が出ない。実機では
呼び出し回数と I-cache 圧がそのまま効いて +12.8% だった。

**ホストのプロファイルは「どこが重いか」の当たりを付けるのに使い、
効いたかどうかは必ず実機で判定する。** ホストだけを見ていたら、この
変更は「無意味」と判断して捨てていた。

### 効かなかった変更 (revert 済み)

`groupOrDiv` / `groupSub` / `memoryShift` を IRAM へ移した。IRAM に
157KB の空きがあったので「置けるなら置く」と判断したが、**実効は
4312 → 4315 kHz で変化なし**。この 3 つは全実行の 0.9% 程度しか通らない。

配置の最適化が効くのは**実際に頻繁に通るコードだけ**で、空きがあることは
理由にならない。元の「Flash のまま」というコメントの判断が正しかった。

### 残りの上限

CPU 本体が 70.3% を占めるので、**デバイス側を完全にゼロにしても
約 6100 kHz が上限**。それ以上はインタプリタ自体の作り替えが要る
(現状は「上位 4bit で分岐 → グループ内で switch」の 2 段デコード)。
